	\section{De TSP a VRP}
	El Problema del Vendedor Viajero (TSP, por sus siglas en inglés) es uno de los problemas de 
	optimización combinatoria más estudiados y fundamentales en la investigación de operaciones. 
	En su forma más simple, el problema busca determinar el recorrido más corto posible que visita 
	un conjunto de ciudades exactamente una vez, comenzando y terminando en la misma ciudad. 
	
	A pesar de su sencilla definición, el TSP es NP-duro, lo que significa que el tiempo requerido 
	para encontrar una solución óptima crece exponencialmente con el número de ciudades, haciendo 
	que las instancias de gran tamaño sean computacionalmente intratables para métodos exactos \citep{Lenstra1981}.

	El TSP sirve como pilar para una clase más amplia y práctica de problemas de logística: 
	el Problema de Enrutamiento de Vehículos (VRP). La transición conceptual del TSP al VRP o
	currió con el trabajo seminal de \citet{Dantzig1959}, quienes formularon "The Truck Dispatching 
	Problem". Este trabajo generalizó el TSP al considerar una flota de vehículos con capacidad 
	limitada, con el objetivo de servir a un conjunto de clientes desde un depósito central. 
	Esta generalización marcó el nacimiento del VRP, que busca minimizar el costo total de las 
	rutas (usualmente en términos de distancia o tiempo) para una flota de vehículos que atiende 
	a un conjunto de clientes con demandas conocidas.

	Al igual que el TSP, el VRP es NP-duro \citep{Lenstra1981}, pero su estructura es significativamente
	 más rica y compleja. La complejidad no solo reside en encontrar las secuencias óptimas de visitas 
	 (como en el TSP), sino también en asignar clientes a vehículos y rutas de manera eficiente \citep{Caceres-Cruz2014}. A lo 
	 largo de cinco décadas, el VRP ha evolucionado para incorporar una gran variedad de restricciones 
	 del mundo real, dando lugar a los llamados "Rich VRPs" \citep{Caceres-Cruz2014}. Estas extensiones 
	 incluyen, entre otras:

	\subsection{VRP clásico y extensiones con restricciones } % Dantzig1959, Caceres-Cruz2014, Laporte2009VRPSurvey

	\begin{itemize}
		\item \textbf{Capacidades de los vehículos (CVRP)}: Donde cada vehículo tiene una capacidad 
		máxima de carga que no puede ser excedida. El CVRP introduce la decisión adicional de no solo 
		determinar la secuencia de visitas, sino también decidir \textit{cuánto llevar} en cada viaje, 
		lo que aumenta significativamente la complejidad computacional del problema. Cada vehículo debe 
		partir desde un depósito central y retornar a él, respetando siempre la restricción de capacidad \citep{Caceres-Cruz2014}.
		
		\item \textbf{Ventanas de tiempo (VRPTW)}: Donde cada cliente debe ser atendido dentro de un 
		intervalo de tiempo específico. Las ventanas de tiempo añaden complejidad porque no solo se optimiza 
		la distancia de las rutas, sino también el tiempo, considerando que los vehículos pueden llegar 
		temprano (y esperar con costo de tiempo de espera) o llegar tarde (incurriendo en penalizaciones). 
		Esta restricción introduce la dimensión temporal explícita al problema de ruteo \citep{Caceres-Cruz2014}.
		
		\item \textbf{Múltiples depósitos (MDVRP)}: Donde los vehículos pueden iniciar y terminar sus rutas
		 desde diferentes ubicaciones, en lugar de un único depósito central. Esto introduce complejidad 
		 adicional porque el algoritmo debe decidir no solo las rutas de visita, sino también asignar 
		 qué vehículos operan desde qué depósitos. El MDVRP es relevante en contextos logísticos donde 
		 múltiples centros de distribución sirven diferentes regiones geográficas \citep{Caceres-Cruz2014}.
	\end{itemize}

	Más allá de estas extensiones fundamentales, la literatura identificada en \citet{Laporte2009VRPSurvey} 
	documenta otras variantes relevantes, como problemas con pickup y delivery (recogida y entrega en diferentes 
	ubicaciones), problemas con splits de demanda (dividir la demanda de un cliente entre múltiples vehículos) y 
	problemas con tiempos de servicio variables. Cada una de estas extensiones añade dimensiones de realismo 
	operacional, pero también incrementa exponencialmente la dificultad de encontrar soluciones óptimas.

	La progresión desde el VRP clásico hacia variantes más complejas establece el contexto para entender el 
	Problema de Enrutamiento de Entrega de Comida (MDRP). El MDRP no es simplemente una combinación de estas 
	restricciones estáticas; es un problema fundamentalmente \textit{dinámico} en el que nuevas órdenes arriban 
	continuamente durante el día operativo, requiriendo que las decisiones de ruteo se reoptimicen periódicamente. 
	Este cambio de paradigma de problemas estáticos a dinámicos, junto con la necesidad de considerar redes viales 
	reales, sitúa la motivación y relevancia del presente trabajo.
	
	
	\section{Última milla y contexto urbano} % Jazemi2023
	
	La última milla de entrega---el segmento final desde un centro de distribución o 
	punto de recogida hasta el domicilio del cliente---representa el componente más 
	costoso, complejo y crítico en logística urbana. Jazemi et al. (2023) documentan 
	que la última milla puede representar entre el 30\% y el 60\% del costo total de 
	una operación de envío, dependiendo de la densidad urbana, la dispersión geográfica 
	de clientes y la volatilidad de la demanda \cite{Jazemi2023}.
	
	En el contexto de entrega de comida rápida, la última milla presenta desafíos 
	específicos adicionales: (1) alta urgencia---los clientes esperan entregas 
	en ventanas de 30-60 minutos desde la orden, significativamente más restrictivas 
	que en logística general; (2) perecedibilidad---la comida debe mantener 
	temperatura, frescura y presentación, implicando rutas directas sin desviaciones 
	innecesarias; (3) demanda dinámica e impredecible---los flujos de órdenes no son 
	uniformes sino que presentan picos pronunciados (horas de almuerzo, cena), 
	requiriendo reoptimización continua de asignaciones.
	
	Estas características transforman la última milla de comida en un problema 
	distinto del VRP clásico: es inherentemente dinámico, con ventanas de tiempo 
	estrictas y demanda estocástica. Aunque la literatura de ruteo dinámico 
	\cite{Psaraftis1980, Cordeau2007} y las estrategias de anticipación 
	\cite{Ichoua2006DDARP} han abordado componentes de este desafío, la entrega de 
	comida presenta particularidades únicas que requieren una integración específica 
	de estos conceptos, como se explora en la siguiente sección.

	\section{Ruteo dinámico: DVRP y DARP} % Larsen2000DVRP, Psaraftis1980, Cordeau2007, Ichoua2006DDARP
	
	Mientras que el VRP clásico y sus extensiones (CVRP, VRPTW, MDVRP) asumen que todas las demandas de clientes 
	son conocidas \textit{ex-ante} (antes de la ejecución), la realidad operacional de los sistemas de entrega 
	urbana es fundamentalmente distinta: nuevas órdenes llegan continuamente durante el día, y las decisiones de 
	despacho deben reoptimizarse en tiempo real. Este cambio de paradigma de lo \textit{estático} a lo \textit{dinámico} 
	define una nueva clase de problemas de ruteo que requieren políticas de despacho adaptativas.
	
	\subsection{DVRP: Definición y características fundamentales}
	
	Larsen (2000) proporciona la taxonomía fundamental del Problema de Ruteo de Vehículos Dinámico (DVRP), 
	definiéndolo como una clase de problemas donde, en contraste con el VRP estático, ``nuevas solicitudes 
	de clientes arriban en tiempo real durante la operación, y el conjunto de clientes a atender no es conocido 
	completamente en el inicio'' \cite{Larsen2000DVRP}. Formalmente, el DVRP se caracteriza por:
	
	\begin{itemize}
		\item \textbf{Llegada estocástica de solicitudes}: Las órdenes no existe como conjunto fijo, sino que 
		arriban según un proceso estocástico.
		
		\item \textbf{Reoptimización periódica}: El plan de ruteo no es estático sino que debe recalcularse 
		continuamente. Las decisiones previas (repartidores ya en ruta) no pueden revertirse completamente, pero 
		las nuevas decisiones pueden considerar órdenes recién llegadas.
		
		\item \textbf{Incertidumbre temporal}: No solo la demanda es incierta, sino también los tiempos de 
		viaje pueden variar por congestión u otros factores, lo que crea desviaciones entre el plan y la ejecución.
		
		\item \textbf{Disyuntiva decisión-información}: Cada política de despacho enfrenta un dilema: decidir 
		inmediatamente (riesgo de decisiones subóptimas) vs. esperar más información (riesgo de incumplir criterios de servicio). 
		Pillac et al. (2013) profundizan en este aspecto, clasificando los problemas según su grado de dinamismo y la calidad de la información disponible \cite{Pillac2013}.
	\end{itemize}
	
	Esta caracterización es central para entender la última milla de entrega: cada vez que un cliente 
	coloca una orden en una plataforma de entrega de comida (Grubhub, Uber Eats, DoorDash), el sistema de despacho enfrenta una decisión 
	urgente: asignar esa orden a un repartidor para que sea recogida y entregada. La decisión no puede posponerse 
	indefinidamente (los clientes esperan entregas en 30-60 minutos), pero tampoco puede hacerse de forma 
	completamente reactiva sin consideración del contexto futuro.
	
	\subsection{DARP: Del transporte de pasajeros a la entrega de bienes}
	
	Un problema históricamente relacionado pero conceptualmente distinto es el Dial-a-Ride Problem (DARP). 
	Las raíces del DARP se encuentran en Psaraftis (1980), quien formuló el primer modelo dinámico de 
	dial-a-ride: en sistemas de transporte compartido (típicamente para pasajeros), usuarios solicitan 
	recogida en una ubicación y entrega en otra ubicación diferente, y ambas solicitudes llegan en tiempo 
	real. Psaraftis (1980) abordó la pregunta central: ¿cómo asignar dinámicamente los pasajeros a vehículos 
	y secuenciar sus viajes de forma óptima bajo políticas de despacho inmediato? \cite{Psaraftis1980}
	
	Cordeau y Laporte (2007) extendieron significativamente este trabajo, formalizando matemáticamente el 
	Dial-a-Ride Problem y desarrollando heurísticas de solución prácticas \cite{Cordeau2007}. Su 
	contribución fue crítica para la investigación en ruteo dinámico. Definieron explícitamente las 
	restricciones estructurales del DARP:
	
	\begin{itemize}
		\item \textbf{Restricción de capacidad}: Cada vehículo tiene límite de pasajeros simultáneos.
		
		\item \textbf{Restricción de secuencia temporal}: Un pasajero debe ser recogido antes de ser entregado, 
		con límite temporal máximo entre recogida y entrega.
		
		\item \textbf{Ventanas de tiempo}: Tanto recogida como entrega pueden tener ventanas horarias de disponibilidad.
		
		\item \textbf{Criterios de optimización}: Minimización de distancia total o tiempo total de espera, 
		frecuentemente con penalizaciones por incumplimiento de compromisos de tiempo.
	\end{itemize}
	
	Aunque el DARP fue originalmente formulado para transporte de pasajeros, su estructura conceptual es 
	directamente transferible a problemas de entrega de bienes. De hecho, la estructura matemática es análoga: 
	en lugar de ``recoger un pasajero en ubicación A y entregar en ubicación B'', se tiene ``recoger una 
	orden en restaurante A y entregar en domicilio B''. Sin embargo, existen diferencias operacionales críticas:
	
	\begin{itemize}
		\item En transporte de pasajeros, la restricción de secuencia es rígida (recogida antes de entrega), 
		mientras que en entrega de comida existe más flexibilidad: múltiples órdenes de diferentes restaurantes 
		pueden incluirse en una sola ruta.
		
		\item En transporte de pasajeros, el tiempo entre recogida y entrega es determinístico (depende de la 
		ruta), mientras que en comida existe heterogeneidad: tiempo de preparación varía por restaurante, 
		impactando cuando la orden está disponible para recogida.
		
		\item En transporte de pasajeros, la experiencia del cliente es inmediata (espera observable), mientras 
		que en comida, el cliente está dispuesto a esperar mientras el pedido se prepara, reduciendo la presión 
		sobre latencia de decisión de despacho.
	\end{itemize}
	
	\subsection{El valor de la información futura y el enfoque de Horizonte Rodante}
	
	A pesar de la diferencia entre DVRP y DARP, ambas clases de problemas comparten una pregunta fundamental: ¿Deben las decisiones ser reacitvas (FCFS) 
	o pueden ser anticipatorias?
	
	Ichoua et al. (2006) abordaron directamente esta pregunta en el contexto de dial-a-ride dinámico. Compararon 
	políticas de despacho que desconocen solicitudes futuras (puramente reactivas) contra políticas que tienen 
	acceso a información sobre solicitudes que llegarán en los próximos 20-30 minutos. Su hallazgo fue 
	significativo: en escenarios críticos con elevada tasa de llegada de solicitudes, políticas anticipatorias 
	pueden lograr mejoras de hasta el 29\% en la reducción de clientes no servidos y entre 4-16\% en tiempo total 
	y retrasos, demostrando que la anticipación moderada proporciona ganancias sustanciales sin requerir 
	información perfecta sobre el futuro distante \cite{Ichoua2006DDARP}.
	
	Esta idea fundamental conecta DVRP/DARP con el concepto de horizonte rodante (rolling horizon): 
	en lugar de una asignación inmediata (FCFS), el sistema puede esperar un breve período (el horizonte $\Delta$, 
	típicamente 10-30 minutos), acumular un lote de solicitudes cuyo arribo es conocido con certeza relativa, 
	optimizar globalmente ese lote resolviendo un VRP estático (el ``matching'' óptimo), y luego ejecutar la 
	primera etapa de esa solución optimizada. En la siguiente época, repite el proceso.
	
	\section{MDRP y políticas de despacho} % Reyes2018
	
	El Problema de Enrutamiento de Entrega de Comida (MDRP) fue formalmente introducido por Reyes et al. (2018) 
	como una nueva clase de problema de ruteo dinámico que, aunque comparte características fundamentales con 
	DVRP y DARP, añade dimensiones específicas de la entrega de alimentos que lo distinguen conceptualmente y 
	requieren políticas de despacho especializadas.
	
	\subsection{Características compartidas con DVRP y DARP}
	
	Como todo problema DVRP, el MDRP hereda la característica de dinamicidad: nuevas órdenes arriban 
	continuamente en tiempo real, y el conjunto de demanda no es conocido \textit{ex-ante}. Como problema 
	similar a DARP, el MDRP hereda la estructura de recogida-entrega: una orden debe ser recogida en un 
	restaurante (fuente) y entregada en un domicilio (destino), con restricciones de ventanas de tiempo y 
	capacidad de vehículos. Estass características---dinamicidad y estructura pickup-delivery---crean el 
	contexto operacional básico.
	
	Sin embargo, Reyes et al. (2018) evidenciaron que estas dos extensiones no capturan plenamente la realidad de 
	la entrega de comida en ultima milla. El MDRP fue definido para llenar esta brecha, formulando un problema que 
	integra cinco características estructurales que no aparecen de forma acoplada en la literatura previa:
	
	\subsection{Definición y características del MDRP}

	Reyes et al. (2018) definen el MDRP como una clase de problema de recolección y entrega dinámico (DPDP) caracterizado por una
	 "urgencia extrema" y menores oportunidades de consolidación en comparación con la logística tradicional. Sus características
	  distintivas son:
	
	\begin{enumerate}
		\item \textbf{Múltiples puntos de recolección (Restaurantes):} A diferencia del VRP clásico con un depósito central, el 
		MDRP opera con múltiples restaurantes dispersos, cada uno actuando como un punto de recolección independiente con ubicación
		 fija.
		
		\item \textbf{Tiempos de preparación y "Ready Times":} Las órdenes no están listas inmediatamente al ser colocadas. 
		Reyes et al. (2018) introducen el concepto de \textit{ready time} ($e_o$) como una restricción dura: el courier no puede
		 recoger la orden antes de que la comida esté lista. Esto crea un buffer natural pero reduce la flexibilidad del ruteo.
		
		\item \textbf{Alta urgencia y Dinamismo:} La mayoría de las solicitudes se revelan durante la operación (dinamismo puro) 
		y deben completarse en ventanas de tiempo muy cortas (urgencia), típicamente menos de una hora. Reyes et al. (2018) 
		señalan que esta combinación de dinamismo y urgencia es el desafío central del MDRP.
		
		\item \textbf{Bundling (Agrupamiento):} Para mejorar la eficiencia, el MDRP permite agrupar múltiples órdenes de un 
		mismo restaurante en una sola ruta ("bundles"). Aunque el modelo teórico de Reyes et al. (2018) asume capacidad 
		ilimitada para estos bundles, en la implementación práctica de esta tesis se considera la capacidad física limitada 
		de los vehículos (motocicletas/bicicletas) como una restricción operativa real.
	\end{enumerate}
	
	\subsection{Formalización del problema de despacho}
	
	Dado estas características, Reyes et al. (2018) formularon el MDRP como un problema de despacho dinámico 
	donde, en cada época de reoptimización (cada $\Delta$ minutos, típicamente 5-10 min), el sistema debe:
	
	\begin{enumerate}
		\item Acumular el conjunto de órdenes aún no asignadas $O^t$
		\item Determinar cuáles órdenes están lista para recogida (han superado el tiempo de preparación)
		\item Asignar estas órdenes a couriers disponibles $C$, considerando:
		\begin{itemize}
			\item Ubicación actual de cada courier
			\item Capacidad disponible del courier
			\item Ventana de tiempo restante de cada orden (riesgo de incumplimiento SLA)
			\item Multirrestaurante: un courier debe visitar múltiples restaurantes en una sola ruta
		\end{itemize}
		\item Secuenciar los pasos de recogida y entrega para minimizar tiempo total de ruta
		\item Comprometerse a la primera etapa del plan (decision commitment) y desechar el resto
	\end{enumerate}
	
	Esta formalización genera un problema de optimización de gran complejidad, que es NP-duro incluso para 
	instancias medianas. Reyes et al. (2018) demostraron que una heurística de horizonte rodante 
	(RH)---que resuelve el subproblema como VRP estático en cada época---produce mejoras sustanciales sobre 
	políticas miopes como FCFS.
	
	\subsection{Comparación: FCFS versus Rolling Horizon}
	
	La política de \textbf{First-Come-First-Served (FCFS)} es el baseline operacional más simple. En FCFS, 
	cuando una orden $o$ está lista para recogida (tiempo de preparación completado), el sistema identifica 
	inmediatamente el courier más cercano al restaurante y le asigna la orden:
	
	\begin{equation}
	c^* = \arg\min_{c \in C_{\text{available}}} d(c_{\text{loc}}, r_o)
	\end{equation}
	
	La complejidad es $O(n)$ donde $n$ es el número de couriers. FCFS es miope: no considera que esperar un 
	breve período podría permitir que órdenes futuras se agrupen con la actual, reduciendo viajes redundantes. 
	Como resultado, FCFS genera rutas subóptimas: entregas a múltiples domicilios desde un único restaurante 
	requieren viajes separados, y el sistema pierde oportunidades de consolidación.
	
	La política de \textbf{Rolling Horizon (RH)} implementa una estrategia anticipatoria. En lugar de asignar 
	órdenes inmediatamente, el sistema espera un horizonte $\Delta$ (típicamente 10-30 minutos), durante el cual 
	acumula todas las órdenes listas y pendientes, resuelve un VRP estático sobre este conjunto, y ejecuta la 
	primera etapa. La optimización en cada época es:
	
	\begin{equation}
	\min \sum_{c \in C} \text{costo}(\text{ruta}_c) + \sum_{o \in O^t} \text{penalización}(o)
	\end{equation}
	
	donde $\text{costo}(\text{ruta}_c)$ incluye distancia total, y $\text{penalización}(o)$ es un costo para 
	órdenes no asignadas (reflejando el riesgo SLA). El problema es NP-duro, pero instancias de 5-20 órdenes 
	y 15-60 couriers pueden resolverse en segundos mediante heurísticas (Lin-Kernighan, metaheurísticas, etc.).
	
	El beneficio de RH proviene del bundling (agrupación): órdenes geográficamente cercanas se asignan a un 
	único courier en una sola ruta, reduciendo distancia total de viaje y aumentando utilización de capacidad. 
	Reyes et al. (2018) demostraron experimentalmente que RH logra mejoras de aproximadamente 99\% en 
	órdenes/courier-hora comparado con FCFS (aumentando de ~20 a ~40 órdenes servidas por courier por hora) 
	\cite{Reyes2018}, con todo ello manteniendo cumplimiento de SLA en > 95\%.
	
	\subsection{Naturaleza anticipatoria del horizonte rodante}
	
	¿Por qué funciona mejor RH que FCFS? Ichoua et al. (2006) proporcionan la justificación teórica: el 
	valor de conocimiento sobre el futuro cercano. En su estudio de dial-a-ride dinámico, demostraron que 
	políticas que acceden a información sobre solicitudes futuras en un horizonte de 20-30 minutos pueden 
	superar políticas puramente reactivas en hasta 29\% (en instancias críticas) o de forma más conservadora 
	en 9\% en promedio general, sin necesidad de predicción perfecta. El mecanismo es la anticipación: el 
	sistema puede retrasar estratégicamente decisiones, esperando información que mejore la calidad de decisiones 
	futuras, incluso bajo incertidumbre residual \cite{Ichoua2006DDARP}.
	
	Para entrega de comida, existe un factor adicional que vuelve esta anticipación prácticamente ``gratuita'' 
	en términos de experiencia del cliente: los tiempos de preparación del restaurante. Cuando una orden es 
	colocada en $t=0$, está disponible para recogida en $t=p$ (tiempo de preparación). El horizonte de 
	reoptimización $\Delta$ (típicamente 15-30 minutos) puede ocurrir enteramente dentro del período de espera, 
	sin que el courier sea enviado prematuramente. Es decir, el RH no añade latencia perceptible al cliente; 
	en su lugar, aprovecha eficientemente la latencia existente en la cadena de preparación.
	
	\section{Ruteo realista en redes viales} % Haklay2010, Geisberger2008, Figliozzi2007
	
	Todas las políticas de despacho discutidas anteriormente (FCFS, RH) dependen críticamente de una entrada 
	fundamental: matrices de distancias o tiempos de viaje entre ubicaciones. Las decisiones de despacho son 
	tan buenas como la información de red que las informa. Sin embargo, existe una tensión fundamental en 
	logística académica: precisión versus disponibilidad.
	
	Sistemas comerciales como Google Maps, Mapbox y Here Maps proporcionan datos de red vial altamente precisos, 
	actualizados continuamente con información de tráfico real y capas geográficas completas. Sin embargo, su 
	costo operacional es prohibitivo: típicamente \$50-\$150 USD por día para consultas de ruteo a escala de 
	simulación. Para microempresas urbanas de entrega de comida, este costo elimina cualquier viabilidad económica. 
	Figliozzi (2007) documentó que esta tensión es real: distancias euclidianas (la aproximación más simple) 
	subestiman tiempos reales de viaje en 30-50\% en redes urbanas complejas \cite{Figliozzi2007}.
	
	La pregunta de investigación que surge es: ¿existe una alternativa que balance precisión y disponibilidad 
	económica? La respuesta viene de dos componentes que, combinadas, ofrecen una solución viable: datos abiertos 
	(OpenStreetMap) e infraestructura de ruteo de código abierto (OSRM).
	
	\subsection{OpenStreetMap: Datos abiertos de cartografía urbana}
	
	OpenStreetMap (OSM) es un proyecto colaborativo de mapeo global iniciado en 2004 que captura la geometría 
	de redes viales, límites administrativos, puntos de interés, y otros elementos geográficos, principalmente 
	mediante contribución voluntaria. A diferencia de cartografía comercial (Google Maps, Mapbox) o estatal 
	(catastros oficiales), OSM es un bien común digital: los datos son abiertos (licencia ODbL), reutilizables 
	sin restricciones comerciales, y auditables por cualquiera \cite{Haklay2010}.
	
	Haklay y Weber (2010) realizaron el primer análisis comprehensivo de la calidad de OSM, comparándolo contra 
	cartografía de referencia oficial en varios contextos urbanos \cite{Haklay2010}. Sus hallazgos fueron 
	significativos: en áreas urbanas bien documentadas (típicamente ciudades en países desarrollados y en líneas 
	de interés público), OSM alcanza una precisión horizontal (exactitud de posicionamiento) de 5-10 metros, 
	comparable a datos comerciales. Más importante aún, el nivel de cobertura de la red vial en áreas urbanas 
	es típicamente del 85-95\% en ciudades medianas desarrolladas, y ha mejorado consistentemente con el tiempo 
	conforme crece la comunidad de mapeadores.
	
	Para contextos latinoamericanos y ciudades medianas, la cobertura de OSM ha mostrado mejora significativa 
	en los últimos años. Aunque no alcanza la densidad de ciudades como Londres o Nueva York, ciudades medianas 
	como La Paz han sido ampliamente mapeadas, particularmente en zonas urbanas donde la densidad de usuarios y 
	mapeadores es mayor. El factor crítico es que OSM no es una instantánea estática: es una base de datos 
	viva que se actualiza continuamente. Esto permite que trabajos de investigación que utilicen OSM sean 
	reproducibles en múltiples contextos geográficos sin depender de acuerdos comerciales con proveedores de mapas.
	
	Las características clave de OSM relevantes para ruteo son:
	
	\begin{itemize}
		\item \textbf{Geometría de red}: OSM captura la topología de la red vial como un grafo, donde nodos 
		representan intersecciones y arcos representan segmentos de calle. Cada arco tiene atributos como nombre, 
		tipo de vía (autopista, calle, callejón), y restricciones de circulación (sentido único, prohibiciones 
		de acceso).
				
		\item \textbf{Metadatos de accesibilidad}: OSM registra restricciones de acceso (callejones sin salida, 
		zonas peatonales, etc.) que afectan el ruteo. Esto es especialmente importante en entrega urbana donde 
		ciertas rutas pueden estar prohibidas para vehículos de transporte comercial.
		
		\item \textbf{Escalabilidad temporal}: OSM permite trabajar con descargas históricas de datos, facilitando 
		reproducibilidad exacta: un experimento de 2025 puede ser replicado exactamente con la versión de OSM de 
		2025, sin depender de actualizaciones futuras que cambien resultados.
	\end{itemize}
	
	\subsection{OSRM: Infraestructura de ruteo de código abierto basada en Contraction Hierarchies}
	
	Aunque OSM proporciona datos abiertos, la pregunta operacional permanece: ¿cómo calcular rutas óptimas 
	eficientemente sobre esta red? Este es precisamente el problema que resuelve OSRM (Open Source Routing 
	Machine), una herramienta de código abierto que implementa algoritmos avanzados de ruteo sobre datos de OSM.
	
	OSRM fue originalmente desarrollada por Dennis Luxen en 2010 como respuesta a la necesidad de consultas de 
	ruteo rápidas, reproducibles y sin dependencias comerciales. La característica técnica que vuelve a OSRM 
	viable para aplicaciones dinámicas es su implementación del algoritmo de Contraction Hierarchies (CH).
	
	Geisberger et al. (2008) introdujeron Contraction Hierarchies, un algoritmo de preprocesamiento jerárquico 
	que acelera consultas de camino más corto (shortest path queries) en redes de carreteras en órdenes de 
	magnitud \cite{Geisberger2008}. La idea es ingeniosamente simple: antes de responder consultas, el algoritmo 
	preprocesa la red de carreteras de OSM, identificando y añadiendo ``atajos'' jerárquicos que reflejan 
	estructuras naturales de la red (por ejemplo, autopistas que conectan rápidamente regiones distantes). Este 
	preprocesamiento (ejecutado una sola vez) permite responder consultas de ruta en milisegundos, incluso para 
	redes con millones de nodos.
	
	¿Por qué es esto crítico para MDRP? Una simulación de horizonte rodante requiere recalcular rutas 
	repetidamente---potencialmente decenas o centenas de consultas en cada época de reoptimización. Si cada 
	consulta tomara segundos (como en un algoritmo de Dijkstra simple o una API comercial con latencia de 
	comunicación), la simulación sería computacionalmente inviable. OSRM, usando CH, realiza estas consultas 
	en milisegundos, haciendo viable el pipeline completo.
	
	Formalmente, CH funciona en dos fases:
	
	\begin{enumerate}
		\item \textbf{Preprocesamiento}: Dado una red de carreteras con $n$ nodos y $m$ arcos, CH identifica una 
		ordenación jerárquica de nodos. Para cada nodo, se computan ``atajos'' que conectan sus vecinos, omitiendo 
		el nodo intermedio. Esto se realiza iterativamente, contrayendo nodos (de menor importancia primero) y 
		registrando los atajos generados.
		
		\item \textbf{Consulta}: Para encontrar el camino más corto entre dos nodos, el algoritmo ejecuta búsqueda 
		bidireccional Dijkstra sobre la red aumentada (red original + atajos), deteniéndose cuando el punto de 
		encuentro supera la distancia conocida. Los atajos garantizan que la búsqueda no explora la mayoría de la red.
	\end{enumerate}
	
	El resultado empírico es dramático: en una red de carreteras de Europa (aproximadamente 18 millones de nodos), 
	CH realiza consultas de distancia en aproximadamente 1-2 milisegundos, comparado con 100-500 milisegundos para 
	Dijkstra simple, y segundos para APIs comerciales con latencia de comunicación.
	
	OSRM implementa CH junto con optimizaciones adicionales (caching, paralelización, compresión de datos) que lo 
	hacen viable para aplicaciones del mundo real. Típicamente, OSRM se despliega como un servicio containerizado 
	(Docker) que escucha consultas HTTP, preprocesa la red OSM una sola vez al inicio, y responde consultas en 
	tiempo real.
	
	\subsection{Viabilidad del pipeline: OSM + OSRM para simulación reproducible}
	
	La combinación de OSM y OSRM crea una arquitectura que es simultáneamente precisa, rápida y reproducible:
	
	\begin{itemize}
		\item \textbf{Precisión}: Utiliza geometría de red real (no distancias euclidianas), capturando topología 
		y topografía urbana. Figliozzi (2007) demostró que esta precisión es crítica: errores en estimaciones de 
		tiempo de viaje se propagan directamente a errores en SLA y utilización de recursos.
		
		\item \textbf{Velocidad}: CH permite consultas en milisegundos, habilitando reoptimización dinámica en 
		simulaciones sin penalidad computacional.
		
		\item \textbf{Reproducibilidad}: Ambos componentes son abiertos (código fuente disponible), abiertos 
		(datos auditables), y versionables (ambos tienen versiones explícitas). Un investigador en 2030 puede 
		replicar exactamente un experimento de 2025 usando OSRM v5.26.0 y OSM snapshot de 2025.
		
		\item \textbf{Transferibilidad}: Funciona para cualquier región con cobertura OSM, permitiendo aplicación 
		a contextos geográficos distintos de aquellos en benchmarks estándar (por ejemplo, Manhattan). Para ciudades 
		medianas latinoamericanas, esto es particularmente relevante.
	\end{itemize}
	
	Esta arquitectura contrasta agudamente con el status quo académico donde simulaciones MDRP utilizan distancias 
	euclidianas o matrices sintéticas (sin validación a redes reales), y con la práctica comercial donde APIs 
	propietarias generan dependencias que inhiben reproducibilidad. El pipeline OSM + OSRM + Docker ofrece una 
	tercera vía: rigor académico con realismo operacional y reproducibilidad completa.
	
	\section{Brecha de reproducibilidad y motivación del pipeline} % Merkel2014, Pillac2013, Reyes2018
	
	La visión de un pipeline integrado de simulación MDRP usando OSM+OSRM+Docker no surge del vacío, sino que 
	responde a brechas específicas en cómo la literatura contemporánea aborda el problema de validación de 
	políticas dinámicas de despacho. Para contextualizar, es útil revisar brevemente el panorama de herramientas 
	y aproximaciones disponibles.
	
	\subsection{Panorama de herramientas y simuladores: Estado del arte}
	
	Existen varias clases de soluciones para simular y evaluar políticas de ruteo:
	
	\textbf{(1) Plataformas comerciales de ruteo (Google Maps, Mapbox, Here Maps):} Proporcionan APIs que 
	calculan rutas óptimas usando datos de red vial real, actualizados continuamente. Ventajas: precisión, 
	integración con datos de tráfico real, interfaz estándar. Desventajas: costo prohibitivo (\$50-\$150/día 
	para volúmenes de simulación), dependencia externa, no reproducible (resultados pueden variar entre versiones 
	o regiones), imposible auditar algoritmos subyacentes.
	
	\textbf{(2) Simuladores académicos con distancias euclidianas (CVRP, VRPTW, MDVRP):} La mayoría de trabajos 
	en optimización combinatoria (desde Dantzig \& Ramser 1959 hasta trabajos contemporáneos) utilizan matrices 
	de distancia euclidiana o sintéticas, sin relación con geometría real. Ventajas: costo cero, fácil de 
	implementar, énfasis en algoritmos de optimización. Desventajas: falta de realismo (Figliozzi 2007 documenta 
	errores de 30-50\%), no transferible a contextos reales, resultados pueden no generalizarse.
	
	\textbf{(3) Frameworks de simulación general (SUMO, AnyLogic, Simul8):} Plataformas de simulación de eventos 
	discretos que pueden modelar transporte urbano, pero requieren configuración manual de redes viales y típicamente 
	se integran con APIs comerciales o matrices sintéticas. Ventajas: flexibilidad, soporte comercial. Desventajas: 
	complejidad, costo, dependencias externas.
	
	\textbf{(4) Herramientas de código abierto especializadas (OSRM, Vroom, GraphHopper):} Software de código 
	abierto que implementa ruteo eficiente. OSRM (Open Source Routing Machine) es específicamente diseñado para 
	consultas rápidas de camino más corto. Vroom (Vehicle Routing Open Optimization Machine) añade soporte para 
	VRP. GraphHopper es alternativa general de ruteo. Ventajas: código abierto, reproducible, rápido. Desventajas: 
	menor soporte comercial, requiere integración manual.
	
	\subsection{Heterogeneidad y fragmentación del ecosistema}
	
	La realidad actual del ecosistema de ruteo es fragmentada: no existe un estándar integrado que combine precisión, 
	velocidad, reproducibilidad y transferibilidad. En cambio, investigadores típicamente \textit{eligen}:
	
	\begin{itemize}
		\item \textbf{Precisión + velocidad pero sin reproducibilidad}: Usar APIs comerciales (Google Maps). 
		Resultados publicados no pueden ser auditados ni replicados exactamente.
		
		\item \textbf{Reproducibilidad + bajo costo pero sin realismo}: Usar distancias euclidianas. Resultados 
		no generalizan a contextos reales.
		
		\item \textbf{Parcialmente reproducible pero con complejidad}: Usar frameworks generales (SUMO, AnyLogic). 
		Integración manual, dependencias múltiples.
	\end{itemize}
	
	Para MDRP específicamente, Reyes et al. (2018) utilizó distancias euclidianas en sus experimentos publicados, 
	logrand demostraciones teóricas convincentes (99\% mejora RH vs FCFS), pero sin validación empírica contra 
	redes reales. Esta no es una crítica al trabajo de Reyes; refleja simplemente el estado de la práctica académica.
	
	\subsection{Motivación del pipeline: Cerrando la brecha con Docker}
	
	El presente trabajo propone un pipeline integrado que resuelve simultáneamente las dimensiones de precisión, velocidad, reproducibilidad y transferibilidad detalladas en la sección anterior. El componente unificador para garantizar la reproducibilidad técnica es la containerización.
	
	Merkel (2014) introdujo Docker como herramienta estándar para reproducibilidad en investigación e 
	ingeniería \cite{Merkel2014}. Docker permite capturar el estado completo de un experimento (versión de OSRM, 
	configuración de preprocesamiento, datasets, scripts de análisis) en un contenedor inmutable que puede 
	ejecutarse idénticamente en cualquier máquina. Para simulación MDRP, esto significa que un investigador 
	en 2030 puede descargar el contenedor original, ejecutarlo, y obtener exactamente los mismos resultados, 
	sin depender de actualizaciones de software o cambios en servicios externos.
	
	\subsection{Contribución específica del presente trabajo}
	
	La contribución de esta tesis no es inventar nuevos algoritmos de ruteo (CH ya existe desde 2008), ni 
	proponer nuevas políticas de despacho (RH ya existe desde Reyes 2018). En su lugar, la contribución es 
	\textit{integración y validación local}: construir un pipeline que combine componentes maduros (OSM, OSRM, 
	Docker) de una manera coherente, y validar que políticas de despacho abstractas (RH, FCFS) funcionan 
	efectivamente en contextos reales (La Paz, B.C.S.) con geometría y topografía específica.
	
	Pillac et al. (2013) enfatizaron que las políticas de reoptimización periódica (como RH) son un enfoque 
	estándar pero bien establecido para problemas dinámicos \cite{Pillac2013}. La pregunta abierta que permanece 
	es: ¿generalizan estas políticas a contextos urbanos no estudiados? ¿Funcionan en ciudades medianas latinoamericanas? 
	¿Qué configuraciones de parámetros (horizonte $\Delta$, frecuencia de reoptimización) son óptimas localmente?
	
	Este trabajo responde estas preguntas de forma reproducible y auditables, creando además un pipeline que 
	puede servir como referencia metodológica para trabajos futuros en otros contextos urbanos.
	
	\subsection{Sugerencias para mejora del pipeline (Extensiones futuras)}
	
	Durante la construcción del pipeline, varias mejoras potenciales han emergido, que se documentan aquí como 
	direcciones futuras:
	
	\begin{itemize}
		\item \textbf{Integración con datos de tráfico real}: OSRM actualmente usa velocidades promedio por tipo 
		de vía. Integración con datos de tráfico históricos (disponibles en plataformas como TomTom, AggData) 
		podría refinar estimaciones de tiempo de viaje, particularmente en horarios pico.
		
		\item \textbf{Modelado estocástico de tiempos de preparación}: Actualmente, tiempos de prep se sampleen 
		de distribuciones paramétricas. Usar datos históricos reales de restaurantes (si disponibles) podría 
		mejorar fidelidad.
		
		\item \textbf{Algoritmos de optimización más avanzados}: Actualmente se usa heurística simple (nearest 
		neighbor + 2-opt) para resolver VRP en cada época. Metaheurísticas (Tabu Search, Genetic Algorithms) o 
		solvers comerciales (Gurobi) podrían mejorar calidad de soluciones.
		
		\item \textbf{Machine Learning para predicción de demanda}: Actualmente se asume patrones estocásticos 
		conocidos. Usar ML (LSTM, XGBoost) para predicción de órdenes futuras podría refinar horizonte rodante.
		
		\item \textbf{Extensión a múltiples ciudades}: Validar el pipeline en otras ciudades medianas 
		latinoamericanas (Bogotá, Medellín, Quito) para confirmar generalización.
		
		\item \textbf{Integración con aprendizaje por refuerzo}: El pipeline construido podría servir como 
		``gym'' (entorno de simulación) para entrenar agentes de RL, como los descritos en Asadi et al. (2025) 
		y papers recientes de Meituan.
	\end{itemize}
	
	Estas extensiones no son requisitos para el trabajo actual, pero representan direcciones naturales de 
	investigación futura que construirían sobre la base reproducible aquí establecida.
	
	
	\chapter{Descripción del problema}
	
	El Problema de Enrutamiento de Entrega de Comida (MDRP) en ciudades medianas 
	presenta un desajuste fundamental entre los requisitos operacionales y la 
	viabilidad técnico-económica de las soluciones disponibles. Por un lado, 
	sistemas comerciales de ruteo (Google Maps, Mapbox) proporcionan precisión 
	geográfica mediante datos de red vial real, pero generan costos operacionales 
	prohibitivos (\$50-\$150 USD/día) que limitan su adopción por microempresas 
	urbanas \cite{Figliozzi2007}. Por otro lado, aproximaciones académicas basadas 
	en distancias euclidianas o matrices sintéticas reducen costos al eliminar 
	dependencias de APIs comerciales, pero sacrifican realismo: Figliozzi (2007) 
	documentó que distancias euclidianas subestiman tiempos reales de viaje en 
	30-50\% en redes urbanas complejas, comprometiendo la precisión de estimaciones 
	de SLA y utilización de couriers.
	
	Aunque la literatura reciente proporciona métodos promisorios, existe una 
	brecha de validación sin resolver. Reyes et al. (2018) propusieron una política 
	de horizonte rodante (Rolling Horizon) que demuestra mejoras de aproximadamente 
	99\% en eficiencia comparada con el baseline FCFS, pero esta validación se 
	limita a instancias sintéticas de Grubhub (contexto de metrópolis estadounidenses) 
	sin evidencia empírica de generalización a ciudades medianas ni vinculación 
	comprobada a geometría real de red vial. Consecuentemente, permanece sin resolver 
	la pregunta de investigación central: ¿generalizan las políticas de despacho 
	dinámico a topologías urbanas y contextos geográficos distintos de aquellos 
	usados en su validación original?
	
	Tres limitaciones específicas están asociadas a esta brecha y sirven como  
	motivación directa del presente trabajo. Primero, la dependencia de infraestructura 
	de ruteo propietaria inhibe reproducibilidad: estudios que utilizan APIs comerciales 
	no pueden ser auditados o replicados exactamente sin acceso a los mismos servicios 
	y versiones \cite{Merkel2014}. Segundo, la abstracción o simplificación de redes 
	viales en trabajos académicos compromete la transferencia a operaciones reales, 
	donde la complejidad topológica impacta directamente en estimaciones de tiempo 
	y eficiencia. Tercero, no existe en la literatura un pipeline de referencia que 
	integre datos abiertos (OpenStreetMap), herramientas de código abierto (OSRM), 
	y métodos reproducibles (containerización, control de semillas), que sirva como 
	estándar de validación local para algoritmos académicos en contextos urbanos 
	latinoamericanos.

	\chapter{Justificación}
	
	El MDRP combina dinámicas de demanda real (llegada estocástica de órdenes) con 
	restricciones de red compleja \cite{Reyes2018}. A diferencia de métodos exactos 
	\cite{Letchford2004} que requieren tiempo exponencial, y de Deep RL que demanda 
	entrenamiento costoso \cite{Lin2018GreedRL}, el horizonte rodante \cite{Pillac2013} 
	ofrece soluciones prácticas y evaluables. La brecha de investigación es local: 
	validar esta heurística en contextos urbanos específicos con infraestructura real 
	en lugar de simplificaciones.
	
	\section{Brecha científica y metodológica}
	Reyes et al. (2018) introdujeron el MDRP y demostraron que el RH con bundling 
	supera a políticas miopes. Sin embargo, su validación se limitó a instancias 
	sintéticas sin vinculación explícita a datos de red vial real. Figliozzi (2007) 
	demostró que las distancias reales difieren significativamente de euclidianas; 
	nuestro aporte es cerrar esa brecha usando OSM+OSRM en contexto real.
	
	\section{Viabilidad técnica: OSM y reproducibilidad}
	OSM proporciona cobertura del 100\% en La Paz urbana \cite{Haklay2010}. Docker 
	\cite{Merkel2014} garantiza reproducibilidad del código y del contenedor OSRM, 
	eliminando dependencias de APIs comerciales. Juan et al. (2015) validan que la 
	simulación es el método apropiado para evaluar políticas dinámicas con estocasticidad.
	
	\section{Impacto y transferibilidad}
	Resultados preliminares muestran 99.31\% mejora en órdenes/courier-hora, con 
	significancia estadística ($p < 0.0001$). El método es transferible a cualquier 
	ciudad con cobertura OSM, proporcionando alternativa económica a APIs propietarias.
	
	\section{Originalidad}
	Primera validación local del RH en La Paz usando infraestructura de código abierto, 
	con análisis estadístico robusto y documentación reproducible.

	vehicular se basa en el modo \texttt{car.lua}, ajustando únicamente las velocidades
	promedio para asemejarse al desempeño de motocicletas y bicicletas utilizadas por los
	couriers locales; cualquier modelado avanzado de tráfico o restricciones contextuales
	se documentará posteriormente en la metodología. El preprocesamiento se ejecuta con el
	pipeline \texttt{osrm-extract/partition/customize} y habilita Contraction Hierarchies para
	garantizar consultas en milisegundos \cite{Geisberger2008}. La precisión cartográfica se
	sustenta en la cobertura reportada por OpenStreetMap para La Paz (\textgreater 90\% de la
	red vial urbana), lo que permite prescindir de APIs propietarias sin sacrificar fidelidad
	geométrica \cite{Haklay2010}. En este capítulo solo se declara que el simulador utilizará
	esa infraestructura como ``caja negra'' confiable; los detalles operativos (mallas de
	validación, tamaños de caché, despliegue en Docker) se describirán en la metodología.

	\subsection{Políticas FCFS y RH (según Reyes2018)}
	El estudio confronta dos políticas ya caracterizadas en la sección de antecedentes: (i)
		extbf{First-Come-First-Served (FCFS)} como línea base operacional y (ii) \textbf{Rolling
	Horizon (RH)} como política anticipatoria propuesta por \citet{Reyes2018}. En términos de
	alcance, únicamente se implementarán las reglas mínimas necesarias para comparar ambas
	estrategias bajo idénticos parámetros de simulación: FCFS asigna cada orden lista al
	courier disponible con menor distancia OSRM al restaurante, mientras que RH acumula las
	órdenes liberadas durante un horizonte configurable (10--20 minutos), resuelve un VRP
	simplificado y ejecuta la primera ruta resultante, siguiendo el criterio anticipatorio
	descrito por \citet{Ichoua2006DDARP}. No se exploran variantes híbridas ni heurísticas
	adicionales; el objetivo funcional es establecer una referencia cuantitativa clara entre
	ambos extremos de complejidad. La instrumentación detallada (estructuras de datos,
	heurísticas de bundling o metaheurísticas internas) se traslada a la sección de
	metodología para evitar redundancia.

	\subsection{Generación de datos sintéticos (inspirados en LaDe)} % Wu2023LaDe
	La generación de datos sintéticos constituye el componente con mayor detalle en el
	alcance funcional, dado que condiciona todas las métricas posteriores. El escenario base
	se compone de 1,038 órdenes distribuidas entre las 11:00 y las 23:00 horas, con llegadas
	estocásticas calibradas contra los patrones bursátiles reportados para plataformas tipo
	LaDe \cite{Wu2023LaDe}. Cada orden incluye: restaurante origen (extraído del catálogo
	local con 142 ubicaciones georreferenciadas), domicilio destino (muestreado dentro del
	polígono urbano mediante densidades kernel ajustadas a datos históricos), valor del
	tiempo de preparación (log-normal truncada dependiente del tipo de cocina) y ventana
	implícita de servicio (click-to-door $\leq$ 60 minutos). La cohorte de 58 couriers se divide
	en dos turnos (matutino y vespertino) y se inicializa con posiciones reales para minimizar
	los efectos de arranque en frío. Todos los elementos del dataset se generan bajo una semilla
	determinística (\texttt{seed}=2025) y se almacenan tanto en formato CSV como Parquet para
	facilitar reproducción y trazabilidad. Aspectos como validación estadística de las
	distribuciones, sensibilidad a la semilla o incorporación de datos reales se desarrollarán
	en la metodología y en los anexos experimentales.

	scripts de arranque dentro del repositorio, siguiendo las buenas prácticas de

	\subsection{Trazabilidad de experimentos}
	Se adopta un esquema de trazabilidad que permita reconstruir cualquier corrida del

	establece que toda evidencia cuantitativa deberá quedar enlazada a su corrida
	generadora, facilitando auditoría y reproducción en etapas posteriores del proyecto.
	\section{Supuestos y limitaciones}
	\subsection{Tráfico estático y velocidades promedio}
	El ruteo depende de perfiles OSRM estáticos; aun cuando el perfil \texttt{car.lua}
	se ajustó para asemejarse al desempeño de motocicletas y bicicletas locales, las
	velocidades asociadas a cada tipo de vía permanecen fijas durante toda la
	simulación. Esto implica que fenómenos de congestión intrahoraria, cierres
	temporales o patrones de marea urbana no se representan explícitamente: todas las
	consultas heredan los tiempos de viaje promedio aprendidos durante la fase de
	preprocesamiento con Contraction Hierarchies \cite{Geisberger2008}. La
	consecuencia directa es que las métricas Click-to-Door tenderán a subestimar los
	picos reales en horas punta, justo como advierte \citet{Figliozzi2007} cuando se
	utilizan aproximaciones deterministas. Aceptar tráfico estático es un compromiso
	para privilegiar la reproducibilidad (no dependemos de APIs externas con datos en
	tiempo real), pero delimita el alcance de los resultados: cualquier despliegue en
	operación debería recalibrar velocidades o integrar feeds de tráfico, algo que se
	deja documentado como trabajo futuro.
	\subsection{Datos sintéticos vs. datos reales}
	Como se describió en la subsección de alcance funcional, el escenario de 1,038
	órdenes proviene íntegramente del generador sintético basado en patrones LaDe
	\cite{Wu2023LaDe}. Se conservará allí la descripción detallada de cómo se
	muestrean restaurantes, domicilios y tiempos de preparación, porque forma parte
	del alcance declarativo; en esta subsección sólo se explicita la limitación: no
	se cuenta con datos transaccionales reales debido a acuerdos de confidencialidad
	y restricciones de protección de información. En consecuencia, las demandas,
	tiempos de preparación y comportamiento de couriers reflejan distribuciones
	paramétricas calibradas mediante observaciones indirectas (análisis de densidad
	urbana, tasas de captura de órdenes y cuadros horarios reportados en
	\cite{Wu2023LaDe}), lo que implica que cualquier sesgo en esas suposiciones se
	propaga a los resultados. Para mitigar el riesgo se mantendrá versionado el
	dataset sintético (hash, semilla y scripts) y se propone como línea futura la
	validación cruzada con registros reales agregados cuando exista autorización.

	\section{Alcance metodológico}

	\subsection{Justificación del enfoque de simulación}

	La evaluación cuantitativa de políticas de despacho dinámico para el MDRP enfrenta un desafío metodológico fundamental: la naturaleza estocástica y dinámica del problema impide el uso de técnicas de optimización exacta tradicionales para determinar el desempeño de una política bajo condiciones operacionales realistas. A diferencia de problemas de ruteo estáticos, donde el conjunto completo de órdenes es conocido \textit{ex-ante} y puede resolverse mediante métodos de programación entera mixta o metaheurísticas deterministas, el MDRP requiere tomar decisiones de asignación y ruteo \textbf{bajo incertidumbre}: las órdenes arriban estocásticamente a lo largo del horizonte de operación, los tiempos de preparación de restaurantes varían de forma impredecible, y el estado del sistema (posiciones de couriers, órdenes pendientes) evoluciona continuamente.

	En este contexto, \citet{Juan2015} establecen que para problemas de ruteo vehicular con componentes estocásticos o dinámicos, \textbf{los enfoques puramente analíticos son insuficientes}. Los métodos exactos requieren conocer la distribución completa de probabilidad de todos los eventos futuros y resolver un problema de optimización estocástica de gran escala, lo cual es computacionalmente intratable para instancias realistas. Las aproximaciones deterministas (por ejemplo, resolver el problema reemplazando variables estocásticas por sus valores esperados) ignoran la variabilidad inherente del sistema y producen estimaciones sesgadas del desempeño real de las políticas.

	\paragraph{Simulación de eventos discretos como método de evaluación}

	La \textbf{simulación de eventos discretos} (Discrete Event Simulation, DES) emerge como el enfoque metodológico apropiado para evaluar políticas de despacho dinámico en el MDRP. Como argumentan \citet{Juan2015} en su revisión de simheurísticas, la simulación permite:

	\begin{enumerate}
		\item \textbf{Modelar explícitamente la estocasticidad:} Los tiempos de preparación de restaurantes se muestrean de distribuciones log-normales calibradas, los arribos de órdenes siguen procesos de Poisson no homogéneos con intensidad variable por hora del día, y las decisiones de las políticas se toman con información parcial sobre el futuro, reflejando fielmente las condiciones operacionales reales.

		\item \textbf{Capturar la dinámica temporal:} El simulador avanza mediante eventos discretos (llegada de orden, orden lista, courier disponible, inicio de recogida, completación de entrega), actualizando el estado del sistema de manera consistente y permitiendo que las políticas reaccionen a información en tiempo real.

		\item \textbf{Evaluar el desempeño a largo plazo:} Ejecutando múltiples réplicas de simulación con diferentes semillas aleatorias, es posible estimar las distribuciones de métricas de desempeño (Click-to-Door time, órdenes por courier-hora, utilización de flota) y cuantificar la variabilidad inherente al sistema, algo imposible con métodos deterministas.

		\item \textbf{Comparar políticas bajo condiciones controladas:} Al ejecutar FCFS y Rolling Horizon sobre exactamente las mismas instancias sintéticas (mismas órdenes, mismos tiempos de preparación, misma red vial), la simulación aísla el efecto puro de la política de despacho, eliminando variables confusoras.
	\end{enumerate}

	\paragraph{Validez y limitaciones del enfoque de simulación}

	La validez de los resultados obtenidos mediante simulación depende críticamente de dos factores:

	\textbf{(1) Fidelidad del modelo de simulación:} El simulador debe representar fielmente la estructura del sistema real, incluyendo las restricciones del MDRP (capacidades de couriers, ventanas de servicio, precedencia pickup-delivery), la infraestructura de ruteo (red vial real de La Paz mediante OSRM + OSM), y las distribuciones de eventos estocásticos (calibradas contra patrones LaDe \cite{Wu2023LaDe}). La sección de Metodología (Capítulo 7) documenta exhaustivamente la arquitectura del simulador, los procedimientos de calibración, y las pruebas de verificación y validación realizadas para garantizar que el modelo de simulación es una representación fiel del sistema MDRP.

	\textbf{(2) Reproducibilidad y control de aleatoriedad:} Todos los experimentos de simulación se ejecutan bajo control estricto de semillas aleatorias (\texttt{seed}=2025 para generación de instancias sintéticas, semillas independientes para réplicas de simulación), garantizando reproducibilidad bit-a-bit de los resultados. Como establecen \citet{Juan2015}, la reproducibilidad no es solo un requisito técnico, sino una condición necesaria para la verificación científica de los hallazgos.

	En síntesis, el enfoque de simulación de eventos discretos adoptado en este trabajo no es una elección arbitraria de conveniencia, sino la \textbf{consecuencia metodológica necesaria} de las características intrínsecas del MDRP: dinamicidad, estocasticidad, y complejidad combinatoria. La simulación constituye el método estándar en la literatura de ruteo dinámico \cite{Pillac2013} y es el único enfoque viable para evaluar rigurosamente el desempeño relativo de políticas de despacho bajo condiciones operacionales realistas. Las limitaciones de este enfoque (dependencia de la fidelidad del modelo, necesidad de múltiples réplicas para obtener estimaciones confiables) son reconocidas explícitamente y mitigadas mediante los procedimientos de validación y diseño experimental descritos en la Metodología.

	\section{Supuestos y limitaciones}

	\subsection{Eventos no modelados (cancelaciones, rechazos)}
	La simulación actual carece de eventos ``irregulares'' como cancelaciones de
	clientes, rechazos de couriers, reasignaciones sobre la marcha, múltiples apps
	por courier o tiempos muertos por incidencias (clima, inspecciones, accidentes).
	Las órdenes, una vez colocadas, se asumen irrevocables y siempre listas tras su
	tiempo de preparación; los couriers tampoco abandonan rutas ni se salen del
	servicio antes del fin de turno. Esta simplificación permite concentrar la
	evaluación en el efecto puro de las políticas FCFS vs. RH \cite{Reyes2018}, pero
	limita la transferencia directa a operaciones donde la tasa de cancelación puede
	superar el 5-8\%. Cualquier adopción industrial debería incorporar un módulo de
	eventos estocásticos y mecanismos de replaneación en caliente, aspecto que se
	documenta como restricción metodológica.

\section{Modelo Matemático del Meal Delivery Routing Problem (MDRP)}

El Meal Delivery Routing Problem (MDRP), introducido formalmente por \citet{Reyes2018}, establece
un marco conceptual para los sistemas dinámicos de entrega de alimentos que incorpora cinco dimensiones
operacionales ausentes en la literatura clásica del VRP: (i) múltiples depósitos heterogéneos
(restaurantes con tiempos de preparación independientes), (ii) llegada estocástica de órdenes en
tiempo real, (iii) ventanas de servicio Click-to-Door estrictas, (iv) capacidades limitadas de
couriers con requisitos de temperatura, y (v) estructura pickup-delivery con secuenciación forzada.
A continuación se formaliza la representación matemática del MDRP tal como se implementa en el
pipeline de simulación de este trabajo.

\subsection{Conjuntos y parámetros}

El modelo se construye sobre la base de los siguientes conjuntos fundamentales, siguiendo la notación
establecida por \citet{Reyes2018}:

\begin{itemize}
    \item $\mathcal{O} = \{o_1, o_2, \ldots, o_n\}$: Conjunto de órdenes de clientes. Cada orden
    $o \in \mathcal{O}$ se caracteriza por:
    \begin{itemize}
        \item $r_o \in \mathcal{R}$: Restaurante origen donde debe recogerse la orden
        \item $d_o \in \mathbb{R}^2$: Coordenadas geográficas del domicilio destino
        \item $t_o^{\text{placement}}$: Tiempo de colocación de la orden (click del cliente)
        \item $t_o^{\text{ready}}$: Tiempo en que la orden está lista para recogida ($= t_o^{\text{placement}} + p_{r_o}$)
        \item $\Delta_o^{\text{SLA}}$: Ventana de servicio máxima aceptable (típicamente 60 minutos)
    \end{itemize}
    
    \item $\mathcal{C} = \{c_1, c_2, \ldots, c_m\}$: Conjunto de couriers disponibles. Cada courier
    $c \in \mathcal{C}$ tiene:
    \begin{itemize}
        \item $\text{loc}_c(t) \in \mathbb{R}^2$: Posición geográfica en el tiempo $t$
        \item $Q_c$: Capacidad máxima de órdenes simultáneas (típicamente 3--6 pedidos)
        \item $[t_c^{\text{on}}, t_c^{\text{off}}]$: Ventana de disponibilidad del turno
    \end{itemize}
    
    \item $\mathcal{R} = \{r_1, r_2, \ldots, r_k\}$: Conjunto de restaurantes. Cada restaurante
    $r \in \mathcal{R}$ se caracteriza por:
    \begin{itemize}
        \item $\text{loc}_r \in \mathbb{R}^2$: Coordenadas geográficas fijas
        \item $p_r$: Tiempo de preparación promedio (log-normal truncada en implementación sintética)
    \end{itemize}
\end{itemize}

Además, el modelo incorpora funciones derivadas de la infraestructura OSRM que capturan la red vial real:

\begin{itemize}
    \item $d(i, j)$: Distancia de ruteo (en metros) entre ubicaciones $i, j \in \mathbb{R}^2$, calculada
    mediante Contraction Hierarchies \cite{Geisberger2008} sobre el grafo OSM
    \item $\tau(i, j)$: Tiempo de viaje (en minutos) entre ubicaciones $i, j$, considerando el perfil
    vehicular ajustado para motocicletas/bicicletas urbanas
\end{itemize}

\subsection{Variables de decisión y estructura de rutas}

El problema de despacho en cada época de reoptimización $t$ requiere determinar:

\begin{itemize}
    \item $x_{oc}^t \in \{0, 1\}$: Variable binaria que indica si la orden $o$ se asigna al courier $c$ en
    la época $t$
    \item $\pi_c^t = \langle (r_{o_1}, d_{o_1}), (r_{o_2}, d_{o_2}), \ldots \rangle$: Secuencia ordenada
    de pares (pickup, delivery) que define la ruta del courier $c$. Esta secuencia debe respetar:
    \begin{enumerate}
        \item Precedencia: El pickup de $o_i$ debe preceder a su delivery
        \item Capacidad: En ningún punto de la ruta $|\{\text{órdenes recogidas no entregadas}\}| > Q_c$
        \item Factibilidad temporal: $t_{o}^{\text{delivery}} \leq t_{o}^{\text{placement}} + \Delta_o^{\text{SLA}}$
    \end{enumerate}
\end{itemize}

\subsection{Función objetivo}

La formulación matemática del MDRP persigue dos objetivos interrelacionados que capturan la esencia
operacional del sistema. Siguiendo a \citet{Reyes2018}, el problema puede formalizarse como:

\begin{equation}
\min \quad Z = \sum_{c \in \mathcal{C}} \text{Cost}(\pi_c) + \lambda \sum_{o \in \mathcal{O}} \mathbb{I}(o \text{ no asignada})
\end{equation}

donde:

\begin{itemize}
    \item $\text{Cost}(\pi_c)$: Costo total de la ruta del courier $c$, típicamente medido como distancia
    total de viaje:
    \[
    \text{Cost}(\pi_c) = \sum_{(i,j) \in \pi_c} d(i, j)
    \]
    
    \item $\lambda$: Parámetro de penalización por órdenes no servidas, ajustado para reflejar riesgo de
    incumplimiento SLA
    
    \item $\mathbb{I}(\cdot)$: Función indicadora
\end{itemize}

En la práctica operacional y en la implementación de este trabajo, la función objetivo se reformula
en términos de **eficiencia del sistema**, medida como:

\begin{equation}
\max \quad \eta = \frac{\sum_{c \in \mathcal{C}} |\text{órdenes entregadas}_c|}{\sum_{c \in \mathcal{C}} \text{horas-turno}_c}
\end{equation}

Esta métrica de **órdenes por courier-hora** captura directamente el impacto de las decisiones de
bundling y ruteo sobre la productividad del sistema, siendo coherente con las métricas reportadas
por \citet{Reyes2018} en sus experimentos con datos de Grubhub.

\subsection{Restricciones del modelo}

El MDRP está sujeto a un conjunto de restricciones estructurales que reflejan las limitaciones
operacionales del sistema real:

\paragraph{(R1) Asignación única:} Cada orden debe ser asignada a exactamente un courier:
\begin{equation}
\sum_{c \in \mathcal{C}} x_{oc} = 1, \quad \forall o \in \mathcal{O}
\end{equation}

\paragraph{(R2) Capacidad del courier:} El número de órdenes simultáneas en posesión del courier $c$
en cualquier momento $t$ no puede exceder su capacidad:
\begin{equation}
|\{o : o \text{ recogida pero no entregada en } t\}| \leq Q_c, \quad \forall c \in \mathcal{C}, \forall t
\end{equation}

\paragraph{(R3) Ventana Click-to-Door:} El tiempo total desde la colocación de la orden hasta su
entrega no puede exceder el SLA:
\begin{equation}
t_o^{\text{delivery}} - t_o^{\text{placement}} \leq \Delta_o^{\text{SLA}}, \quad \forall o \in \mathcal{O}
\end{equation}

Esta restricción puede descomponerse en tres componentes temporales que caracterizan el MDRP:
\begin{align}
\text{Click-to-Door} &= \underbrace{(t_o^{\text{ready}} - t_o^{\text{placement}})}_{\text{Tiempo de preparación}} 
+ \underbrace{(t_o^{\text{pickup}} - t_o^{\text{ready}})}_{\text{Ready-to-Pickup}} \notag \\
&\quad + \underbrace{(t_o^{\text{delivery}} - t_o^{\text{pickup}})}_{\text{Pickup-to-Door}} \leq \Delta_o^{\text{SLA}}
\end{align}

\paragraph{(R4) Restricción de precedencia pickup-delivery:} Para cada orden, la recogida debe
preceder estrictamente a la entrega:
\begin{equation}
t_o^{\text{pickup}} < t_o^{\text{delivery}}, \quad \forall o \in \mathcal{O}
\end{equation}

\paragraph{(R5) Sincronización con tiempo de preparación:} Un courier no puede recoger una orden
antes de que esté lista:
\begin{equation}
t_o^{\text{pickup}} \geq t_o^{\text{ready}} = t_o^{\text{placement}} + p_{r_o}, \quad \forall o \in \mathcal{O}
\end{equation}

Esta restricción es crítica y diferencia al MDRP del DARP clásico \cite{Cordeau2007}: mientras
que en transporte de pasajeros el tiempo de servicio es determinístico y controlado por el sistema,
en entrega de comida el tiempo de preparación $p_{r_o}$ es exógeno, estocástico y específico de
cada restaurante.

\paragraph{(R6) Disponibilidad del courier:} Las operaciones de un courier están restringidas a su
ventana de turno:
\begin{equation}
t_c^{\text{on}} \leq t_o^{\text{pickup}}, t_o^{\text{delivery}} \leq t_c^{\text{off}}, 
\quad \forall o \text{ asignada a } c
\end{equation}

\subsection{Complejidad computacional}

El MDRP hereda la complejidad NP-dura del VRP clásico \cite{Lenstra1981}, pero añade dimensiones
adicionales de dificultad. Aun cuando el conjunto de órdenes $\mathcal{O}$ fuera conocido
completamente \textit{ex-ante} (eliminando la dimensión dinámica), el problema resultante sigue
siendo un VRP con ventanas de tiempo, capacidades y pickup-delivery simultáneo---una clase de
problemas para la cual no existen algoritmos de tiempo polinomial que garanticen soluciones óptimas
\cite{Letchford2004}.

La dinamicidad añade complejidad adicional: en cada época de reoptimización $t$, el conjunto
$\mathcal{O}^t$ de órdenes pendientes cambia, y las decisiones pasadas (couriers ya en ruta) crean
restricciones de estado que acoplan épocas sucesivas. Este acoplamiento temporal impide la
descomposición trivial del problema y motiva el uso de políticas heurísticas como FCFS y Rolling
Horizon, cuya evaluación es el objetivo central de este trabajo.

% SECCIÓN 2: Las dos soluciones que comparas
\section{Políticas de Despacho Dinámico: FCFS vs. Rolling Horizon}

En el contexto de sistemas dinámicos de ruteo de vehículos, la elección de una política de despacho
determina fundamentalmente cómo las órdenes entrantes son asignadas a la flota disponible. Como se
estableció en el capítulo de antecedentes, la naturaleza dinámica y urgente de la entrega de comida
crea un dilema operacional inherente: ¿deben las órdenes ser asignadas inmediatamente conforme están
listas (estrategia reactiva), o el sistema debe esperar estratégicamente para acumular información y
consolidar rutas (estrategia anticipatoria)? Esta sección formaliza matemáticamente ambas políticas,
establece sus fundamentos teóricos y caracteriza sus diferencias estructurales.

\subsection{Política Reactiva: First-Come-First-Served (FCFS)}

La política FCFS representa el baseline operacional más simple para el MDRP y sirve como referencia
contra la cual se evalúan estrategias más sofisticadas. Su principio rector es la inmediatez: tan
pronto como una orden alcanza su tiempo de preparación (i.e., $t \geq e_o$), el sistema ejecuta una
asignación inmediata al courier disponible con menor costo de acceso.

\subsubsection{Formulación matemática}

Formalmente, para cada orden $o \in \mathcal{O}$ que satisface $e_o \leq t$ (ya lista para recogida)
y aún no asignada, la política FCFS resuelve:

\begin{equation}
c^*(o) = \arg\min_{c \in \mathcal{C}_{\text{available}}(t)} \, d\big(loc_c(t), loc_{r_o}\big)
\end{equation}

donde:
\begin{itemize}
    \item $\mathcal{C}_{\text{available}}(t) = \{c \in \mathcal{C} : \text{ruta}_c(t) = \emptyset \land l_c > t\}$
    representa el conjunto de couriers sin rutas activas y cuyo turno aún no ha finalizado
    \item $loc_c(t)$ denota la ubicación del courier $c$ en el instante $t$
    \item $loc_{r_o}$ es la ubicación del restaurante origen de la orden $o$
    \item $d(\cdot, \cdot)$ es la función de distancia (o tiempo de viaje) proporcionada por OSRM
\end{itemize}

Una vez identificado el courier óptimo $c^*(o)$, la orden se asigna inmediatamente y se comunica
al courier una ruta individual $R_{c^*} = \{loc_{r_o}, loc_{drop\_o}\}$ que consta únicamente de
dos segmentos: recogida en el restaurante y entrega en el domicilio.

\subsubsection{Caracterización algorítmica}

El mecanismo de FCFS puede expresarse mediante el siguiente algoritmo:

\begin{algorithmic}
\STATE \textbf{Input:} Orden $o$ recién lista ($e_o \leq t$), conjunto de couriers $\mathcal{C}$
\STATE \textbf{Output:} Asignación courier-orden y ruta individual
\STATE
\STATE $\mathcal{C}_{\text{disp}} \leftarrow \{c \in \mathcal{C} : \text{ruta}_c = \emptyset\}$
\STATE $c^* \leftarrow \arg\min_{c \in \mathcal{C}_{\text{disp}}} d(loc_c, loc_{r_o})$
\STATE Calcular ruta $R = \text{OSRM}(loc_{c^*}, [loc_{r_o}, loc_{drop\_o}])$
\STATE Asignar $\text{ruta}_{c^*} \leftarrow R$
\STATE Actualizar $\text{estado}_o \leftarrow$ ``asignado''
\STATE \textbf{return} $(c^*, R)$
\end{algorithmic}

La complejidad computacional de esta operación es $O(|\mathcal{C}_{\text{disp}}|)$ para identificar
el courier óptimo, más el costo de una consulta OSRM (típicamente $O(1)$ bajo Contraction Hierarchies,
como se detallará en la Sección 5.3). En la práctica, esto implica que FCFS puede ejecutarse en
milisegundos incluso para flotas de 50-100 couriers.

\subsubsection{Limitaciones teóricas: Miopía y optimalidad local}

A pesar de su simplicidad y eficiencia computacional, FCFS sufre de dos limitaciones estructurales
críticas ampliamente documentadas en la literatura de ruteo dinámico \cite{Pillac2013}:

\textbf{(1) Miopía decisional:} FCFS no considera información sobre órdenes futuras que podrían beneficiarse
de consolidación. Ichoua et al. (2006) demostraron en el contexto de dial-a-ride dinámico que políticas
puramente reactivas (sin conocimiento del futuro) pueden tener desempeños 20-30\% inferiores a políticas
que explotan incluso información imperfecta sobre solicitudes próximas \cite{Ichoua2006DDARP}. En el
MDRP, esto se manifiesta dramáticamente: si dos órdenes del mismo restaurante están listas con diferencia
de 5 minutos, FCFS enviará dos couriers independientes, mientras que una política anticipatoria podría
consolidarlas en una sola ruta, reduciendo distancia total y aumentando utilización de capacidad.

\textbf{(2) Optimalidad local sin garantía global:} Cada decisión de FCFS es localmente óptima (minimiza
la distancia inmediata courier-restaurante), pero la secuencia de decisiones locales no garantiza
optimalidad global. Este fenómeno es análogo al problema clásico del algoritmo greedy en el TSP: la
heurística del vecino más cercano (nearest neighbor) produce soluciones típicamente 15-25\% más largas
que el óptimo global \cite{Laporte1992}. En el MDRP, donde las decisiones de asignación afectan la
disponibilidad futura de couriers y la distribución espacial de la flota, la acumulación de decisiones
miopes puede degradar significativamente el desempeño del sistema en períodos de alta demanda.

\subsection{Política Anticipatoria: Rolling Horizon (RH)}

La política de Rolling Horizon, introducida por Reyes et al. (2018) para el MDRP y sustentada en
principios generales de optimización dinámica establecidos por Pillac et al. (2013), representa una
estrategia fundamentalmente distinta: en lugar de reaccionar inmediatamente a cada orden, el sistema
espera estratégicamente un horizonte de tiempo $\Delta_u$ (típicamente 10-30 minutos), acumula un
lote de órdenes conocidas, resuelve un problema de matching óptimo sobre ese lote, y ejecuta únicamente
la primera etapa de la solución \cite{Reyes2018, Pillac2013}.

\subsubsection{Fundamento teórico: El valor de la información futura}

La justificación conceptual del Rolling Horizon proviene del reconocimiento de que, en problemas
dinámicos, \textit{postergar decisiones puede tener valor económico}. Este principio fue formalizado
por Ichoua et al. (2006) en el contexto del Dial-a-Ride Problem dinámico, donde demostraron que
políticas con acceso a información sobre solicitudes futuras (aunque imperfecta) superan consistentemente
a políticas puramente reactivas \cite{Ichoua2006DDARP}. El mecanismo subyacente es la \textit{flexibilidad
de consolidación}: al esperar brevemente, el sistema puede identificar órdenes geográficamente cercanas
o compatibles en tiempo, agrupándolas (bundling) en rutas consolidadas que reducen la distancia total
de viaje y aumentan la utilización de la capacidad de los couriers.

Para el MDRP, este principio es especialmente poderoso porque los tiempos de preparación de los
restaurantes crean naturalmente un ``buffer'' temporal: aunque una orden sea formalmente asignada en
$t$, el courier no puede recogerla hasta $e_o$ (cuando está lista). Este buffer absorbe parte del
tiempo de espera del horizonte sin comprometer el SLA del cliente, haciendo que la estrategia anticipatoria
sea prácticamente ``gratuita'' en términos de latencia percibida por el cliente.

\subsubsection{Descripción del mecanismo: Bucle de tres fases}

El Rolling Horizon opera mediante un ciclo repetido cada $f$ minutos (frecuencia de optimización,
típicamente $f=5$ min) que consta de tres fases:

\textbf{Fase 1: Acumulación de órdenes dentro del horizonte de asignación.} En cada época de
reoptimización $t$, el sistema identifica el conjunto de órdenes cuyo tiempo de preparación cae dentro
del horizonte $\Delta_u$:

\begin{equation}
\mathcal{U}_t = \{o \in \mathcal{O}_t : e_o \leq t + \Delta_u\}
\end{equation}

donde $\mathcal{O}_t$ denota todas las órdenes conocidas pero aún no asignadas en el tiempo $t$.
Nótese que $\Delta_u$ define la ``ventana de visibilidad'' del sistema: órdenes con $e_o > t + \Delta_u$
son ignoradas en esta época (serán consideradas en épocas futuras).

\textbf{Fase 2: Generación de bundles y solución del problema de matching.} Para las órdenes en
$\mathcal{U}_t$, el algoritmo genera \textit{bundles} (rutas consolidadas) mediante una heurística de
inserción paralela (detallada en el Procedimiento~1 de Reyes et al., 2018). Posteriormente, resuelve
un problema de matching bipartito para asignar bundles a couriers disponibles. La formulación del
matching se basa en maximizar un peso compuesto que balancea eficiencia (órdenes por hora) contra
calidad de servicio (penalizaciones por retrasos):

\begin{equation}
\max \sum_{b \in \mathcal{B}} \sum_{c \in \mathcal{C}_{\text{avail}}} w_{bc} \cdot x_{bc}
\end{equation}

sujeto a:
\begin{align}
\sum_{c \in \mathcal{C}_{\text{avail}}} x_{bc} &\leq 1 \quad \forall b \in \mathcal{B} \quad \text{(cada bundle asignado a lo más un courier)} \\
\sum_{b \in \mathcal{B}} x_{bc} &\leq 1 \quad \forall c \in \mathcal{C}_{\text{avail}} \quad \text{(cada courier recibe a lo más un bundle)} \\
x_{bc} &\in \{0,1\}
\end{align}

donde el peso $w_{bc}$ captura el costo-beneficio de asignar el bundle $b$ al courier $c$, definido como:

\begin{equation}
w_{bc} = \frac{|b|}{T_{bc}^{\text{delivery}}} - \theta \cdot (t_{bc}^{\text{pickup}} - e_b) - \text{penalización}_{\text{grupo}}(b)
\end{equation}

Aquí:
\begin{itemize}
    \item $|b|$ es el número de órdenes en el bundle
    \item $T_{bc}^{\text{delivery}}$ es el tiempo total desde que $c$ inicia la ruta hasta completar todas las entregas
    \item $\theta$ (parámetro $\texttt{PICKUP\_DELAY\_THETA}$) pondera la penalización por retraso en recogida
    \item $e_b = \max_{o \in b} e_o$ es el tiempo más temprano en que el bundle está completamente listo
    \item $\text{penalización}_{\text{grupo}}(b)$ es un término de prioridad que castiga bundles en riesgo
    de incumplir SLA (detallado en Reyes et al., 2018, Sección 3.2)
\end{itemize}

Este problema de matching se resuelve eficientemente en $O(|\mathcal{B}| \cdot |\mathcal{C}| \cdot \log(|\mathcal{C}|))$
mediante el algoritmo húngaro (Hungarian algorithm) \cite{Reyes2018}.

\textbf{Fase 3: Estrategia de compromiso (commitment).} Una vez resuelto el matching, no todas las
asignaciones se ejecutan inmediatamente. Siguiendo la estrategia de ``compromiso en dos etapas'' de
Reyes et al. (2018, Sección 3.3), cada asignación $(c, b)$ se evalúa bajo las siguientes reglas:

\begin{itemize}
    \item \textbf{Compromiso final:} Si todas las órdenes en $b$ están listas ($e_b \leq t + f$) y el
    courier $c$ puede iniciar la ruta antes de $t + f$, se comunica la ruta completa al courier (recogida
    + entregas).
    
    \item \textbf{Compromiso parcial:} Si las órdenes no están completamente listas pero el courier
    terminará su asignación actual antes de $t + f$, se comunica únicamente el movimiento hacia el
    restaurante (prepositioning), postergando la decisión sobre qué órdenes recoger.
    
    \item \textbf{Sin compromiso:} Si el courier no puede iniciar antes de $t + f$, la asignación se
    pospone para la siguiente época de reoptimización.
    
    \item \textbf{Excepción de forzado:} Si alguna orden en $b$ ha estado lista por más de un umbral
    crítico (típicamente 10-15 minutos, parámetro $\texttt{MAX\_WAIT\_BEFORE\_FORCED\_COMMIT}$), se
    fuerza un compromiso final inmediato para evitar degradación extrema de SLA.
\end{itemize}

Esta estrategia de compromiso gradual permite al sistema balancear flexibilidad (postergar decisiones
hasta tener mejor información) contra urgencia (ejecutar decisiones cuando el riesgo de incumplimiento
es alto).

\subsubsection{Parámetros clave del modelo y su impacto}

El desempeño del Rolling Horizon depende críticamente de cuatro parámetros fundamentales:

\begin{itemize}
    \item \textbf{Frecuencia de optimización ($f$):} Intervalo entre épocas de reoptimización. Valores
    típicos: 5 minutos. Un $f$ menor aumenta la capacidad de respuesta pero incrementa carga computacional;
    un $f$ mayor reduce costo computacional pero disminuye flexibilidad.
    
    \item \textbf{Horizonte de asignación ($\Delta_u$):} Ventana de visibilidad para órdenes futuras.
    Valores típicos: 15-30 minutos. Un $\Delta_u$ mayor permite identificar más oportunidades de
    consolidación, pero introduce riesgo de incumplimiento si la demanda es subestimada; un $\Delta_u$
    menor es más conservador pero pierde oportunidades de bundling.
    
    \item \textbf{Horizontes de lookahead ($\Delta_1, \Delta_2$):} Definen la ventana para calcular el
    tamaño objetivo de bundles $Z_t$. Como se describe en Reyes et al. (2018, Sección 3.1), el sistema
    calibra dinámicamente cuántas órdenes consolidar por bundle según la intensidad instantánea del sistema:
    
    \begin{equation}
    Z_t = \left\lceil \frac{|\{o \in \mathcal{O}_t : e_o \leq t + \Delta_1\}|}{|\{c \in \mathcal{C} : e_c^{\text{avail}} \leq t + \Delta_2\}|} \right\rceil
    \end{equation}
    
    donde $e_c^{\text{avail}}$ es el tiempo en que el courier $c$ estará disponible para nueva asignación.
    Esta fórmula induce bundles pequeños (incluso unitarios) cuando hay abundancia de couriers, y bundles
    grandes cuando el sistema está bajo presión.
    
    \item \textbf{Ponderación de frescura ($\beta$) y penalización de pickup ($\theta$):} Parámetros que
    controlan el trade-off entre consolidación agresiva (bundles grandes, menor distancia total) vs.
    calidad de servicio individual (entregas rápidas). Valores bajos de $\beta$ y $\theta$ favorecen
    eficiencia; valores altos favorecen velocidad de entrega.
\end{itemize}

\subsubsection{Justificación empírica: El caso Grubhub}

Reyes et al. (2018) validaron extensivamente el Rolling Horizon mediante simulaciones basadas en datos
históricos reales de Grubhub (Chicago, EUA), abarcando instancias con 50-150 couriers y 800-2,500
órdenes diarias. Sus resultados demostraron mejoras dramáticas sobre FCFS:

\begin{itemize}
    \item \textbf{Eficiencia operacional:} Rolling Horizon aumentó el throughput de 18-22 órdenes/courier-hora
    (bajo FCFS) a 35-42 órdenes/courier-hora, representando mejoras del orden de 90-100\%.
    
    \item \textbf{Calidad de servicio:} A pesar de la consolidación agresiva, el Click-to-Door promedio
    se mantuvo bajo control (35-40 minutos vs. 30-35 minutos de FCFS), y el cumplimiento de SLA (porcentaje
    de órdenes entregadas dentro de 60 minutos) superó consistentemente 95\%.
    
    \item \textbf{Utilización de couriers:} El bundling incrementó la utilización promedio de couriers
    de 60-65\% (FCFS) a 80-85\%, reduciendo el tiempo muerto y maximizando el valor de cada turno.
\end{itemize}

Estos resultados posicionan al Rolling Horizon como la política de referencia para sistemas MDRP de
escala industrial. Sin embargo, es crucial notar que la validación de Reyes et al. se limitó a instancias
sintéticas basadas en distancias euclidianas y contextos urbanos específicos (Chicago). La pregunta
de investigación central del presente trabajo es precisamente validar si estas mejoras se generalizan
a contextos urbanos distintos (ciudades medianas latinoamericanas) y bajo infraestructura de ruteo
realista (redes OSM + OSRM).

\section{Ruteo de Mínimo Costo en Redes Viales Reales}

La evaluación rigurosa de políticas de despacho dinámico requiere el cálculo de rutas de mínimo costo en redes viales reales. A diferencia de simplificaciones comunes que emplean distancias euclidianas (que ignoran la topología de calles, sentidos únicos, y patrones de conectividad urbana), el modelado realista de redes viales mediante grafos ponderados constituye un requisito fundamental para obtener resultados válidos en contextos de optimización dinámica. Esta sección presenta la formalización del problema de ruteo en redes viales, el algoritmo de \textit{Contraction Hierarchies} (CH) que permite consultas de camino más corto en tiempo sub-milisegundo, y la justificación teórica de por qué este enfoque algorítmico es indispensable para la viabilidad computacional del algoritmo de Rolling Horizon.

%======================================
% Sub-subsección: Modelado de Redes Viales como Grafos
%======================================
\subsection{Modelado de Redes Viales como Grafos Ponderados}

El modelado formal de redes viales se fundamenta en la teoría de grafos. Una red vial se representa como un grafo dirigido ponderado $G = (V, E, w)$, donde:

\begin{itemize}
    \item $V$ es el conjunto de \textbf{nodos} (también denominados vértices), que representan puntos geográficos de interés: intersecciones de calles, accesos a edificios, o cualquier punto de transición en la red de transporte.
    
    \item $E \subseteq V \times V$ es el conjunto de \textbf{arcos} dirigidos, donde cada arco $(u, v) \in E$ representa un segmento transitable de calle que conecta el nodo origen $u$ con el nodo destino $v$. La direccionalidad del grafo permite modelar restricciones de sentido único, giros prohibidos, y otras características de la topología vial urbana.
    
    \item $w: E \rightarrow \mathbb{R}^+$ es la función de \textbf{peso} que asigna a cada arco $(u, v)$ un costo positivo $w(u, v)$. Este peso representa típicamente el \textbf{tiempo de viaje esperado} (en segundos o minutos) o la distancia física (en metros) del segmento vial. En el contexto del MDRP, donde los tiempos de entrega son críticos, $w(u, v)$ se define como el tiempo de viaje, permitiendo optimizar la minimización del Click-to-Door time.
\end{itemize}

Formalmente, un \textbf{camino} $P$ en $G$ desde el nodo origen $s \in V$ hasta el nodo destino $t \in V$ es una secuencia ordenada de nodos $P = \langle v_0, v_1, \ldots, v_k \rangle$ tal que $v_0 = s$, $v_k = t$, y para cada par consecutivo $(v_i, v_{i+1})$ existe un arco $(v_i, v_{i+1}) \in E$. El \textbf{costo} (o longitud) del camino $P$ se define como la suma de los pesos de los arcos que lo componen:

\begin{equation}
w(P) = \sum_{i=0}^{k-1} w(v_i, v_{i+1})
\end{equation}

El \textbf{Problema de Camino Más Corto} (\textit{Shortest Path Problem}, SPP) consiste en encontrar, para un par dado de nodos $(s, t)$, un camino $P^*$ que minimice $w(P)$:

\begin{equation}
P^* = \arg\min_{P \in \mathcal{P}_{s,t}} w(P)
\end{equation}

donde $\mathcal{P}_{s,t}$ denota el conjunto de todos los caminos posibles desde $s$ hasta $t$ en $G$. La solución al problema SPP, conocida como \textbf{camino más corto} o \textbf{ruta óptima}, constituye la base para el cálculo de distancias y tiempos de viaje entre ubicaciones de restaurantes, clientes y posiciones de repartidores en el MDRP.

El algoritmo clásico para resolver SPP es el \textbf{algoritmo de Dijkstra} \citep{Dijkstra1959}, el cual garantiza encontrar el camino más corto desde un nodo origen $s$ a todos los demás nodos alcanzables en $G$ mediante una exploración sistemática del grafo. El algoritmo de Dijkstra mantiene un conjunto de nodos visitados y una estimación del costo mínimo desde $s$ a cada nodo, actualizando iterativamente estas estimaciones hasta encontrar el camino óptimo.

La \textbf{complejidad computacional} del algoritmo de Dijkstra, utilizando una cola de prioridad implementada con un heap binario, es de orden:

\begin{equation}
\mathcal{O}\bigl(|E| + |V| \log |V|\bigr)
\end{equation}

donde $|V|$ es el número de nodos y $|E|$ es el número de arcos del grafo. En redes viales urbanas de tamaño medio (como la red de La Paz, B.C.S.), $|V|$ puede alcanzar decenas de miles de nodos y $|E|$ centenas de miles de arcos. Aunque el algoritmo de Dijkstra es eficiente para consultas aisladas, presenta un desafío crítico en el contexto del algoritmo de Rolling Horizon del MDRP: \textbf{la necesidad de ejecutar consultas de camino más corto repetidamente, en tiempo real, para múltiples pares origen-destino}.

Considérese el escenario de reoptimización del Rolling Horizon: en cada periodo de optimización (cada 5 minutos en la configuración experimental), el algoritmo debe calcular los tiempos de viaje entre todos los repartidores disponibles y todos los pedidos pendientes, lo que puede requerir cientos o miles de consultas SPP por periodo. Si cada consulta requiriera varios segundos (como ocurriría con Dijkstra estándar en una red de gran escala), el tiempo total de cómputo haría \textbf{computacionalmente inviable} la simulación de escenarios realistas de múltiples horas de operación. Esta limitación motivó el desarrollo de técnicas de \textbf{preprocesamiento jerárquico} para acelerar consultas de camino más corto.

% Sub-subsección: Contraction Hierarchies (CH)
%======================================
\subsection{Contraction Hierarchies para Consultas Rápidas}

El algoritmo de \textbf{Contraction Hierarchies} (CH), introducido por \citet{Geisberger2008}, constituye una técnica de preprocesamiento jerárquico que permite realizar consultas de camino más corto órdenes de magnitud más rápidas que el algoritmo de Dijkstra clásico, a costa de un preprocesamiento inicial intensivo y un uso incrementado de memoria. CH es especialmente efectivo en redes viales, donde la estructura topológica presenta patrones jerárquicos naturales (autopistas, vías principales, calles secundarias).

El algoritmo de Contraction Hierarchies opera en dos fases bien diferenciadas:

\paragraph{Fase de Preprocesamiento (Contracción Jerárquica)}

En la fase de preprocesamiento, el grafo original $G$ se transforma en un \textbf{grafo aumentado} $G'$ mediante un proceso de contracción de nodos y creación de \textbf{atajos} (\textit{shortcuts}). El procedimiento consta de los siguientes pasos:

\begin{enumerate}
    \item \textbf{Ordenamiento de nodos:} Se establece un orden jerárquico de importancia sobre los nodos $V$, asignando a cada nodo $v \in V$ un rango $\text{rank}(v) \in \{1, 2, \ldots, |V|\}$. Este ordenamiento se calcula mediante heurísticas que consideran el grado del nodo, la centralidad en la red, y el impacto de contraer el nodo en el tamaño del grafo resultante. Los nodos menos importantes (típicamente calles residenciales o vías secundarias) reciben rangos bajos, mientras que los nodos críticos (intersecciones principales, accesos a autopistas) reciben rangos altos.
    
    \item \textbf{Contracción iterativa:} Los nodos se contraen en orden ascendente de rango (del menos importante al más importante). Al contraer un nodo $v$, se eliminan todos los arcos que inciden en $v$ (arcos entrantes y salientes). Sin embargo, antes de eliminar $v$, se verifica si algún camino más corto en el grafo original pasaba a través de $v$. Si existen pares de nodos $(u, w)$ tales que el camino más corto de $u$ a $w$ pasaba por $v$ (es decir, $u \rightarrow v \rightarrow w$), se crea un \textbf{atajo} (arco directo) $(u, w)$ con peso igual al costo del camino original $w(u, v) + w(v, w)$. Este atajo preserva la distancia más corta incluso después de eliminar $v$ del grafo.
    
    \item \textbf{Grafo augmentado resultante:} Al finalizar la contracción de todos los nodos, el grafo original $G$ ha sido transformado en un grafo aumentado $G' = (V, E \cup E_{\text{shortcuts}})$, donde $E_{\text{shortcuts}}$ es el conjunto de atajos creados durante la contracción. Cada arco en $G'$ (ya sea original o atajo) mantiene información sobre el rango del nodo que lo generó, permitiendo explotar la jerarquía durante las consultas.
\end{enumerate}

El preprocesamiento de CH, aunque computacionalmente costoso (puede requerir minutos u horas dependiendo del tamaño de la red), se ejecuta \textbf{una sola vez} de forma offline. El resultado (el grafo aumentado $G'$ con atajos) se almacena en disco y se carga en memoria al iniciar la simulación, permitiendo consultas rápidas repetidas sin necesidad de recalcular la jerarquía.

\paragraph{Fase de Consulta (Búsqueda Bidireccional Jerárquica)}

Una vez completado el preprocesamiento, las consultas de camino más corto entre cualquier par de nodos $(s, t)$ se realizan mediante una \textbf{búsqueda bidireccional} en el grafo aumentado $G'$, explotando la jerarquía de nodos para reducir drásticamente el espacio de búsqueda.

El procedimiento de consulta opera de la siguiente manera:

\begin{enumerate}
    \item \textbf{Búsqueda hacia adelante desde $s$:} Se ejecuta una variante modificada del algoritmo de Dijkstra desde el nodo origen $s$, explorando únicamente arcos $(u, v) \in E'$ donde $\text{rank}(v) > \text{rank}(u)$. Es decir, la búsqueda hacia adelante solo asciende en la jerarquía, moviéndose hacia nodos de mayor importancia. Esta restricción garantiza que la búsqueda se dirige hacia las "autopistas" de la red jerárquica.
    
    \item \textbf{Búsqueda hacia atrás desde $t$:} Simultáneamente, se ejecuta una búsqueda hacia atrás desde el nodo destino $t$ en el grafo transpuesto, explorando solo arcos donde se asciende en la jerarquía (desde $t$ hacia nodos de mayor rango). Esta búsqueda identifica los nodos importantes desde los cuales es posible descender hacia $t$.
    
    \item \textbf{Encuentro en nodos de alto rango:} Las dos búsquedas (hacia adelante y hacia atrás) se encuentran en un conjunto reducido de nodos de alto rango (típicamente nodos cercanos a la "columna vertebral" jerárquica de la red). El camino más corto se reconstruye combinando las distancias encontradas por ambas búsquedas.
\end{enumerate}

La \textbf{complejidad de consulta} de Contraction Hierarchies es de orden:

\begin{equation}
\mathcal{O}\bigl(k \log k\bigr)
\end{equation}

donde $k$ representa el número de nodos visitados durante la búsqueda bidireccional. En redes viales bien estructuradas, $k$ es típicamente varios órdenes de magnitud menor que $|V|$, debido a que la búsqueda jerárquica explora solo una fracción pequeña del grafo total. Empíricamente, \citet{Geisberger2008} reportan tiempos de consulta del orden de \textbf{microsegundos a milisegundos} en redes viales continentales (con millones de nodos), en comparación con segundos o minutos requeridos por Dijkstra estándar en las mismas redes.

Esta aceleración de consultas de camino más corto es \textbf{crítica para la viabilidad computacional del algoritmo de Rolling Horizon}. En cada periodo de optimización, el matching bipartito entre repartidores y pedidos requiere calcular las distancias entre todos los repartidores disponibles y todas las ubicaciones de pedidos (restaurantes y clientes). Si se tienen $C$ repartidores disponibles y $O$ pedidos pendientes, el número de consultas de camino más corto puede alcanzar $\mathcal{O}(C \cdot O)$ por periodo. Con consultas en milisegundos (gracias a CH), un periodo de optimización con $C=50$ repartidores y $O=100$ pedidos requiere aproximadamente 5,000 consultas $\times$ 1 ms = 5 segundos de cómputo total para distancias, lo cual es factible para simulación en tiempo razonable. En contraste, si cada consulta requiriera 1 segundo (Dijkstra estándar), el mismo periodo requeriría más de 1 hora de cómputo, tornando la simulación inviable.

%======================================
% Sub-subsección: OSRM y su Implementación en la Simulación
%======================================
\paragraph{OSRM: Implementación Práctica de Contraction Hierarchies}

La implementación concreta del algoritmo de Contraction Hierarchies en este trabajo se realiza mediante \textbf{OSRM (Open Source Routing Machine)}, una plataforma de ruteo de código abierto que implementa CH sobre datos de \textit{OpenStreetMap} (OSM). OSRM se configura localmente en un servidor HTTP (\texttt{localhost:5000}) que responde a consultas de ruteo en tiempo real.

La versión utilizada es \textbf{OSRM v5.26.0}, ejecutándose en un contenedor Docker para garantizar reproducibilidad del entorno de ruteo. El preprocesamiento de CH se ejecuta una vez sobre el archivo \texttt{map.osm} (extracto de la red vial de La Paz, B.C.S. descargado desde OpenStreetMap), generando las estructuras de datos jerárquicas que permiten consultas rápidas. El archivo preprocesado se almacena en cache y se reutiliza en todas las ejecuciones de simulación.

Durante la simulación, el módulo \texttt{getrouteOSMR.py} realiza llamadas HTTP al endpoint de ruteo de OSRM:

\begin{verbatim}
GET http://localhost:5000/route/v1/driving/{lon,lat};{lon,lat}
\end{verbatim}

donde cada par \texttt{\{lon,lat\}} representa las coordenadas geográficas (longitud, latitud) de un punto de ruta. OSRM responde con un objeto JSON que contiene:

\begin{itemize}
    \item \textbf{Distancia total:} longitud física de la ruta en metros.
    \item \textbf{Duración total:} tiempo de viaje estimado en segundos, calculado considerando los límites de velocidad y tipo de vía de cada segmento vial según los metadatos de OSM.
    \item \textbf{Geometría de la ruta:} secuencia de coordenadas geográficas que define el trayecto completo, codificada en formato \textit{polyline} para compresión.
\end{itemize}

El tiempo de respuesta típico de OSRM para consultas punto-a-punto en la red de La Paz es de \textbf{1-2 milisegundos}, confirmando empíricamente la eficiencia del algoritmo CH implementado. Para reducir aún más la latencia de consultas repetidas (por ejemplo, cuando un repartidore se asigna al mismo restaurante múltiples veces), el módulo \texttt{getrouteOSMR.py} implementa un \textbf{cache en memoria} que almacena resultados de consultas previas, evitando llamadas HTTP redundantes.

En resumen, el uso de OSRM con Contraction Hierarchies garantiza que el cálculo de rutas de mínimo costo se realiza sobre la topología vial real de La Paz (no sobre simplificaciones euclidianas), con tiempos de consulta sub-milisegundo que hacen computacionalmente viable la ejecución de simulaciones de Rolling Horizon con cientos de pedidos y decenas de repartidores operando simultáneamente. Esta infraestructura de ruteo realista constituye un pilar fundamental de la validez experimental del presente trabajo.

\section{Fundamentos de la Reproducibilidad Computacional}

La validez de los resultados de investigación en ciencias computacionales no depende únicamente de la solidez teórica de los algoritmos implementados o de la calidad de los datos empleados. En el contexto de experimentos de simulación y optimización dinámica (como el MDRP), la capacidad de \textbf{reproducir} los resultados de manera independiente constituye un requisito metodológico fundamental para garantizar la verificabilidad, transparencia, y comparabilidad de las contribuciones científicas. Esta sección presenta el concepto de reproducibilidad computacional, la \textit{crisis de reproducibilidad} que afecta a múltiples disciplinas científicas, la distinción conceptual entre virtualización y containerización, y el rol específico de Docker como tecnología habilitadora de entornos de ejecución reproducibles.

%======================================
% Subsección: La Crisis de Reproducibilidad en la Ciencia Computacional
%======================================
\subsection{La Crisis de Reproducibilidad en la Ciencia Computacional}

La \textbf{reproducibilidad} se define como la capacidad de un investigador independiente de obtener los mismos resultados cuantitativos que un estudio previo, ejecutando el mismo código con los mismos datos de entrada en un entorno computacional equivalente. A diferencia de la \textit{replicabilidad} (que implica reproducir el estudio completo con nuevos datos o implementaciones independientes), la reproducibilidad se enfoca específicamente en la capacidad de verificar que los resultados reportados en un artículo científico pueden ser regenerados de manera exacta a partir de los artefactos computacionales originales (código, datos, configuraciones).

A pesar de ser un principio fundamental del método científico, la reproducibilidad computacional enfrenta desafíos críticos que han dado lugar a lo que se conoce como la \textbf{crisis de reproducibilidad}. Múltiples estudios empíricos han documentado tasas alarmantemente bajas de reproducibilidad en disciplinas que dependen de experimentos computacionales:

\begin{itemize}
    \item Una encuesta de 2016 publicada en \textit{Nature} reveló que más del 70\% de los investigadores habían intentado sin éxito reproducir los experimentos de otros colegas, y más del 50\% no lograron reproducir sus propios experimentos previos después de meses o años.
    
    \item En el ámbito de la investigación de operaciones y optimización combinatoria (incluyendo problemas de ruteo vehicular), trabajos que reportan resultados de algoritmos heurísticos o metaheurísticos frecuentemente no proporcionan el código fuente, especificaciones detalladas del entorno de ejecución, o semillas aleatorias, haciendo imposible la verificación independiente de los resultados.
    
    \item La comparación de algoritmos de optimización para problemas DVRP (Dynamic Vehicle Routing Problems) se ve frecuentemente dificultada por la falta de \textit{benchmarks} estandarizados ejecutables y de pipelines de evaluación compartidos.
\end{itemize}

Las causas principales de la no-reproducibilidad en experimentos computacionales incluyen:

\paragraph{Dependencias de software no documentadas}

Los algoritmos de optimización y simulación dependen de múltiples bibliotecas externas, compiladores, intérpretes, y sistemas operativos. Diferencias en las versiones de estas dependencias (por ejemplo, Python 3.8 vs. 3.12, NumPy 1.18 vs. 2.0, sistemas de optimización como CPLEX vs. Gurobi) pueden generar resultados numéricos diferentes debido a cambios en la implementación de algoritmos internos, precisión aritmética, o comportamiento de generadores de números pseudoaleatorios.

\paragraph{Configuración del entorno de ejecución}

Factores como la arquitectura del procesador (x86 vs. ARM), el sistema operativo (Linux vs. Windows vs. macOS), variables de entorno (e.g., \texttt{PYTHONHASHSEED}, \texttt{OMP\_NUM\_THREADS}), y configuraciones del compilador pueden afectar el comportamiento de programas computacionales, especialmente en algoritmos que dependen de operaciones de punto flotante o paralelización.

\paragraph{Falta de acceso a datos y código}

Aunque un porcentaje creciente de publicaciones en optimización incluye referencias a repositorios de código (GitHub, Zenodo), muchos trabajos aún no publican el código fuente completo o los datos de entrada necesarios para reproducir los experimentos. Incluso cuando se publica el código, la ausencia de documentación clara sobre cómo compilarlo, configurarlo, y ejecutarlo limita severamente su utilidad para la comunidad científica.

\paragraph{Servicios externos no controlados}

En el contexto del MDRP y otros problemas de ruteo en redes viales reales, muchos trabajos dependen de APIs de ruteo comerciales (Google Maps API, Mapbox Routing API) que actúan como \textit{cajas negras}. Estas APIs no documentan públicamente los algoritmos internos que utilizan, pueden cambiar su comportamiento sin notificación previa, imponen límites de consultas, y requieren credenciales de acceso que no son compartibles. Esta dependencia hace imposible reproducir exactamente los resultados del estudio años después, ya que la API puede haber cambiado o dejado de estar disponible.

La falta de reproducibilidad no solo compromete la validez científica de los resultados individuales, sino que también dificulta el avance acumulativo del conocimiento en la disciplina: si los resultados de un algoritmo de referencia no pueden ser verificados, ¿cómo puede un nuevo algoritmo demostrar de manera rigurosa que constituye una mejora? Esta problemática ha motivado un movimiento creciente hacia la \textbf{ciencia abierta} y el desarrollo de infraestructuras tecnológicas que faciliten la reproducibilidad.

%======================================
% Subsección: Virtualización vs. Containerización
%======================================
\subsection{Virtualización vs. Containerización: Una Distinción Conceptual}

Para abordar los problemas de reproducibilidad relacionados con la configuración del entorno de ejecución, se han desarrollado dos paradigmas tecnológicos principales: \textbf{virtualización} y \textbf{containerización}. Aunque ambos permiten aislar aplicaciones de las particularidades del sistema operativo host, difieren fundamentalmente en su arquitectura y eficiencia.

\paragraph{Virtualización Completa}

La virtualización completa (implementada mediante \textit{hypervisors} como VirtualBox, VMware, Hyper-V) crea \textbf{máquinas virtuales} (VMs) que emulan completamente un sistema computacional, incluyendo hardware virtualizado (CPU, memoria, disco, red) y un sistema operativo completo (guest OS). Cada VM ejecuta su propio kernel del sistema operativo, independiente del sistema operativo host.

\textbf{Ventajas:}
\begin{itemize}
    \item Aislamiento total: cada VM es completamente independiente y puede ejecutar un sistema operativo diferente (e.g., Linux en un host Windows).
    \item Compatibilidad: permite ejecutar aplicaciones diseñadas para sistemas operativos específicos sin modificación.
\end{itemize}

\textbf{Desventajas:}
\begin{itemize}
    \item \textbf{Sobrecarga de recursos:} Cada VM requiere asignar memoria RAM, espacio en disco, y procesamiento para ejecutar un sistema operativo completo, resultando en un consumo significativo de recursos (típicamente varios GB de RAM y decenas de GB de disco por VM).
    
    \item \textbf{Tiempo de inicio lento:} Iniciar una VM requiere arrancar todo el sistema operativo guest, lo que puede tomar minutos.
    
    \item \textbf{Portabilidad limitada:} Las imágenes de VMs son archivos de gran tamaño (varios GB) que dificultan su distribución a través de redes o repositorios de código.
\end{itemize}

Estas limitaciones hacen que la virtualización completa sea poco práctica para escenarios donde se requiere ejecutar múltiples entornos aislados de manera eficiente, o distribuir entornos reproducibles de forma ágil.

\paragraph{Containerización (Contenedores)}

La containerización, en contraste, implementa \textbf{aislamiento a nivel de proceso} sin virtualizar el hardware o ejecutar múltiples kernels del sistema operativo. Los contenedores comparten el kernel del sistema operativo host, pero cada contenedor tiene su propio sistema de archivos aislado, espacio de nombres de procesos, y configuraciones de red.

\textbf{Arquitectura:} Los contenedores utilizan características del kernel de Linux (namespaces, cgroups, Union File Systems) para crear entornos aislados que parecen ser sistemas completos desde la perspectiva de la aplicación, pero que en realidad comparten el kernel subyacente.

\textbf{Ventajas:}
\begin{itemize}
    \item \textbf{Ligereza:} Los contenedores no incluyen un sistema operativo completo, solo las bibliotecas y dependencias necesarias para la aplicación. Un contenedor típico pesa decenas o cientos de MB, en lugar de varios GB.
    
    \item \textbf{Tiempo de inicio rápido:} Un contenedor puede iniciarse en milisegundos o segundos, ya que no requiere arrancar un sistema operativo completo.
    
    \item \textbf{Portabilidad:} Las imágenes de contenedores son fácilmente distribuibles a través de registros públicos (e.g., Docker Hub) y garantizan que la aplicación se ejecutará de manera idéntica en cualquier sistema que soporte el runtime de contenedores.
    
    \item \textbf{Eficiencia de recursos:} Al compartir el kernel del host, es posible ejecutar decenas o cientos de contenedores simultáneamente en un solo servidor con sobrecarga mínima.
\end{itemize}

\textbf{Limitaciones:}
\begin{itemize}
    \item Los contenedores deben ejecutarse sobre un kernel compatible (típicamente Linux). En sistemas Windows o macOS, Docker utiliza una VM ligera interna para ejecutar el kernel de Linux, añadiendo una capa de abstracción.
    
    \item El aislamiento no es tan completo como en VMs: todos los contenedores comparten el mismo kernel, lo que podría representar riesgos de seguridad en entornos multi-tenant.
\end{itemize}

Para el propósito de la reproducibilidad científica, la containerización ofrece una solución práctica y eficiente: permite empaquetar una aplicación junto con todas sus dependencias exactas (versiones de Python, bibliotecas, configuraciones) en una imagen inmutable que puede ser compartida, ejecutada, y verificada de manera idéntica en diferentes sistemas computacionales.

% Subsección: El Modelo de Docker
%======================================
\subsection{El Modelo de Docker: Imágenes, Contenedores y Capas}

\textbf{Docker}, introducido en 2013 y formalizado por \citet{Merkel2014}, es la plataforma de containerización más ampliamente adoptada en la industria y la investigación científica. Docker proporciona un conjunto de herramientas y abstracciones que simplifican la creación, distribución, y ejecución de contenedores.

El modelo conceptual de Docker se basa en tres elementos fundamentales:

\paragraph{Imágenes (Images)}

Una \textbf{imagen de Docker} es una plantilla de solo lectura que contiene el sistema de archivos completo de un contenedor: el código de la aplicación, las bibliotecas del sistema, las herramientas de línea de comandos, y las configuraciones necesarias. Las imágenes se construyen a partir de un archivo de especificación llamado \texttt{Dockerfile}, que define paso a paso cómo construir el entorno.

Ejemplo simplificado de \texttt{Dockerfile} para un entorno de simulación MDRP:

\begin{verbatim}
FROM python:3.10-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY src/ ./src/
COPY data/ ./data/
CMD ["python", "src/main.py"]
\end{verbatim}

Este \texttt{Dockerfile} especifica: (1) partir de una imagen base oficial de Python 3.10, (2) instalar dependencias desde \texttt{requirements.txt}, (3) copiar el código fuente y datos, (4) definir el comando de ejecución. El resultado es una imagen que contiene exactamente las versiones de Python y bibliotecas especificadas, independientemente del sistema donde se construya o ejecute.

\paragraph{Contenedores (Containers)}

Un \textbf{contenedor} es una instancia en ejecución de una imagen. Cuando se inicia un contenedor a partir de una imagen, Docker crea un entorno aislado con su propio sistema de archivos (derivado de la imagen), procesos, y configuraciones de red. El contenedor ejecuta la aplicación especificada en la imagen y puede ser detenido, reiniciado, o destruido sin afectar la imagen original o el sistema host.

La inmutabilidad de las imágenes garantiza que cada ejecución del contenedor parte del mismo estado inicial, facilitando la reproducibilidad.

\paragraph{Capas (Layers) y Union File System}

Las imágenes de Docker se construyen mediante un sistema de \textbf{capas} (\textit{layers}). Cada instrucción en el \texttt{Dockerfile} (e.g., \texttt{RUN}, \texttt{COPY}) crea una nueva capa que representa los cambios incrementales al sistema de archivos. Las capas son inmutables y se apilan utilizando un \textit{Union File System}, permitiendo que múltiples imágenes compartan capas comunes.

\textbf{Implicación para la eficiencia:} Si dos imágenes utilizan la misma imagen base (e.g., \texttt{python:3.10-slim}), Docker almacena esa capa solo una vez en disco, reduciendo significativamente el espacio requerido y acelerando la descarga y construcción de imágenes.

\textbf{Implicación para la reproducibilidad:} Cada capa tiene un identificador hash criptográfico único basado en su contenido. Esto garantiza que una imagen construida con el mismo \texttt{Dockerfile} y las mismas dependencias producirá exactamente las mismas capas (y por tanto, el mismo hash de imagen final), permitiendo verificación de integridad.

\paragraph{Registros de Imágenes (Image Registries)}

Docker Hub y otros registros públicos permiten compartir imágenes de Docker. Un investigador puede publicar la imagen Docker de su experimento en Docker Hub, y cualquier otro investigador puede descargarla y ejecutarla con un simple comando:

\begin{verbatim}
docker pull usuario/mdrp-simulation:v1.0
docker run usuario/mdrp-simulation:v1.0
\end{verbatim}

Esto elimina la ambigüedad sobre configuraciones de entorno: la imagen contiene todo el entorno exacto utilizado en el estudio original.

% Subsección: Containerización en Investigación Reproducible
%======================================
\subsection{El Rol de la Containerización en la Investigación Reproducible}

La adopción de Docker en la investigación científica ha crecido exponencialmente en la última década, especialmente en campos computacionales como bioinformática, machine learning, y optimización. Las razones principales son:

\paragraph{Aislamiento de Dependencias}

Cada proyecto de investigación puede tener requisitos de software específicos y potencialmente conflictivos. Por ejemplo, un proyecto puede requerir Python 3.8 con NumPy 1.18, mientras que otro requiere Python 3.12 con NumPy 2.0. Sin containerización, instalar ambos entornos en el mismo sistema requiere gestión manual compleja de entornos virtuales, que puede fallar debido a dependencias del sistema operativo subyacente.

Docker resuelve este problema encapsulando cada entorno en un contenedor aislado. El investigador puede ejecutar simultáneamente múltiples experimentos con dependencias incompatibles sin conflictos.

\paragraph{Garantía de Resultados Idénticos}

La inmutabilidad de las imágenes Docker garantiza que el entorno de ejecución es exactamente el mismo en cada ejecución. Esto elimina una fuente principal de no-reproducibilidad: diferencias sutiles en versiones de bibliotecas, configuraciones del sistema, o comportamiento del compilador.

En el contexto del MDRP, donde el simulador depende de bibliotecas como \texttt{requests} (para comunicación con OSRM), \texttt{polyline} (para decodificación de geometrías), y \texttt{pandas} (para procesamiento de datos), Docker garantiza que todos los investigadores ejecutan el experimento con las mismas versiones exactas de estas dependencias.

\paragraph{Facilidad de Distribución y Verificación}

Compartir un entorno reproducible sin Docker requeriría documentar manualmente todas las dependencias, configuraciones, y pasos de instalación, con alto riesgo de omisiones o ambigüedades. Con Docker, el entorno completo se distribuye como una imagen autocontenida que puede ser ejecutada con un solo comando.

Esto facilita no solo la reproducción por terceros, sino también la \textbf{verificación por revisores de publicaciones científicas}: un revisor puede ejecutar los experimentos del artículo en su propia computadora sin necesidad de instalar manualmente decenas de dependencias.

\paragraph{Integración con Pipelines de CI/CD}

Los contenedores Docker se integran naturalmente con sistemas de integración continua (Continuous Integration, CI) y despliegue continuo (Continuous Deployment, CD), permitiendo que los experimentos se ejecuten automáticamente cada vez que se modifica el código, garantizando que los resultados permanecen reproducibles a lo largo del desarrollo del proyecto.

\subsection{Implementación de Docker en el Pipeline MDRP}

En el presente trabajo, Docker se emplea para encapsular dos componentes críticos del pipeline de simulación:

\paragraph{Servidor OSRM}

El servidor de ruteo OSRM (versión 5.26.0) se ejecuta en un contenedor Docker oficial (\texttt{osrm/osrm-backend}). Esto garantiza que:

\begin{itemize}
    \item La versión exacta del algoritmo de Contraction Hierarchies utilizada es la misma en todas las ejecuciones.
    \item El preprocesamiento de la red vial de La Paz (archivo \texttt{map.osm}) genera estructuras de datos idénticas.
    \item Las consultas de ruteo producen resultados deterministas (para los mismos pares origen-destino, se obtienen las mismas rutas y tiempos de viaje).
\end{itemize}

El contenedor se inicia mediante el comando:

\begin{verbatim}
docker run -d -p 5000:5000 -v ./osrm_data:/data \
  osrm/osrm-backend osrm-routed --algorithm mld /data/map.osrm
\end{verbatim}

Este comando monta el directorio \texttt{osrm\_data} (que contiene los archivos preprocesados \texttt{.osrm}) en el contenedor y expone el servidor en el puerto 5000 del host.

\paragraph{Entorno de Simulación (Futuro)}

Aunque en la versión actual del proyecto el simulador Python se ejecuta directamente en el sistema host, una extensión natural del trabajo (recomendada para publicación) sería containerizar también el simulador, creando una imagen Docker que incluya Python 3.10, todas las dependencias listadas en \texttt{requirements.txt}, el código fuente del simulador, y los datos de entrada. Esto permitiría ejecutar el pipeline completo con un solo comando \texttt{docker run}, garantizando reproducibilidad absoluta.

En resumen, la adopción de Docker como infraestructura de containerización constituye una contribución metodológica relevante del presente trabajo: mientras que trabajos previos en MDRP (incluyendo \citealt{Reyes2018}) no proporcionan mecanismos para reproducir sus experimentos de manera automatizada, el pipeline desarrollado en esta tesis puede ser ejecutado por cualquier investigador con acceso a Docker, contribuyendo al avance hacia la ciencia abierta y reproducible en el campo de la optimización de ruteo dinámico.


\chapter{Metodología}

\section{Arquitectura del sistema de simulación}

El pipeline de simulación del MDRP desarrollado en este trabajo adopta una arquitectura modular de tres capas que separa las responsabilidades de ruteo, lógica de negocio, y persistencia de resultados. Esta sección documenta la estructura técnica del sistema, las interfaces de comunicación entre componentes, y el modelo de eventos discretos que gobierna la evolución temporal del sistema.

\subsection{Componentes: simulador, OSRM, orquestación Docker}

La arquitectura del sistema se compone de tres componentes principales orquestados mediante contenedores Docker para garantizar reproducibilidad:

\paragraph{Motor de simulación (Python 3.12)}

El núcleo del sistema es un simulador de eventos discretos implementado en Python 3.12, estructurado en los siguientes módulos principales (ubicados en \texttt{src/}):

\begin{itemize}
	\item \textbf{\texttt{main.py}:} Contiene el bucle principal de simulación (\texttt{run\_simulation()}) y las clases de dominio \texttt{Order}, \texttt{Courier}, y \texttt{Restaurant}. Este módulo coordina el avance temporal del sistema, procesando eventos secuencialmente desde \texttt{start\_time} hasta \texttt{simulation\_end}. La función \texttt{run\_simulation()} recibe como entrada las órdenes sintéticas, la flota de couriers, el catálogo de restaurantes, y parámetros de configuración, retornando métricas de desempeño al finalizar.
	
	\item \textbf{\texttt{config.py}:} Define constantes de configuración del sistema que parametrizan el comportamiento del Rolling Horizon. Los parámetros clave incluyen:
	\begin{itemize}
		\item \texttt{OPTIMIZATION\_FREQUENCY = timedelta(minutes=5)}: Frecuencia de reoptimización ($f = 5$ min)
		\item \texttt{ASSIGNMENT\_HORIZON = timedelta(minutes=20)}: Horizonte de asignación ($\Delta_u = 20$ min)
		\item \texttt{DELTA\_1 = timedelta(minutes=20)}: Lookahead para cálculo de $Z_t$
		\item \texttt{MAX\_BUNDLE\_SIZE = 6}: Capacidad máxima de couriers
		\item \texttt{PICKUP\_DELAY\_THETA = 0.1}: Penalización por retraso en pickup ($\theta$)
	\end{itemize}
	
	\item \textbf{\texttt{bundling.py}:} Implementa la heurística de generación de bundles mediante inserción paralela, siguiendo el Procedimiento 1 de \citet{Reyes2018}. La función \texttt{generate\_bundles\_for\_restaurant()} agrupa órdenes del mismo restaurante que son temporalmente compatibles (diferencia de tiempos de preparación $< 10$ min) y geográficamente factibles (SLA no violado por detours adicionales).
	
	\item \textbf{\texttt{asignaciontentativa.py}:} Resuelve el problema de matching bipartito bundle-courier mediante el algoritmo húngaro (Hungarian algorithm), maximizando los pesos $w_{bc}$ definidos en la ecuación correspondiente del Marco Teórico. También implementa la lógica FCFS mediante \texttt{assign\_order\_to\_nearest\_courier()}.
	
	\item \textbf{\texttt{synth\_loader.py}:} Carga instancias sintéticas desde archivos CSV generados por \texttt{scripts/make\_synth\_orders.py}. Implementa el dimensionamiento automático de flota mediante la fórmula:
	\begin{equation}
	n_{\text{couriers}} = \max\left(\texttt{min\_couriers}, \left\lceil \frac{\text{total\_orders}}{\texttt{orders\_per\_courier}} \right\rceil\right)
	\end{equation}
	donde \texttt{orders\_per\_courier} = 18 (calibrado a patrones LaDe).
\end{itemize}

El simulador se ejecuta directamente sobre el sistema operativo host (Windows/Linux/macOS) sin containerización, permitiendo iteración rápida durante desarrollo. La selección de política de despacho se controla mediante la variable de entorno \texttt{FCFS\_POLICY}: si \texttt{FCFS\_POLICY=1}, el sistema ejecuta FCFS; de lo contrario, ejecuta Rolling Horizon.

\paragraph{Servidor de ruteo OSRM (v5.26.0)}

El componente de ruteo se implementa mediante un servidor OSRM ejecutándose en un contenedor Docker oficial (\texttt{osrm/osrm-backend:5.26.0}). OSRM proporciona capacidades de cálculo de rutas óptimas sobre la red vial real de La Paz extraída de OpenStreetMap, utilizando el algoritmo de Contraction Hierarchies preprocesado sobre el archivo \texttt{data/map.osm}.

El contenedor OSRM se inicia mediante el siguiente comando Docker:

\begin{verbatim}
docker run -d -p 5000:5000 \
  -v $(pwd)/osrm_data:/data \
  osrm/osrm-backend:5.26.0 \
  osrm-routed --algorithm mld /data/map.osrm
\end{verbatim}

Este comando realiza las siguientes operaciones:
\begin{itemize}
	\item \texttt{-d}: Ejecuta el contenedor en modo background (daemon)
	\item \texttt{-p 5000:5000}: Expone el puerto 5000 del contenedor en el host
	\item \texttt{-v \$(pwd)/osrm\_data:/data}: Monta el directorio local \texttt{osrm\_data/} (que contiene archivos \texttt{.osrm} preprocesados) en \texttt{/data} dentro del contenedor
	\item \texttt{osrm-routed --algorithm mld}: Inicia el servidor de ruteo usando el algoritmo MLD (Multi-Level Dijkstra, variante de Contraction Hierarchies)
\end{itemize}

El servidor OSRM responde a consultas HTTP en \texttt{http://localhost:5000}, proporcionando tiempos de respuesta típicos de 1-2 milisegundos para consultas punto-a-punto en la red de La Paz. Esta latencia baja es crítica para la viabilidad computacional del Rolling Horizon, que puede requerir cientos de consultas de ruteo por época de optimización.

\paragraph{Orquestación y flujo de datos}

La comunicación entre el simulador Python y el servidor OSRM se realiza mediante el protocolo HTTP/REST, sin necesidad de orquestación Docker Compose (cada componente se inicia independientemente). El flujo de datos en cada época de simulación sigue el siguiente patrón:

\begin{enumerate}
	\item \textbf{Generación de evento:} El bucle de simulación identifica que una orden alcanzó su tiempo de preparación (\texttt{ready\_time}), o que llegó una nueva época de optimización.
	
	\item \textbf{Decisión de política:} Según la variable \texttt{FCFS\_POLICY}, el sistema ejecuta:
	\begin{itemize}
		\item \textbf{FCFS:} Llama \texttt{assign\_order\_to\_nearest\_courier()}, que consulta OSRM para calcular distancias courier-restaurante y asigna la orden al courier disponible más cercano.
		\item \textbf{Rolling Horizon:} Llama \texttt{generate\_bundles\_for\_restaurant()} para agrupar órdenes, luego \texttt{assign\_bundles\_to\_couriers()} que resuelve el matching bipartito consultando OSRM para calcular costos de rutas consolidadas.
	\end{itemize}
	
	\item \textbf{Consultas de ruteo:} El módulo \texttt{getrouteOSMR.py} realiza llamadas HTTP GET al endpoint \texttt{/route/v1/driving/} de OSRM, recibiendo respuestas JSON con distancias, duraciones, y geometrías de rutas.
	
	\item \textbf{Actualización de estado:} El simulador actualiza el estado de órdenes (pending $\to$ assigned $\to$ picked\_up $\to$ delivered) y couriers (available $\to$ on\_route $\to$ available), avanzando el reloj de simulación al siguiente evento.
	
	\item \textbf{Registro de métricas:} Al completar cada entrega, se registran Click-to-Door time, Ready-to-Pickup time, y Pickup-to-Door time en estructuras de datos que se exportarán a CSV al finalizar la simulación.
\end{enumerate}

Esta arquitectura de acoplamiento débil (loose coupling) mediante HTTP permite que OSRM sea reemplazado por otros backends de ruteo sin modificar el código del simulador, facilitando extensiones futuras como integración de datos de tráfico en tiempo real o perfiles vehiculares heterogéneos.

\subsection{Interfaces: API OSRM, formatos de intercambio}

La comunicación entre el simulador y el servidor OSRM se realiza mediante una API REST estandarizada que sigue la especificación OSRM HTTP API v1. Esta subsección documenta los endpoints utilizados, formatos de datos intercambiados, y mecanismos de tolerancia a fallos implementados.

\paragraph{Endpoint de ruteo point-to-point}

El endpoint principal utilizado es \texttt{/route/v1/driving/}, que calcula la ruta óptima entre una secuencia de coordenadas geográficas. La sintaxis general de la consulta es:

\begin{verbatim}
GET http://localhost:5000/route/v1/driving/{coordinates}
    ?overview=full&geometries=polyline
\end{verbatim}

donde \texttt{\{coordinates\}} es una lista de pares \texttt{lon,lat} separados por punto y coma. Por ejemplo, para calcular la ruta desde el courier en $(-110.3133, 24.1426)$ hacia un restaurante en $(-110.3089, 24.1501)$ y luego al cliente en $(-110.3201, 24.1389)$:

\begin{verbatim}
GET http://localhost:5000/route/v1/driving/
    -110.3133,24.1426;-110.3089,24.1501;-110.3201,24.1389
    ?overview=full&geometries=polyline
\end{verbatim}

Los parámetros de consulta incluyen:
\begin{itemize}
	\item \texttt{overview=full}: Retorna la geometría completa de la ruta (todas las coordenadas intermedias), necesaria para visualización en mapas interactivos.
	\item \texttt{geometries=polyline}: Codifica la geometría en formato Polyline (algoritmo de compresión de Google), reduciendo el tamaño de la respuesta.
\end{itemize}

\paragraph{Formato de respuesta JSON}

OSRM retorna un objeto JSON con la siguiente estructura (simplificada para claridad):

\begin{verbatim}
{
  "code": "Ok",
  "routes": [{
    "distance": 3245.7,        // Distancia total en metros
    "duration": 487.3,         // Duración total en segundos
    "geometry": "u_iiApq...",  // Polyline codificado
    "legs": [
      {
        "distance": 1523.4,
        "duration": 215.2,
        "steps": [
          {
            "distance": 234.1,
            "duration": 32.5,
            "geometry": "...",
            "maneuver": {
              "location": [-110.3089, 24.1501],
              "type": "depart"
            }
          },
          // ... más steps
        ]
      },
      {
        "distance": 1722.3,
        "duration": 272.1,
        "steps": [...]
      }
    ]
  }],
  "waypoints": [
    {"location": [-110.3133, 24.1426], "name": "..."},
    {"location": [-110.3089, 24.1501], "name": "..."},
    {"location": [-110.3201, 24.1389], "name": "..."}
  ]
}
\end{verbatim}

El simulador extrae los siguientes campos clave:
\begin{itemize}
	\item \texttt{routes[0].distance}: Distancia total de la ruta en metros, utilizada para calcular métricas de eficiencia operacional (distancia total recorrida por la flota).
	\item \texttt{routes[0].duration}: Duración total de la ruta en segundos, convertida a minutos para calcular tiempos de viaje en la simulación.
	\item \texttt{routes[0].geometry}: Geometría Polyline que se decodifica mediante la biblioteca \texttt{polyline} para generar visualizaciones en mapas Folium.
	\item \texttt{routes[0].legs}: Segmentos de la ruta (courier $\to$ restaurante, restaurante $\to$ cliente), utilizados para estimar tiempos de pickup y delivery individuales.
\end{itemize}

\paragraph{Cliente HTTP con tolerancia a fallos}

El módulo \texttt{getrouteOSMR.py} implementa un cliente HTTP robusto utilizando la biblioteca \texttt{requests} con reintentos automáticos y backoff exponencial. La configuración de reintentos se define mediante:

\begin{verbatim}
retries = Retry(
    total=int(os.environ.get('OSRM_MAX_RETRIES', '5')),
    backoff_factor=float(os.environ.get('OSRM_BACKOFF_FACTOR', '1.0')),
    status_forcelist=[429, 500, 502, 503, 504],
    allowed_methods=["GET", "POST"]
)
\end{verbatim}

Esta configuración garantiza que:
\begin{itemize}
	\item Hasta 5 reintentos se ejecutan ante errores HTTP 429 (Too Many Requests), 500 (Internal Server Error), 502-504 (Gateway errors).
	\item El backoff exponencial con factor 1.0 introduce esperas de $1^k$ segundos entre reintentos ($k$ = número de reintento), reduciendo la carga en el servidor OSRM.
	\item Solo métodos GET y POST son reintentados, evitando reintentos en operaciones no idempotentes.
\end{itemize}

\paragraph{Cache en memoria para consultas repetidas}

Para reducir la latencia de consultas recurrentes (e.g., múltiples couriers asignados al mismo restaurante), \texttt{getrouteOSMR.py} implementa un diccionario de cache en memoria:

\begin{verbatim}
_osrm_cache = {}

def get_route_details(start_coords, waypoints):
    cache_key = (start_coords,) + tuple(waypoints)
    if cache_key in _osrm_cache:
        return _osrm_cache[cache_key]
    
    # ... consulta HTTP a OSRM ...
    
    _osrm_cache[cache_key] = result
    return result
\end{verbatim}

Este cache es crucial para el desempeño del Rolling Horizon: en cada época de optimización, el algoritmo de bundling puede generar múltiples bundles con el mismo restaurante origen, evitando consultas HTTP redundantes. Empíricamente, el cache logra tasas de acierto (hit rate) del orden de 30-40\% en escenarios con 142 restaurantes y 1,038 órdenes.

\paragraph{Modo de fallback euclidiano}

Para propósitos de prueba y debugging, el sistema soporta un modo de fallback que reemplaza consultas OSRM por cálculos de distancia Haversine (gran círculo) y velocidad constante. Este modo se activa mediante la variable de entorno \texttt{USE\_EUCLIDEAN=1}:

\begin{verbatim}
if os.environ.get('USE_EUCLIDEAN') == '1':
    speed = float(os.environ.get("METERS_PER_MINUTE", 320))
    distance = haversine_distance(start_coords, end_coords)
    duration_sec = (distance / speed) * 60.0
    return {"distance": distance, "duration": duration_sec}
\end{verbatim}

Este modo es útil para validar la lógica del simulador independientemente de OSRM, aunque no se utiliza en experimentos finales debido a la pérdida de realismo en los tiempos de viaje.

\subsection{Modelo de eventos discretos}

El motor de simulación implementa un paradigma de \textbf{simulación de eventos discretos} (Discrete Event Simulation, DES), donde el estado del sistema evoluciona únicamente en instantes discretos de tiempo correspondientes a eventos significativos (llegada de orden, orden lista, courier disponible). A diferencia de simulaciones de tiempo continuo que avanzan en pasos de tiempo fijos, DES permite saltar directamente entre eventos, mejorando eficiencia computacional y precisión temporal.

\paragraph{Tipos de eventos del sistema}

El simulador reconoce seis tipos de eventos principales que modifican el estado del sistema:

\begin{enumerate}
	\item \textbf{OrderPlaced} (\texttt{placement\_time}): Una nueva orden ingresa al sistema. El evento registra el momento en que el cliente coloca la orden en la plataforma. La orden se inserta en la cola \texttt{order\_queue} ordenada por tiempo de colocación.
	
	\item \textbf{OrderReady} (\texttt{ready\_time = placement\_time + prep\_time}): El restaurante completa la preparación de la comida y notifica que la orden está lista para pickup. Este evento marca la elegibilidad de la orden para asignación bajo FCFS, o su inclusión en el conjunto $\mathcal{U}_t$ para Rolling Horizon.
	
	\item \textbf{CourierAvailable}: Un courier completa la entrega de órdenes de su ruta actual y queda disponible para nueva asignación. Este evento actualiza \texttt{courier.location} a la ubicación de la última entrega y libera capacidad del courier.
	
	\item \textbf{OptimizationEpoch}: Evento periódico que se dispara cada \texttt{OPTIMIZATION\_FREQUENCY} minutos (5 min) bajo Rolling Horizon. Desencadena la ejecución del ciclo de bundling, matching, y commitment descrito en el Marco Teórico.
	
	\item \textbf{PickupCompleted}: El courier arriba al restaurante y recoge la orden. Este evento actualiza \texttt{order.status = "picked\_up"} y registra \texttt{order.pickup\_time} para cálculo de métricas Ready-to-Pickup.
	
	\item \textbf{DeliveryCompleted}: El courier entrega la orden al cliente. Este evento actualiza \texttt{order.status = "delivered"}, registra \texttt{order.delivery\_time}, y calcula métricas Click-to-Door. La orden se mueve a la lista \texttt{delivered\_orders}.
\end{enumerate}

\paragraph{Cola de eventos y avance temporal}

El bucle principal de simulación mantiene una cola de eventos futuros implementada mediante una \texttt{deque} de Python, ordenada por tiempo de ocurrencia:

\begin{verbatim}
order_queue = deque(sorted(orders, key=lambda o: o.placement_time))
current_time = start_time  # datetime(2025, 1, 1, 11, 0)

while current_time < simulation_end:
    # Procesar todos los eventos que ocurren en current_time
    ready_orders = [o for o in order_queue 
                    if o.ready_time <= current_time 
                    and o.status == "pending"]
    
    # Ejecutar política de despacho
    if use_fcfs:
        for order in ready_orders:
            assign_order_to_nearest_courier(order, active_couriers)
    else:  # Rolling Horizon
        if is_optimization_epoch(current_time):
            bundles = generate_bundles(ready_orders, current_time)
            assign_bundles_to_couriers(bundles, active_couriers)
    
    # Avanzar al siguiente evento
    current_time = next_event_time(order_queue, active_couriers)
\end{verbatim}

El mecanismo \texttt{next\_event\_time()} calcula el tiempo del próximo evento inspeccionando:
\begin{itemize}
	\item Tiempos de colocación de órdenes futuras en \texttt{order\_queue}
	\item Tiempos estimados de finalización de rutas de couriers activos
	\item Próxima época de optimización (si Rolling Horizon)
\end{itemize}

Este enfoque de "salto entre eventos" evita iteraciones innecesarias en periodos sin actividad (e.g., durante la madrugada cuando no hay órdenes), mejorando la eficiencia computacional.

\paragraph{Estado del sistema y estructuras de datos}

El estado global del sistema en cualquier instante $t$ se representa mediante tres estructuras de datos principales:

\begin{enumerate}
	\item \textbf{\texttt{order\_queue}}: Cola de órdenes pendientes, cada una con atributos:
	\begin{verbatim}
	class Order:
	    restaurant: Restaurant      # Origen (lat, lon)
	    placement_time: datetime    # Tiempo de colocación
	    ready_time: datetime        # placement_time + prep_time
	    dropoff_loc: (lat, lon)     # Destino del cliente
	    status: str                 # "pending", "assigned", 
	                                # "picked_up", "delivered"
	    pickup_time: datetime       # Tiempo de pickup
	    delivery_time: datetime     # Tiempo de delivery
	    courier_id: int             # ID del courier asignado
	    bundle_size: int            # Tamaño del bundle
	\end{verbatim}
	
	\item \textbf{\texttt{active\_couriers}}: Lista de couriers activos durante el tiempo $t$:
	\begin{verbatim}
	class Courier:
	    id: int
	    on_time: datetime           # Inicio de turno
	    off_time: datetime          # Fin de turno
	    location: (lat, lon)        # Ubicación actual
	    current_route: Route        # Ruta activa (None si disponible)
	    orders_delivered: int       # Contador de entregas
	    total_distance: float       # Distancia acumulada (metros)
	    driving_time: float         # Tiempo conduciendo (minutos)
	\end{verbatim}
	
	\item \textbf{\texttt{delivered\_orders}}: Lista de órdenes completadas, utilizada para cálculo de métricas agregadas al finalizar la simulación.
\end{enumerate}

\paragraph{Invariantes del sistema}

El simulador garantiza los siguientes invariantes en todo momento:
\begin{itemize}
	\item \textbf{Conservación de órdenes:} $|\texttt{order\_queue}| + |\texttt{assigned\_orders}| + |\texttt{delivered\_orders}| = n_{\text{total}}$
	\item \textbf{Precedencia temporal:} Para toda orden $o$: \texttt{placement\_time} $\leq$ \texttt{ready\_time} $\leq$ \texttt{pickup\_time} $\leq$ \texttt{delivery\_time}
	\item \textbf{Capacidad de couriers:} En todo instante $t$, ningún courier posee más de \texttt{MAX\_BUNDLE\_SIZE} órdenes simultáneamente recogidas pero no entregadas
	\item \textbf{Asignación única:} Cada orden está asignada a exactamente un courier (ninguna orden asignada a múltiples couriers o sin asignar tras su \texttt{ready\_time})
\end{itemize}

Estos invariantes se verifican mediante aserciones (\texttt{assert}) en puntos críticos del código durante la fase de desarrollo, y se desactivan en ejecuciones de producción para maximizar desempeño.

\section{Preparación de la infraestructura de ruteo}

La infraestructura de ruteo constituye el componente más crítico del pipeline experimental, dado que todos los cálculos de distancias, tiempos de viaje, y rutas utilizados por las políticas de despacho dependen de la precisión y disponibilidad del servidor OSRM. Esta sección documenta el proceso completo de preparación de la red vial: desde la descarga de datos OpenStreetMap, pasando por el preprocesamiento algorítmico necesario para habilitar consultas rápidas de Contraction Hierarchies, hasta la validación de cobertura geográfica que garantiza que todos los puntos de interés (restaurantes, ubicaciones de clientes) son alcanzables en la red.

\subsection{Descarga y filtrado de red OSM de La Paz}

OpenStreetMap (OSM) es una plataforma colaborativa de cartografía digital que proporciona datos geoespaciales de libre acceso para prácticamente cualquier región del mundo. Los datos OSM incluyen no solo la geometría de calles y carreteras, sino también metadatos ricos sobre tipo de vía (autopista, avenida, calle residencial), límites de velocidad, restricciones de giro, sentidos únicos, y características de superficie (pavimentada, terracería). Esta riqueza de información permite que OSRM calcule rutas realistas que respetan las restricciones físicas y regulatorias de la red vial urbana.

\paragraph{Definición del área de interés}

El primer paso del proceso consiste en definir un \textbf{bounding box} (caja delimitadora) que cubra completamente la zona urbana de La Paz, Baja California Sur. Esta área se especifica mediante coordenadas geográficas que delimitan el rectángulo:

\begin{equation}
\text{Bounding Box} = [\lambda_{\text{min}}, \phi_{\text{min}}, \lambda_{\text{max}}, \phi_{\text{max}}]
\end{equation}

donde:
\begin{itemize}
	\item $\lambda_{\text{min}}, \lambda_{\text{max}}$: Longitudes mínima y máxima (oeste-este)
	\item $\phi_{\text{min}}, \phi_{\text{max}}$: Latitudes mínima y máxima (sur-norte)
\end{itemize}

Para La Paz, el bounding box se define como:
\begin{verbatim}
Bounding Box: [-110.335, 24.100, -110.290, 24.160]
\end{verbatim}

Estas coordenadas abarcan aproximadamente 5 km (este-oeste) × 7 km (norte-sur), cubriendo la zona urbana densa de La Paz desde el malecón costero hasta los desarrollos residenciales al norte de la ciudad, excluyendo áreas rurales periféricas con baja densidad poblacional.

\paragraph{Descarga desde Geofabrik}

Los datos OSM del estado completo de Baja California Sur se descargan desde \textbf{Geofabrik} (\url{https://download.geofabrik.de/}), un servicio que proporciona extractos regionales actualizados diariamente del planeta OSM en formato \texttt{.osm.pbf} (Protocolbuffer Binary Format), que es altamente comprimido y eficiente para procesamiento.

El archivo descargado (\texttt{baja-california-sur-latest.osm.pbf}) contiene toda la información cartográfica del estado, incluyendo no solo vías vehiculares sino también senderos peatonales, límites administrativos, cuerpos de agua, edificios, y puntos de interés. El tamaño típico del archivo para Baja California Sur es de aproximadamente 15-20 MB (comprimido).

Alternativamente, para áreas urbanas pequeñas como La Paz, es posible realizar una descarga más específica mediante la \textbf{Overpass API}, que permite consultas geoespaciales directas con filtros personalizados. Un ejemplo de consulta Overpass para extraer únicamente vías vehiculares dentro del bounding box sería:

\begin{verbatim}
[bbox:24.100,-110.335,24.160,-110.290];
way["highway"~"motorway|trunk|primary|secondary|tertiary|
     residential|unclassified|service"];
out geom;
\end{verbatim}

Esta consulta retorna únicamente los segmentos viales relevantes para navegación vehicular, excluyendo senderos peatonales (\texttt{highway=footway}), ciclovías (\texttt{highway=cycleway}), y caminos privados no transitables.

\paragraph{Filtrado de características viales}

Una vez descargado el extracto OSM completo de Baja California Sur, se aplica un proceso de filtrado para retener únicamente las vías transitables por vehículos motorizados (motocicletas, automóviles). OSM clasifica las vías mediante la etiqueta \texttt{highway}, cuyas categorías principales incluyen:

\begin{itemize}
	\item \texttt{motorway}: Autopistas de alta velocidad (aunque no existen en La Paz urbana)
	\item \texttt{trunk}: Carreteras principales interurbanas
	\item \texttt{primary}: Avenidas principales dentro de la ciudad (e.g., Álvaro Obregón)
	\item \texttt{secondary}: Vías secundarias importantes (e.g., 5 de Febrero)
	\item \texttt{tertiary}: Calles terciarias de conexión entre barrios
	\item \texttt{residential}: Calles residenciales locales
	\item \texttt{unclassified}: Calles no clasificadas pero transitables
	\item \texttt{service}: Vías de servicio (accesos a estacionamientos, gasolineras)
\end{itemize}

El filtrado se realiza mediante la herramienta de línea de comandos \texttt{osmium} (parte del ecosistema OSM), que permite extraer subconjuntos de archivos \texttt{.osm.pbf} mediante expresiones de filtro:

\begin{verbatim}
osmium tags-filter baja-california-sur-latest.osm.pbf \
  w/highway=motorway,trunk,primary,secondary,tertiary,\
    residential,unclassified,service \
  -o lapaz_roads.osm.pbf
\end{verbatim}

Posteriormente, se aplica un recorte geográfico al bounding box de La Paz:

\begin{verbatim}
osmium extract -b -110.335,24.100,-110.290,24.160 \
  lapaz_roads.osm.pbf -o lapaz_filtered.osm
\end{verbatim}

El resultado es un archivo \texttt{lapaz\_filtered.osm} (formato XML sin comprimir, típicamente 5-10 MB) que contiene únicamente la red vial vehicular dentro del área urbana de interés.

\paragraph{Conversión a formato OSRM}

El archivo \texttt{.osm} filtrado se convierte al formato interno de OSRM mediante el pipeline de preprocesamiento descrito en la siguiente subsección. Este archivo constituye la entrada fundamental para todos los cálculos de ruteo en la simulación.

\subsection{Preprocesamiento en OSRM (extract/partition/customize)}

El servidor OSRM no puede operar directamente sobre archivos \texttt{.osm} en formato XML, ya que las consultas de camino más corto requieren estructuras de datos optimizadas (grafos de Contraction Hierarchies) que permitan respuestas en milisegundos. El preprocesamiento de OSRM transforma el archivo OSM en una representación jerárquica altamente eficiente mediante tres etapas secuenciales: \textbf{extract}, \textbf{partition}, y \textbf{customize}.

\paragraph{Etapa 1: Extract (extracción y construcción del grafo)}

La primera etapa parsea el archivo \texttt{.osm} y construye el grafo dirigido $G = (V, E, w)$ que representa la red vial. El comando utilizado es:

\begin{verbatim}
osrm-extract -p car.lua lapaz_filtered.osm
\end{verbatim}

Este comando ejecuta las siguientes operaciones:

\begin{enumerate}
	\item \textbf{Parseo del XML OSM:} Lee todos los nodos (intersecciones) y ways (segmentos de calle) del archivo \texttt{.osm}.
	
	\item \textbf{Aplicación del perfil vehicular:} El archivo \texttt{car.lua} es un script Lua que define las reglas de transitabilidad y velocidades por tipo de vía. Por ejemplo:
	\begin{verbatim}
	-- Velocidades por tipo de vía (km/h)
	speeds = {
	  motorway = 90,
	  trunk = 70,
	  primary = 50,
	  secondary = 40,
	  tertiary = 30,
	  residential = 25,
	  service = 20
	}
	\end{verbatim}
	
	Estas velocidades se ajustan para reflejar el comportamiento típico de couriers en motocicleta en La Paz (velocidades ligeramente superiores a automóviles en tráfico urbano debido a mayor maniobrabilidad).
	
	\item \textbf{Cálculo de pesos de arcos:} Para cada segmento vial con longitud $d$ (en metros) y tipo de vía asociado a velocidad $v$ (en km/h), el peso $w(u, v)$ se define como el tiempo de viaje esperado:
	\begin{equation}
	w(u, v) = \frac{d}{v / 3.6} \quad \text{(segundos)}
	\end{equation}
	
	\item \textbf{Construcción del grafo dirigido:} Se crean arcos dirigidos que respetan sentidos únicos (especificados en OSM mediante \texttt{oneway=yes}). En La Paz, varias calles del centro histórico son de sentido único, lo cual afecta significativamente las rutas óptimas.
	
	\item \textbf{Generación de archivos de salida:} La etapa \texttt{extract} produce los siguientes archivos:
	\begin{itemize}
		\item \texttt{lapaz\_filtered.osrm}: Grafo extraído en formato binario OSRM
		\item \texttt{lapaz\_filtered.osrm.names}: Nombres de calles (para instrucciones de navegación)
		\item \texttt{lapaz\_filtered.osrm.restrictions}: Restricciones de giro (prohibiciones de giro en U, giros obligatorios)
	\end{itemize}
\end{enumerate}

Esta etapa tiene complejidad $O(|E| + |V|)$ y típicamente requiere 5-10 segundos para la red de La Paz.

\paragraph{Etapa 2: Partition (particionamiento jerárquico)}

La segunda etapa implementa el algoritmo de Contraction Hierarchies descrito en la Sección 6.3 del Marco Teórico. El comando es:

\begin{verbatim}
osrm-partition lapaz_filtered.osrm
\end{verbatim}

Esta etapa realiza:

\begin{enumerate}
	\item \textbf{Cálculo del ordenamiento jerárquico de nodos:} Asigna un rango (nivel de importancia) a cada nodo del grafo mediante heurísticas que minimizan el número de atajos generados. Los nodos en intersecciones principales (e.g., Álvaro Obregón con 5 de Febrero) reciben rangos altos, mientras que nodos en calles residenciales reciben rangos bajos.
	
	\item \textbf{Contracción secuencial de nodos:} Procesa los nodos en orden ascendente de importancia, eliminándolos del grafo y creando atajos que preservan distancias más cortas. Para cada nodo $v$ eliminado, OSRM verifica todos los pares de vecinos $(u, w)$ y crea un atajo $(u, w)$ si el camino más corto de $u$ a $w$ pasaba por $v$.
	
	\item \textbf{Optimización del grafo aumentado:} El número de atajos creados determina el tamaño del grafo preprocesado y el tiempo de consulta. OSRM implementa optimizaciones para minimizar atajos redundantes.
\end{enumerate}

La complejidad de esta etapa es $O(|V| \cdot |E| \log |V|)$ en el peor caso, pero en redes viales con estructura jerárquica natural (como La Paz), el tiempo de ejecución es significativamente menor. Para la red de La Paz, esta etapa requiere aproximadamente 30-60 segundos.

Archivos generados:
\begin{itemize}
	\item \texttt{lapaz\_filtered.osrm.partition}: Información de particionamiento
	\item \texttt{lapaz\_filtered.osrm.cells}: Estructura de celdas jerárquicas
\end{itemize}

\paragraph{Etapa 3: Customize (customización de pesos)}

La tercera y última etapa preprocesa los atajos con los pesos finales del grafo:

\begin{verbatim}
osrm-customize lapaz_filtered.osrm
\end{verbatim}

Esta etapa calcula y almacena los pesos exactos (tiempos de viaje) de todos los atajos creados en la etapa de particionamiento. Esto permite que el servidor de ruteo responda consultas sin necesidad de recalcular pesos en tiempo de ejecución.

La etapa \texttt{customize} es especialmente útil cuando se desea experimentar con diferentes perfiles de velocidad (e.g., escenarios de tráfico congestionado vs. fluido) sin recomputar todo el particionamiento: solo se reejecutaría \texttt{customize} con los nuevos pesos.

Archivos finales generados:
\begin{itemize}
	\item \texttt{lapaz\_filtered.osrm.hsgr}: Grafo jerárquico completo (Hierarchical Sparse Graph Representation)
	\item \texttt{lapaz\_filtered.osrm.datasource\_names}: Metadatos de fuente de datos
\end{itemize}

\paragraph{Validación del preprocesamiento}

Al finalizar las tres etapas, se verifica la integridad del grafo preprocesado iniciando el servidor de ruteo en modo de prueba:

\begin{verbatim}
osrm-routed --algorithm mld lapaz_filtered.osrm
\end{verbatim}

El parámetro \texttt{--algorithm mld} especifica el uso de Multi-Level Dijkstra (MLD), una variante de Contraction Hierarchies implementada en OSRM v5.26.0 que optimiza el uso de memoria para grafos grandes.

Si el servidor inicia sin errores y responde correctamente a consultas de prueba (e.g., \texttt{http://localhost:5000/route/v1/driving/-110.31,24.14;-110.30,24.15}), el preprocesamiento se considera exitoso.

\paragraph{Persistencia y reutilización}

El conjunto completo de archivos \texttt{.osrm.*} generados por el pipeline de preprocesamiento se almacena en el directorio \texttt{osrm\_data/} del proyecto. Estos archivos constituyen un \textbf{artefacto reproducible crítico}: mientras el archivo \texttt{.osm} original y el perfil \texttt{car.lua} permanezcan sin cambios, el preprocesamiento generará exactamente los mismos archivos binarios, garantizando que consultas idénticas produzcan rutas idénticas en ejecuciones futuras de la simulación.

El tamaño típico del conjunto de archivos preprocesados para La Paz es de aproximadamente 30-50 MB (sin comprimir), lo cual permite su inclusión en repositorios Git LFS para distribución junto con el código del proyecto.

\subsection{Validación de cobertura de la red}

Una vez completado el preprocesamiento de OSRM, es fundamental validar que la red vial cubre adecuadamente todas las ubicaciones de interés del problema (restaurantes, destinos de clientes) y que no existen puntos inaccesibles o componentes desconectados que invaliden los resultados de simulación.

\paragraph{Verificación de componentes conexos}

El primer paso de validación consiste en confirmar que el grafo $G$ de la red vial es \textbf{fuertemente conexo} (strongly connected), es decir, que existe un camino dirigido desde cualquier nodo $u$ hacia cualquier otro nodo $v$. En redes viales urbanas bien desarrolladas, esto generalmente se cumple; sin embargo, errores en los datos OSM (e.g., segmentos viales desconectados, sentidos únicos mal etiquetados) pueden generar componentes aislados.

OSRM reporta automáticamente el número de componentes conexos durante la etapa \texttt{extract}:

\begin{verbatim}

\end{verbatim}

Si el porcentaje de nodos en el componente más grande es inferior al 95\%, se requiere investigación adicional para identificar y corregir desconexiones en el archivo \texttt{.osm}.

\paragraph{Validación de snapping de restaurantes}

El archivo \texttt{data/la\_paz\_restaurants.geojson} contiene las coordenadas GPS de 142 restaurantes en La Paz, extraídas de OpenStreetMap mediante el script \texttt{scripts/extraccion\_restaurantes.py}. Cada restaurante se representa como un punto geográfico con coordenadas $(lon, lat)$.

\section{Generación de instancias sintéticas}

La evaluación experimental del Rolling Horizon requiere instancias de prueba que capturen las características estadísticas reales de sistemas de entrega de comida (patrones temporales de demanda, distribución geográfica de restaurantes y clientes, rangos típicos de distancia), pero que sean completamente controladas y reproducibles. Esta sección documenta el proceso de generación de instancias sintéticas que emulan el comportamiento del dataset LaDe \citep{Wu2023} adaptado al contexto urbano de La Paz, garantizando que todos los experimentos se ejecuten sobre escenarios idénticos.

\subsection{Definición del polígono urbano de La Paz}

El primer requisito para generar órdenes sintéticas realistas es definir un \textbf{polígono urbano} que delimite el área geográfica donde se generarán las ubicaciones de restaurantes y destinos de clientes. Este polígono debe:

\begin{enumerate}
	\item Cubrir la zona urbana densa de La Paz donde operan restaurantes reales
	\item Excluir áreas rurales, cuerpos de agua, y zonas no transitables
	\item Estar completamente contenido dentro del bounding box de la red OSM preprocesada (para garantizar rutabilidad)
\end{enumerate}

\paragraph{Coordenadas del polígono urbano}

El polígono se define mediante cuatro vértices que delimitan un cuadrilátero irregular ajustado a la geografía urbana de La Paz:

\begin{verbatim}
POLYGON_COORDS = [
    (24.124041, -110.311612),  # Vértice Noroeste
    (24.133011, -110.335855),  # Vértice Noreste
    (24.159317, -110.309647),  # Vértice Sureste
    (24.147104, -110.292893),  # Vértice Suroeste
]
\end{verbatim}

Estas coordenadas se expresan en el formato $(lat, lon)$ (latitud, longitud) utilizando el sistema de referencia WGS84 (EPSG:4326), el estándar para datos GPS y OpenStreetMap.

\paragraph{Justificación geográfica del polígono}

La selección de vértices se basa en los siguientes criterios:

\begin{itemize}
	\item \textbf{Vértice Noroeste (24.124, -110.312):} Delimita la zona costera del malecón, excluyendo el mar hacia el oeste.
	
	\item \textbf{Vértice Noreste (24.133, -110.336):} Marca el límite norte de la zona urbana densa, excluyendo desarrollos residenciales dispersos más al norte.
	
	\item \textbf{Vértice Sureste (24.159, -110.310):} Cubre la expansión urbana hacia el sureste (colonias residenciales recientes).
	
	\item \textbf{Vértice Suroeste (24.147, -110.293):} Límite oriental que excluye áreas semi-rurales.
\end{itemize}

El polígono resultante abarca aproximadamente 18 km² (área calculada mediante la fórmula de Shoelace para polígonos no convexos), lo cual es consistente con el tamaño de la zona urbana operacional de La Paz donde se concentran los restaurantes del dataset \texttt{la\_paz\_restaurants.geojson}.

Como se documentó en la Sección 7.2.3, el bounding box de la red OSM es $[-110.335, 24.100, -110.290, 24.160]$. Se verifica que el polígono urbano está completamente contenido:

\subsection{Calibración temporal inspirada en LaDe (Wu2023)}

El dataset LaDe \citep{Wu2023} constituye el benchmark más completo de datos reales de entrega de comida disponible públicamente, compilando 9.44 millones de órdenes de plataformas chinas durante 2020. Los autores documentan patrones temporales característicos que se generalizan a sistemas de meal delivery urbanos:

\begin{itemize}
	\item \textbf{Picos bimodales de demanda:} Un pico matutino (desayuno/almuerzo) alrededor de las 09:00-11:00, y un pico vespertino (cena) alrededor de las 17:00-19:00.
	\item \textbf{Intensidad base baja:} Demanda sostenida pero reducida fuera de picos.
	\item \textbf{Proceso de llegada estocástico:} Las órdenes arriban según un proceso de Poisson no homogéneo con función de intensidad $\lambda(t)$ variable.
\end{itemize}

Esta subsección documenta cómo se adaptan estos patrones para generar 1,038 órdenes sintéticas distribuidas entre las 08:00 y 19:00 horas (ventana operacional de 11 horas).

\paragraph{Función de intensidad bimodal}

La función de intensidad $\lambda(t)$ se modela como la suma de una intensidad base constante más dos componentes gaussianas centradas en los horarios de pico:

\begin{equation}
\lambda(t) = \lambda_{\text{base}} + \lambda_{\text{morning}} \cdot \exp\left(-\frac{(t - t_{\text{morning}})^2}{2\sigma^2}\right) + \lambda_{\text{evening}} \cdot \exp\left(-\frac{(t - t_{\text{evening}})^2}{2\sigma^2}\right)
\end{equation}

donde:
\begin{itemize}
	\item $\lambda_{\text{base}} = 0.6$ órdenes/minuto: Intensidad base constante
	\item $\lambda_{\text{morning}} = 2.4$ órdenes/minuto: Amplitud del pico matutino
	\item $\lambda_{\text{evening}} = 2.0$ órdenes/minuto: Amplitud del pico vespertino
	\item $t_{\text{morning}} = 09:00$ horas: Centro del pico matutino
	\item $t_{\text{evening}} = 17:00$ horas: Centro del pico vespertino
	\item $\sigma = 45$ minutos: Desviación estándar de las gaussianas (controla ancho de picos)
\end{itemize}

\paragraph{Implementación del perfil de intensidad}

La función \texttt{build\_intensity\_profile()} en \texttt{scripts/make\_synth\_orders.py} discretiza $\lambda(t)$ en bins de 1 minuto:

\begin{verbatim}
def build_intensity_profile(duration_minutes, rng, target_orders):
    minute_axis = np.arange(duration_minutes, dtype=float)
    profile = np.full(duration_minutes, BASE_INTENSITY, dtype=float)
    
    def gaussian_weight(center_hour, amplitude):
        center_minute = (center_hour - START_HOUR) * 60
        return amplitude * np.exp(
            -0.5 * ((minute_axis - center_minute) / PEAK_STD_MINUTES) ** 2
        )
    
    profile += gaussian_weight(MORNING_PEAK_HOUR, MORNING_PEAK_WEIGHT)
    profile += gaussian_weight(EVENING_PEAK_HOUR, EVENING_PEAK_WEIGHT)
    
    # Escalar para alcanzar target_orders total
    scale = target_orders / profile.sum()
    profile *= scale
    
    # Muestrear Poisson para cada minuto
    orders_per_minute = rng.poisson(profile)
    return orders_per_minute
\end{verbatim}

El perfil resultante es un arreglo de 660 elementos (11 horas × 60 minutos), donde cada elemento especifica el número esperado de órdenes en ese minuto. El escalamiento final garantiza que $\sum_{t=0}^{660} \lambda(t) \approx 1{,}038$ órdenes.

\paragraph{Generación de timestamps de colocación}

Los tiempos exactos de colocación de órdenes se generan mediante:

\begin{enumerate}
	\item \textbf{Muestreo de minutos:} Para cada minuto $t$, se muestrea $N_t \sim \text{Poisson}(\lambda(t))$ órdenes.
	
	\item \textbf{Asignación de segundos aleatorios:} Dentro de cada minuto con $N_t > 0$ órdenes, se asignan segundos uniformes $s \sim \text{Uniform}(0, 59)$ para evitar colocaciones simultáneas exactas.
	
	\item \textbf{Construcción de timestamps:} Se construyen objetos \texttt{datetime}:
	\begin{verbatim}
	placement_time = START_TIME + timedelta(minutes=t, seconds=s)
	\end{verbatim}
\end{enumerate}

\paragraph{Tiempos de preparación}

El tiempo de preparación (prep time) de cada orden se muestrea de una distribución normal truncada:

\begin{equation}
\text{prep\_time} \sim \max(5, \mathcal{N}(12, 3)) \quad \text{(minutos)}
\end{equation}

Esta distribución refleja:
\begin{itemize}
	\item Media de 12 minutos: tiempo típico de preparación para órdenes de comida rápida
	\item Desviación estándar de 3 minutos: variabilidad entre platillos simples (5-8 min) y complejos (15-18 min)
	\item Truncamiento en 5 minutos: evita tiempos de preparación irrealistamente cortos
\end{itemize}

El tiempo de preparación lista (\texttt{ready\_time}) se calcula como:

\begin{equation}
\texttt{ready\_time} = \texttt{placement\_time} + \texttt{prep\_time}
\end{equation}

\subsection{Muestreo geográfico de restaurantes y destinos}

La generación de ubicaciones geográficas realistas requiere capturar dos características fundamentales:

\begin{enumerate}
	\item \textbf{Heterogeneidad espacial de restaurantes:} Los restaurantes reales se concentran en zonas comerciales específicas, no están distribuidos uniformemente.
	\item \textbf{Rangos realistas de distancia restaurante-cliente:} Las órdenes de meal delivery típicamente tienen distancias de 2-5 km según datos de LaDe y Grubhub.
\end{enumerate}

\paragraph{Muestreo de restaurantes desde catálogo real}

El archivo \texttt{data/la\_paz\_restaurants.geojson} contiene 142 restaurantes extraídos de OpenStreetMap con coordenadas GPS verificadas. Para cada orden sintética, se selecciona un restaurante del catálogo mediante:

\begin{verbatim}
restaurant_id = rng.integers(0, len(restaurants))
restaurant = restaurants[restaurant_id]
\end{verbatim}

Este muestreo uniforme simple asume que todos los restaurantes tienen volúmenes de órdenes similares. En escenarios más sofisticados, se podría implementar muestreo ponderado por popularidad (e.g., cadenas de comida rápida reciben más órdenes que restaurantes boutique).

\paragraph{Generación de destinos de clientes}

Las ubicaciones de destino (clientes) se generan mediante \textbf{muestreo uniforme dentro del polígono urbano}, utilizando el algoritmo de rejection sampling:

\begin{verbatim}
def sample_point_in_polygon(polygon, rng, max_tries=1000):
    minx, miny, maxx, maxy = polygon.bounds
    for _ in range(max_tries):
        x = rng.uniform(minx, maxx)
        y = rng.uniform(miny, maxy)
        candidate = Point(x, y)
        if candidate.within(polygon):
            return candidate
    return polygon.representative_point()  # Fallback
\end{verbatim}

Este algoritmo:
\begin{enumerate}
	\item Muestrea coordenadas $(x, y)$ uniformemente dentro del bounding box rectangular del polígono
	\item Verifica si el punto está dentro del polígono usando el test de contención de Shapely
	\item Retorna el primer punto válido encontrado
	\item Si después de 1,000 intentos no se encuentra punto válido (caso extremadamente raro para polígonos con área significativa), retorna el centroide del polígono
\end{enumerate}

La complejidad esperada es $O(1)$ dado que el área del polígono cubre aproximadamente 60\% del bounding box rectangular.

\paragraph{Validación de rangos de distancia restaurante-cliente}

Para garantizar realismo, cada orden debe satisfacer restricciones de distancia:

\begin{equation}
2 \text{ km} \leq d(\text{restaurante}, \text{cliente}) \leq 5 \text{ km}
\end{equation}

El algoritmo de asignación implementa:

\begin{verbatim}
MIN_DISTANCE_KM = 2.0
MAX_DISTANCE_KM = 5.0

\subsection{Dimensionamiento de la flota de couriers}

El tamaño de la flota de couriers es un parámetro crítico que determina la carga operacional del sistema. Una flota insuficiente resulta en tiempos de espera excesivos y degradación del SLA; una flota sobredimensionada genera costos laborales innecesarios y baja utilización de couriers.

\paragraph{Fórmula de dimensionamiento basada en productividad}

El dimensionamiento se basa en la \textbf{productividad target} (número de órdenes por courier por turno), calibrada según datos LaDe:

\begin{equation}
n_{\text{couriers}} = \max\left(n_{\text{min}}, \left\lceil \frac{N_{\text{total}}}{p_{\text{target}}} \right\rceil\right)
\end{equation}

donde:
\begin{itemize}
	\item $N_{\text{total}} = 1{,}038$: Número total de órdenes en la instancia
	\item $p_{\text{target}} = 18$: Productividad target (órdenes/courier/turno)
	\item $n_{\text{min}} = 15$: Tamaño mínimo de flota para garantizar cobertura geográfica
	\item $\lceil \cdot \rceil$: Operador de techo (redondeo hacia arriba)
\end{itemize}

\paragraph{Calibración de productividad target}

El valor $p_{\text{target}} = 18$ se deriva de:

\begin{itemize}
	\item \textbf{Dataset LaDe \citep{Wu2023}:} Productividad promedio reportada de 17-20 órdenes/courier/turno de 8 horas en ciudades chinas de tamaño medio.
	
	\item \textbf{Validación con Grubhub:} \citet{Reyes2018} reportan productividades de 18-22 órdenes/courier-hora en escenarios de alta demanda, lo cual equivale a ~18 órdenes en turnos de 6-7 horas con tiempos muertos.
	
	\item \textbf{Ajuste para La Paz:} La geometría urbana de La Paz (ciudad compacta con distancias cortas) permite productividades ligeramente superiores a ciudades más dispersas.
\end{itemize}

\paragraph{Cálculo para la instancia sintética}

Aplicando la fórmula:

\begin{equation}
n_{\text{couriers}} = \max\left(15, \left\lceil \frac{1{,}038}{18} \right\rceil\right) = \max(15, \lceil 57.67 \rceil) = \max(15, 58) = 58
\end{equation}

La flota resultante es de \textbf{58 couriers}.

\section{Implementación de políticas de despacho}

La evaluación comparativa del Rolling Horizon contra FCFS requiere implementaciones rigurosas de ambas políticas que respeten fielmente sus especificaciones teóricas. Esta sección documenta la arquitectura de código, algoritmos implementados, y decisiones de diseño de las dos políticas de despacho evaluadas en el experimento.

\subsection{Política base: FCFS}

First-Come-First-Served (FCFS) constituye la política de despacho más simple y ampliamente utilizada en sistemas de entrega bajo demanda. Bajo FCFS, cada orden se asigna inmediatamente al courier disponible más cercano al restaurante en el momento en que la orden está lista para pickup, sin considerar información futura o posibilidades de consolidación.

\paragraph{Principio de operación}

La lógica FCFS se activa mediante la variable de entorno \texttt{FCFS\_POLICY=1}, que modifica el comportamiento del bucle principal de simulación en \texttt{src/main.py}:

\begin{verbatim}
use_fcfs = os.environ.get('FCFS_POLICY') == '1'

if use_fcfs:
    # Asignar órdenes una por una al courier más cercano
    for order in orders_ready:
        if order.status == 'ready':
            assign_order_to_nearest_courier(order, available_couriers, 
                                            current_time)
else:
    # Ejecutar Rolling Horizon
    ...
\end{verbatim}

\paragraph{Algoritmo de asignación FCFS}

La función \texttt{assign\_order\_to\_nearest\_courier()} implementa el algoritmo greedy de proximidad geográfica:

\begin{verbatim}
def assign_order_to_nearest_courier(order, couriers, current_time):
    best_courier = None
    min_dist = float('inf')
    
    for courier in couriers:
        if courier.current_route is None:  # Courier disponible
            # Distancia euclidiana courier → restaurante
            dist = np.sqrt(
                (courier.location[0] - order.restaurant.location[0])**2 + 
                (courier.location[1] - order.restaurant.location[1])**2
            )
            if dist < min_dist:
                min_dist = dist
                best_courier = courier
    
    if best_courier:
        # Calcular ruta real via OSRM: courier → restaurante → cliente
        route_data = get_route_details(
            best_courier.location,
            [order.restaurant.location, order.dropoff_loc]
        )
        
        if route_data:
            # Asignar ruta al courier
            best_courier.current_route = {
                'orders': [order],
                'route': route_data,
                'start_time': current_time,
                'completion_time': current_time + 
                    timedelta(seconds=route_data['duration']),
                'commitment_type': 'final'
            }
            order.status = 'assigned'
            order.courier_id = best_courier.id
\end{verbatim}

\paragraph{Características clave de la implementación}

\begin{itemize}
	\item \textbf{Greedy selection:} El courier se selecciona mediante búsqueda lineal en $O(|C|)$ donde $C$ es el conjunto de couriers disponibles. No se utiliza estructura de datos espacial (e.g., k-d tree) dado el tamaño reducido de la flota (58 couriers).
	
	\item \textbf{Distancia euclidiana para selección:} La métrica de proximidad utiliza distancia euclidiana (gran círculo) en lugar de distancia de ruteo OSRM por eficiencia computacional. Esta aproximación es aceptable dado que en áreas urbanas densas, la correlación entre distancia euclidiana y distancia de ruteo es alta ($r > 0.95$).
	
	\item \textbf{Validación de ruta OSRM:} Aunque la selección usa distancia euclidiana, la ruta final se calcula via OSRM para garantizar realismo en tiempos de viaje y distancias.
	
	\item \textbf{Asignación individual:} Cada orden se asigna como ruta individual (bundle size = 1), sin consolidación. El courier ejecuta la ruta restaurante $\to$ cliente y queda disponible inmediatamente después.
	
	\item \textbf{Commitment inmediato:} La asignación es final e irrevocable (no existe concepto de asignación tentativa bajo FCFS).
\end{itemize}

\paragraph{Complejidad computacional}

Para una época de simulación con $O$ órdenes listas y $C$ couriers disponibles:
\begin{itemize}
	\item \textbf{Selección de courier:} $O(O \cdot C)$ comparaciones de distancia
	\item \textbf{Consultas OSRM:} $O$ llamadas HTTP (una por orden asignada)
	\item \textbf{Total:} $O(O \cdot C + O \cdot T_{\text{OSRM}})$ donde $T_{\text{OSRM}} \approx 1-2$ ms
\end{itemize}

Para la instancia sintética ($O \approx 15$ órdenes por época de 5 min, $C = 58$), el tiempo de cómputo por época es $<$ 100 ms, despreciable comparado con la duración de la época (300 segundos).

\subsection{Política avanzada: Rolling Horizon}

La implementación del Rolling Horizon sigue fielmente el algoritmo de tres fases propuesto por \citet{Reyes2018}: (1) generación de bundles mediante inserción paralela, (2) matching bipartito bundle-courier via algoritmo húngaro, y (3) commitment diferenciado según grupo de factibilidad. Esta subsección documenta cada fase en detalle.

\subsubsection{Generación de bundles}

La fase de bundling agrupa órdenes del mismo restaurante que son temporalmente y geográficamente compatibles, generando rutas consolidadas que maximizan eficiencia operacional sin violar SLA.

\paragraph{Cálculo del tamaño target de bundle ($Z_t$)}

Siguiendo \citet{Reyes2018}, el tamaño objetivo de bundle se calcula como el ratio entre órdenes disponibles y couriers disponibles en horizontes de lookahead $\Delta_1$ y $\Delta_2$:

\begin{equation}
Z_t = \left\lceil \frac{|\{o \in \mathcal{O}_t : e_o \leq t + \Delta_1\}|}{|\{c \in \mathcal{C}_t : a_c \leq t + \Delta_2\}|} \right\rceil
\end{equation}

donde:
\begin{itemize}
	\item $e_o$: Tiempo de preparación lista (\texttt{ready\_time}) de orden $o$
	\item $a_c$: Tiempo de disponibilidad de courier $c$ (cuando finaliza ruta actual)
	\item $\Delta_1 = 20$ min: Lookahead para órdenes (configurado en \texttt{config.py})
	\item $\Delta_2 = 20$ min: Lookahead para couriers
\end{itemize}

Implementación en \texttt{src/bundling.py}:

\begin{verbatim}
def compute_target_bundle_size(current_time, orders, couriers):
    # Órdenes que estarán listas en próximos DELTA_1 minutos
    orders_ready = [
        o for o in orders 
        if o.ready_time <= current_time + DELTA_1
    ]
    
    # Couriers disponibles en próximos DELTA_2 minutos
    def get_available_time(courier):
        if courier.current_route is None:
            return current_time
        return courier.current_route.get('completion_time', current_time)
    
    couriers_soon_available = [
        c for c in couriers 
        if get_available_time(c) <= current_time + DELTA_2
    ]
    
    if not couriers_soon_available:
        return 1  # Fallback si no hay couriers disponibles
    
    # Calcular ratio con ceiling
    ratio = len(orders_ready) / len(couriers_soon_available)
    target = max(int(np.ceil(ratio)), 1)
    
    # Limitar a capacidad máxima
    if MAX_TARGET_BUNDLE_SIZE:
        target = min(target, MAX_TARGET_BUNDLE_SIZE)
    
    return target
\end{verbatim}

\paragraph{Heurística de inserción paralela}

Para cada restaurante con órdenes listas, la función \texttt{generate\_bundles\_for\_restaurant()} genera bundles mediante inserción secuencial de órdenes compatibles:

\begin{verbatim}
def generate_bundles_for_restaurant(restaurant, current_time, 
                                   target_size, n_couriers):
    eligible_orders = [
        o for o in restaurant.orders 
        if o.status == "ready" and 
           o.ready_time <= current_time + ASSIGNMENT_HORIZON
    ]
    
    if not eligible_orders:
        return []
    
    # Ordenar órdenes por ready_time (FCFS dentro del restaurante)
    eligible_orders.sort(key=lambda o: o.ready_time)
    
    bundles = []
    remaining_orders = eligible_orders.copy()
    
    while remaining_orders:
        # Crear bundle semilla con primera orden
        seed_order = remaining_orders.pop(0)
        bundle = [seed_order]
        
        # Inserción paralela: agregar órdenes compatibles
        for candidate in remaining_orders[:]:
            if len(bundle) >= target_size:
                break
            
            # Verificar compatibilidad temporal
            time_diff = abs(
                (candidate.ready_time - seed_order.ready_time).total_seconds()
            )
            if time_diff > 600:  # 10 minutos
                continue
            
            # Verificar factibilidad de SLA con inserción
            test_bundle = bundle + [candidate]
            if is_bundle_feasible(test_bundle, current_time):
                bundle.append(candidate)
                remaining_orders.remove(candidate)
        
        bundles.append(bundle)
    
    return bundles
\end{verbatim}

\paragraph{Verificación de factibilidad de SLA}

La función \texttt{is\_bundle\_feasible()} valida que la ruta consolidada no viole el SLA de 40 minutos click-to-door para ninguna orden del bundle:

\begin{verbatim}
def is_bundle_feasible(bundle, current_time):
    # Calcular ruta óptima: restaurante → dropoff_1 → ... → dropoff_n
    route = get_route_details(
        bundle[0].restaurant.location,
        [o.dropoff_loc for o in bundle]
    )
    
    if not route:
        return False
    
    # Simular tiempos de entrega secuencial
    elapsed_time = 0
    for i, order in enumerate(bundle):
        # Tiempo hasta entrega de esta orden
        leg_duration = route['legs'][i]['duration'] / 60.0  # segundos → min
        service_time = SERVICE_TIME / 60.0  # tiempo en restaurante
        
        elapsed_time += leg_duration + service_time
        
        # Verificar SLA
        estimated_delivery = order.placement_time + 
            timedelta(minutes=elapsed_time)
        sla_deadline = order.placement_time + MAX_CLICK_TO_DOOR
        
        if estimated_delivery > sla_deadline:
            return False
    
    return True
\end{verbatim}

\subsubsection{Matching bipartito}

Una vez generados los bundles, la fase de matching resuelve el problema de asignación óptima bundle-courier mediante el algoritmo húngaro, maximizando la suma de pesos $w_{bc}$ que capturan eficiencia y calidad de servicio.

\paragraph{Cálculo de pesos de matching}

El peso $w_{bc}$ para asignar bundle $b$ a courier $c$ se define según \citet{Reyes2018}:

\begin{equation}
w_{bc} = \frac{|b|}{T_{bc}^{\text{delivery}}} - \theta \cdot (t_{bc}^{\text{pickup}} - e_b) - \text{penalty}_{\text{grupo}}(b)
\end{equation}

donde:
\begin{itemize}
	\item $|b|$: Número de órdenes en el bundle (favorece bundles grandes)
	\item $T_{bc}^{\text{delivery}}$: Tiempo total de entrega (inbound + outbound)
	\item $t_{bc}^{\text{pickup}}$: Tiempo estimado de arribo al restaurante
	\item $e_b = \max_{o \in b} \{\texttt{ready\_time}(o)\}$: Tiempo de preparación lista más tardío en el bundle
	\item $\theta = 0.1$: Penalización por retraso en pickup (configurado en \texttt{config.py})
	\item $\text{penalty}_{\text{grupo}}(b)$: Penalización según grupo de factibilidad
\end{itemize}

Implementación en \texttt{src/bundling.py}:

\begin{verbatim}
def calculate_bundle_score(bundle, courier, current_time):
    # Ruta completa: courier → restaurante → dropoffs
    full_route = get_route_details(
        courier.location,
        [bundle[0].restaurant.location] + 
        [o.dropoff_loc for o in bundle]
    )
    
    if not full_route:
        return float('-inf')
    
    # Tiempos de viaje
    total_travel_time_min = full_route['duration'] / 60.0
    inbound_route = get_route_details(
        courier.location, 
        [bundle[0].restaurant.location]
    )
    inbound_duration_min = inbound_route['duration'] / 60.0
    
    # Tiempo de disponibilidad del courier
    if courier.current_route is None:
        courier_available_time = current_time
    else:
        courier_available_time = courier.current_route.get(
            'completion_time', current_time
        )
    
    # Tiempo de arribo al restaurante
    pickup_time = courier_available_time + 
        timedelta(minutes=inbound_duration_min)
    
    # Tiempo de preparación lista del bundle
    bundle_ready_time = max(o.ready_time for o in bundle)
    pickup_delay = (pickup_time - bundle_ready_time).total_seconds() / 60.0
    
    # Componente 1: Eficiencia (órdenes/tiempo)
    efficiency = len(bundle) / max(total_travel_time_min, 1)
    
    # Componente 2: Penalización por pickup tardío
    pickup_penalty = PICKUP_DELAY_THETA * max(pickup_delay, 0)
    
    # Componente 3: Penalización por grupo
    group = classify_bundle(bundle, [courier], current_time)
    if group == 1:
        group_penalty = GROUP_I_PENALTY  # -1000
    elif group == 2:
        group_penalty = GROUP_II_PENALTY  # -100
    else:
        group_penalty = 0
    
    weight = efficiency - pickup_penalty + group_penalty
    return weight
\end{verbatim}

\paragraph{Resolución del matching mediante algoritmo húngaro}

La matriz de pesos $W_{BC}$ se construye evaluando \texttt{calculate\_bundle\_score(b, c)} para todos los pares bundle-courier, luego se resuelve el problema de asignación mediante \texttt{scipy.optimize.linear\_sum\_assignment}:

\begin{verbatim}
def assign_bundles_to_couriers(bundles, couriers, current_time):
    if not bundles or not couriers:
        return
    
    # Construir matriz de costos (negamos pesos para maximizar)
    cost_matrix = np.zeros((len(bundles), len(couriers)))
    
    for i, bundle in enumerate(bundles):
        for j, courier in enumerate(couriers):
            weight = calculate_bundle_score(bundle, courier, current_time)
            cost_matrix[i, j] = -weight  # Negar para maximización
    
    # Resolver matching
    row_ind, col_ind = linear_sum_assignment(cost_matrix)
    
    # Aplicar asignaciones
    for bundle_idx, courier_idx in zip(row_ind, col_ind):
        if cost_matrix[bundle_idx, courier_idx] < float('inf'):
            bundle = bundles[bundle_idx]
            courier = couriers[courier_idx]
            assign_bundle_to_courier(bundle, courier, current_time)
\end{verbatim}

La complejidad del algoritmo húngaro es $O(n^3)$ donde $n = \max(|B|, |C|)$. Para la instancia sintética con típicamente $|B| \approx 10-20$ bundles y $|C| = 58$ couriers por época, el tiempo de cómputo es $< 50$ ms.

\subsubsection{Estrategia de commitment}

La fase final del Rolling Horizon diferencia entre asignaciones tentativas (que pueden ser reconsideradas en futuras épocas) y compromisos finales (irrevocables), según la clasificación de bundles en tres grupos de factibilidad.

\paragraph{Clasificación de bundles en grupos}

Siguiendo \citet{Reyes2018}, cada bundle se clasifica en:

\begin{itemize}
	\item \textbf{Grupo I (urgentes):} Bundles cuyo tiempo de entrega más temprano posible excedería el SLA. Requieren commitment inmediato para minimizar violaciones.
	
	\item \textbf{Grupo II (restringidos):} Bundles que no pueden recogerse a tiempo (pickup tardío inevitable), pero aún factibles de entregar dentro del SLA. Se asignan tentativamente.
	
	\item \textbf{Grupo III (flexibles):} Bundles sin restricciones críticas. Se asignan tentativamente y pueden ser reconsiderados en futuras épocas.
\end{itemize}

Implementación en \texttt{src/asignaciontentativa.py}:

\begin{verbatim}
def classify_bundle(bundle, couriers, current_time):
    earliest_placement = min(o.placement_time for o in bundle)
    target_dropoff_time = earliest_placement + TARGET_CLICK_TO_DOOR
    
    # Verificar si algún courier puede entregar antes del deadline
    can_meet_deadline = False
    for c in couriers:
        epd = earliest_possible_dropoff(bundle, c, current_time)
        if epd and (epd <= target_dropoff_time):
            can_meet_deadline = True
            break
    
    if not can_meet_deadline:
        return 1  # Grupo I: SLA imposible
    
    # Verificar si todos los couriers llegan tarde al pickup
    all_couriers_miss_pickup = True
    bundle_ready_time = max(o.ready_time for o in bundle)
    
    for c in couriers:
        inbound = earliest_pickup_estimate(bundle, c, current_time)
        if inbound <= bundle_ready_time:
            all_couriers_miss_pickup = False
            break
    
    if all_couriers_miss_pickup:
        return 2  # Grupo II: Pickup tardío inevitable
    
    return 3  # Grupo III: Sin restricciones críticas
\end{verbatim}

\paragraph{Reglas de commitment}

Cada asignación bundle-courier recibe un tipo de commitment según su grupo:

\begin{verbatim}
def assign_bundle_to_courier(bundle, courier, current_time):
    group = classify_bundle(bundle, [courier], current_time)
    
    if group == 1:
        commitment_type = 'final'  # Grupo I: Irrevocable
    elif group == 2:
        commitment_type = 'tentative'  # Grupo II: Reconsiderable
    else:
        commitment_type = 'tentative'  # Grupo III: Reconsiderable
    
    # Calcular ruta y asignar
    route_data = get_route_details(
        courier.location,
        [bundle[0].restaurant.location] + 
        [o.dropoff_loc for o in bundle]
    )
    
    courier.current_route = {
        'orders': bundle,
        'route': route_data,
        'start_time': current_time,
        'completion_time': current_time + 
            timedelta(seconds=route_data['duration']),
        'commitment_type': commitment_type
    }
    
    for order in bundle:
        order.status = 'assigned' if commitment_type == 'final' \
                       else 'tentative'
        order.courier_id = courier.id
        order.bundle_size = len(bundle)
\end{verbatim}

\paragraph{Forzado de commitment por tiempo de espera}

Adicionalmente, si una orden ha esperado más de \texttt{MAX\_WAIT\_BEFORE\_FORCED\_COMMIT} = 10 minutos desde su \texttt{ready\_time}, se fuerza un commitment final independiente de su grupo:

\begin{verbatim}
wait_time = (current_time - bundle_ready_time).total_seconds() / 60.0

if wait_time > MAX_WAIT_BEFORE_FORCED_COMMIT:
    commitment_type = 'final'  # Forzar por timeout
\end{verbatim}

Esta regla previene degradación extrema de Ready-to-Pickup times en escenarios de baja demanda donde bundles podrían permanecer indefinidamente en estado tentativo.

\subsection{Control de aleatoriedad y semillas}

La reproducibilidad de experimentos computacionales requiere control riguroso de todas las fuentes de aleatoriedad. Esta subsección documenta los mecanismos implementados para garantizar que ejecuciones idénticas del experimento produzcan resultados bit-a-bit idénticos.

\paragraph{Fuentes de aleatoriedad en el sistema}

El sistema MDRP presenta las siguientes fuentes de variación estocástica:

\begin{enumerate}
	\item \textbf{Generación de instancia sintética:}
	\begin{itemize}
		\item Tiempos de arribo de órdenes (proceso de Poisson no homogéneo)
		\item Tiempos de preparación (distribución normal truncada)
		\item Ubicaciones de destinos de clientes (muestreo uniforme en polígono)
		\item Selección de restaurantes (muestreo con restricción de distancia)
	\end{itemize}
	
	\item \textbf{Desempates en algoritmos:}
	\begin{itemize}
		\item Matching bipartito con pesos idénticos (algoritmo húngaro puede retornar soluciones diferentes)
		\item Selección de courier en FCFS cuando múltiples couriers están a igual distancia
	\end{itemize}
	
	\item \textbf{Comportamiento de OSRM:}
	\begin{itemize}
		\item OSRM es determinista: para los mismos pares origen-destino, retorna rutas idénticas
		\item No hay variación estocástica en tiempos de viaje (no se modela congestión)
	\end{itemize}
\end{enumerate}

\paragraph{Estrategia de control mediante semillas}

El control de aleatoriedad se implementa en dos niveles:

\textbf{Nivel 1: Generación de instancia sintética (semilla fija)}

El script \texttt{scripts/make\_synth\_orders.py} utiliza una semilla fija para generar la instancia base:

\begin{verbatim}
DEFAULT_SEED = 2025

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--seed", type=int, default=DEFAULT_SEED)
    args = parser.parse_args()
    
    # Inicializar generador numpy con semilla
    rng = np.random.default_rng(args.seed)
    
    # Generar órdenes usando rng
    generate_orders(rng, target_orders, output_path)
\end{verbatim}

Con \texttt{--seed=2025}, cada ejecución del script genera el archivo CSV idéntico con exactamente las mismas 1,038 órdenes. Cambiar la semilla genera una instancia diferente pero igualmente reproducible.

\textbf{Nivel 2: Ejecución de simulación (determinista)}

Una vez generada la instancia CSV, la simulación es \textbf{completamente determinista}:

\begin{itemize}
	\item No se utiliza ningún generador de números aleatorios durante \texttt{run\_simulation()}
	\item El orden de procesamiento de eventos está completamente determinado por timestamps
	\item Los desempates se resuelven mediante ordenamiento estable (e.g., por ID de courier cuando distancias son iguales)
	\item OSRM produce rutas deterministas
\end{itemize}

Por lo tanto, ejecutar la misma política (FCFS o RH) sobre el mismo archivo CSV producirá resultados idénticos en cualquier máquina.

\section{Métricas de evaluación}

La evaluación cuantitativa del desempeño de las políticas de despacho FCFS y Rolling Horizon se realiza mediante un conjunto de métricas que capturan dos dimensiones complementarias: (1) calidad de servicio desde la perspectiva del cliente, y (2) eficiencia operacional desde la perspectiva de la plataforma. Esta sección define formalmente cada métrica, especifica el procedimiento de cálculo, y justifica su relevancia para la comparación de políticas.

\subsection{Métricas de calidad de servicio}

Las métricas de calidad de servicio miden la experiencia del cliente en términos de tiempos de espera y cumplimiento de compromisos de entrega. Estas métricas se alinean con las definiciones de \citet{Reyes2018} para garantizar comparabilidad con la literatura.

\paragraph{Click-to-Door (C2D)}

El tiempo \textit{click-to-door} es la métrica primaria de experiencia de cliente, definida como:

\begin{equation}
\text{C2D}_i = t^{\text{delivery}}_i - t^{\text{placement}}_i
\end{equation}

donde $t^{\text{placement}}_i$ es el instante en que el cliente $i$ coloca la orden, y $t^{\text{delivery}}_i$ es el instante de entrega física. Esta métrica captura el tiempo total percibido por el cliente desde la confirmación del pedido hasta la recepción de la comida.

\textbf{Descomposición temporal:} El tiempo C2D se puede descomponer en tres componentes:

\begin{align}
\text{C2D}_i &= \text{prep}_i + \text{R2P}_i + \text{P2D}_i \\
\text{prep}_i &= t^{\text{ready}}_i - t^{\text{placement}}_i \quad \text{(tiempo de preparación en restaurante)} \\
\text{R2P}_i &= t^{\text{pickup}}_i - t^{\text{ready}}_i \quad \text{(ready-to-pickup: espera del courier)} \\
\text{P2D}_i &= t^{\text{delivery}}_i - t^{\text{pickup}}_i \quad \text{(pickup-to-door: transporte al cliente)}
\end{align}

Esta descomposición permite diagnosticar qué componente contribuye más a los tiempos totales. Por ejemplo, tiempos R2P elevados sugieren ineficiencia en asignación de couriers; tiempos P2D elevados sugieren rutas ineficientes.

\textbf{Estadísticos reportados:} Dado que la distribución de C2D típicamente presenta sesgo positivo (cola derecha larga debido a órdenes retrasadas), se reportan estadísticos robustos además de la media:

\begin{itemize}
	\item \textbf{Media:} $\overline{\text{C2D}} = \frac{1}{n} \sum_{i=1}^{n} \text{C2D}_i$
	\item \textbf{Percentiles:} P10, P50 (mediana), P90, P95
	\item \textbf{Desviación estándar:} $\sigma_{\text{C2D}}$
\end{itemize}

El percentil 95 (P95) es especialmente relevante para SLA, ya que representa el peor caso para el 5\% de clientes más afectados.

\paragraph{Ready-to-Pickup (R2P)}

El tiempo \textit{ready-to-pickup} mide la demora entre que la comida está lista y el courier la recoge:

\begin{equation}
\text{R2P}_i = t^{\text{pickup}}_i - t^{\text{ready}}_i
\end{equation}

Esta métrica refleja directamente la eficiencia de la política de asignación. Valores bajos indican que los couriers llegan rápidamente tras la finalización de la preparación (minimizando deterioro de frescura). Valores altos indican que las órdenes esperan sin ser recogidas, lo cual puede ocurrir cuando:

\begin{itemize}
	\item La política FCFS asigna couriers antes de que las órdenes estén listas, obligando al courier a esperar (R2P $\approx$ 0 pero con tiempo muerto del courier)
	\item La política RH agrupa órdenes y retrasa la asignación hasta tener suficientes órdenes listas (R2P elevado pero mayor utilización de couriers)
\end{itemize}

\textbf{Estadísticos reportados:} Media, P10, P50, P90, desviación estándar.

\paragraph{Cumplimiento de SLA (Service Level Agreement)}

Se define el cumplimiento de SLA como la fracción de órdenes que satisfacen el objetivo de tiempo click-to-door:

\begin{equation}
\text{SLA compliance} = \frac{|\{i : \text{C2D}_i \leq \tau_{\text{target}}\}|}{|\text{órdenes entregadas}|}
\end{equation}

donde $\tau_{\text{target}}$ es el umbral objetivo (e.g., 40 minutos). Complementariamente, se calcula el \textit{overage} promedio:

\begin{equation}
\overline{\text{C2D overage}} = \frac{1}{n} \sum_{i=1}^{n} \max(0, \text{C2D}_i - \tau_{\text{target}})
\end{equation}

Este estadístico mide cuánto exceden las órdenes el objetivo en promedio, ignorando aquellas que cumplen (overage = 0).

\paragraph{Porcentaje de órdenes no entregadas}

Idealmente, todas las órdenes colocadas deben entregarse dentro de la ventana operacional. Se calcula:

\begin{equation}
\text{\% undelivered} = \frac{|\text{órdenes pendientes o canceladas}|}{|\text{total órdenes colocadas}|} \times 100
\end{equation}

En un sistema bien dimensionado (flota adecuada), este porcentaje debe ser cercano a 0\%. Valores elevados indican capacidad insuficiente o asignaciones ineficientes.

\subsection{Métricas de eficiencia operacional}

Las métricas operacionales evalúan el costo y la utilización de recursos (couriers, kilómetros recorridos) necesarios para entregar las órdenes. Estas métricas son críticas para la viabilidad económica de la plataforma.

\paragraph{Distancia total recorrida}

La distancia agregada recorrida por todos los couriers se calcula como:

\begin{equation}
D_{\text{total}} = \sum_{c=1}^{C} \sum_{r \in \text{routes}_c} d_r
\end{equation}

donde $C$ es el número de couriers, $\text{routes}_c$ son las rutas completadas por el courier $c$, y $d_r$ es la distancia (en km) de la ruta $r$. Esta métrica se obtiene directamente de las respuestas OSRM (campo \texttt{distance} en metros, convertido a km).

\textbf{Distancia promedio por orden:}

\begin{equation}
\overline{d}_{\text{per order}} = \frac{D_{\text{total}}}{|\text{órdenes entregadas}|}
\end{equation}

Valores bajos indican mayor consolidación de rutas (bundling efectivo), mientras que valores altos indican viajes individuales ineficientes.

\paragraph{Órdenes por courier-hora}

La productividad de la flota se mide como:

\begin{equation}
\rho_{\text{orders}} = \frac{|\text{órdenes entregadas}|}{\sum_{c=1}^{C} h_c}
\end{equation}

donde $h_c$ es la duración del turno del courier $c$ (en horas). Valores altos indican utilización eficiente de la capacidad de los couriers.

\paragraph{Tamaño promedio de bundle}

El tamaño promedio de los bundles asignados se calcula como:

\begin{equation}
\overline{|b|} = \frac{1}{|\text{bundles}|} \sum_{b \in \text{bundles}} |b|
\end{equation}

Para FCFS, típicamente $\overline{|b|} = 1.0$ (bundles unitarios). Para RH, valores mayores a 1.0 indican consolidación efectiva.

\textbf{Porcentaje de órdenes en bundles consolidados:}

\begin{equation}
\text{\% multi-bundle} = \frac{|\{i : \text{bundle\_size}_i > 1\}|}{|\text{órdenes entregadas}|} \times 100
\end{equation}

Esta métrica mide qué fracción de órdenes se beneficia de bundling (0\% para FCFS puro, potencialmente 60-80\% para RH efectivo).

\paragraph{Utilización de couriers}

La utilización mide el porcentaje del turno que los couriers pasan activamente conduciendo (vs. esperando):

\begin{equation}
U_c = \frac{t^{\text{driving}}_c}{h_c} \times 100\%
\end{equation}

donde $t^{\text{driving}}_c$ es el tiempo total de conducción del courier $c$ (suma de duraciones de rutas OSRM), y $h_c$ es la duración total del turno. Valores altos indican que los couriers están ocupados (deseable desde perspectiva de productividad); valores bajos indican tiempos muertos.

\paragraph{Compensación total de couriers}

El costo operacional se modela mediante la función de compensación:

\begin{equation}
\text{compensation}_c = \max(\text{órdenes}_c \times p_1, \, h_c \times p_2)
\end{equation}

donde $p_1 = \$10$ por orden y $p_2 = \$15$ por hora. Esta función garantiza un ingreso mínimo por hora incluso si el courier entrega pocas órdenes.

\textbf{Métricas derivadas:}

\begin{align}
\text{Costo total} &= \sum_{c=1}^{C} \text{compensation}_c \\
\text{Costo por orden} &= \frac{\text{Costo total}}{|\text{órdenes entregadas}|} \\
\text{Fracción con pago mínimo} &= \frac{|\{c : \text{compensation}_c = h_c \times p_2\}|}{C}
\end{align}

La fracción de couriers que reciben el pago mínimo (vs. pago por productividad) indica si la flota está sobredimensionada (muchos couriers ociosos cobrando el mínimo).

\subsection{Procedimiento de cálculo}

El cálculo de métricas se implementa en el módulo \texttt{scripts/generate\_results.py}, que procesa los archivos CSV de resultados generados por el simulador.

\paragraph{Estructura de datos de salida}

El simulador genera dos archivos CSV por ejecución (FCFS o RH):

\begin{enumerate}
	\item \textbf{\texttt{*\_results.csv}}: Métricas por orden
	\begin{verbatim}
order_id, status, placement_time, ready_time, pickup_time,
delivery_time, click_to_door, ready_to_pickup,
courier_id, bundle_size
	\end{verbatim}
	
	\item \textbf{\texttt{*\_courier\_results.csv}}: Métricas por courier

\subsection{Validación del simulador}

\paragraph{Invariantes del sistema}

El simulador debe preservar cuatro invariantes fundamentales en todo momento:

\begin{enumerate}
	\item \textbf{Conservación de órdenes:} Toda orden ingresada debe ser eventualmente asignada a un courier y entregada (o quedar pendiente al final de la ventana operacional). No deben "desaparecer" órdenes del sistema.
	
	\textit{Verificación:} Al finalizar la simulación, se verifica:
	\begin{equation}
	|\text{órdenes entregadas}| + |\text{órdenes pendientes}| = |\text{órdenes colocadas}|
	\end{equation}
	
	\item \textbf{Consistencia temporal:} Para toda orden entregada, debe cumplirse la secuencia temporal:
	\begin{equation}
	t^{\text{placement}} \leq t^{\text{ready}} \leq t^{\text{pickup}} \leq t^{\text{delivery}}
	\end{equation}
	
	Violaciones de esta desigualdad indican errores de implementación (e.g., asignar timestamps en orden incorrecto).
	
	\textit{Verificación:} El script \texttt{generate\_results.py} verifica automáticamente esta condición para todas las órdenes y emite advertencias si detecta inconsistencias.
	
	\item \textbf{Capacidad de couriers:} Ningún courier debe llevar simultáneamente más de \texttt{MAX\_BUNDLE\_SIZE} = 6 órdenes.
	
	\textit{Verificación:} Durante la ejecución, antes de asignar cada bundle, se verifica:
	\begin{verbatim}
if len(bundle.orders) > MAX_BUNDLE_SIZE:
    raise ValueError(f"Bundle exceeds capacity: {len(bundle.orders)}")
	\end{verbatim}
	
	\item \textbf{Precedencia pickup-delivery:} Para toda orden en un bundle, el courier debe visitar primero el restaurante (pickup) y luego el destino del cliente (delivery).
	
	\textit{Verificación:} La función \texttt{build\_osrm\_route()} construye rutas con estructura fija: primero todos los pickups (en orden de restaurants), luego todos los deliveries (en orden óptimo según OSRM). Esta estructura garantiza precedencia por diseño.
\end{enumerate}

\section{Protocolo de análisis estadístico}

El análisis estadístico cuantifica la significancia de las diferencias observadas entre FCFS y Rolling Horizon. Dado que el experimento compara dos políticas sobre la misma instancia (diseño pareado), se utilizan pruebas estadísticas apropiadas para datos emparejados.

\subsection{Estadísticos descriptivos y percentiles}

El primer paso del análisis es caracterizar la distribución de cada métrica para ambas políticas mediante estadísticos descriptivos.

\paragraph{Estadísticos centrales y de dispersión}

Para cada métrica $M$ (e.g., Click-to-Door, Ready-to-Pickup, distancia por orden), se calculan:

\begin{itemize}
	\item \textbf{Media aritmética:} $\overline{M} = \frac{1}{n} \sum_{i=1}^{n} M_i$
	\item \textbf{Mediana (P50):} Percentil 50, robusto a outliers
	\item \textbf{Desviación estándar:} $\sigma_M = \sqrt{\frac{1}{n-1} \sum_{i=1}^{n} (M_i - \overline{M})^2}$
	\item \textbf{Coeficiente de variación:} $\text{CV} = \frac{\sigma_M}{\overline{M}}$ (dispersión relativa)
\end{itemize}

\paragraph{Percentiles para análisis de extremos}

Los percentiles caracterizan la distribución completa y son especialmente informativos para métricas asimétricas:

\begin{itemize}
	\item \textbf{P10:} Límite superior del 10\% más rápido (mejor caso)
	\item \textbf{P50:} Mediana (caso típico)
	\item \textbf{P90:} Límite inferior del 10\% más lento (peor caso común)
	\item \textbf{P95:} Límite para 95\% de clientes (relevante para SLA)
	\item \textbf{P99:} Casos extremos (útil para detectar outliers)
\end{itemize}

def compute_descriptive_stats(df, metric_name):
    """Calcula estadísticos descriptivos para una métrica."""
    values = df[metric_name].dropna()
    
    stats = {
        'Mean': values.mean(),
        'Median (P50)': values.quantile(0.50),
        'P10': values.quantile(0.10),
        'P90': values.quantile(0.90),

        'CV': values.std() / values.mean() if values.mean() > 0 else np.nan,
        'Min': values.min(),
        'Max': values.max(),
        'N': len(values)
    }
    return stats

\subsection{Pruebas de comparación pareada}

Dado que ambas políticas se ejecutan sobre la misma instancia (mismos restaurantes, mismos clientes, mismos tiempos de preparación), las órdenes están emparejadas. Esto permite usar pruebas estadísticas más potentes que comparaciones independientes.

\paragraph{Test de Wilcoxon (signed-rank test)}

El test de Wilcoxon es una prueba no paramétrica para comparar dos muestras emparejadas. No asume normalidad de distribuciones, lo que es apropiado para métricas de delivery (típicamente asimétricas).

\textbf{Hipótesis nula ($H_0$):} No hay diferencia sistemática entre las políticas (mediana de diferencias = 0).

\textbf{Hipótesis alternativa ($H_1$):} Existe diferencia sistemática (mediana de diferencias $\neq$ 0).

\textbf{Implementación:}

\begin{verbatim}
from scipy.stats import wilcoxon

# Alinear datasets por order_id para garantizar emparejamiento
fcfs_df_sorted = fcfs_df.sort_values('order_id')
rh_df_sorted = rh_df.sort_values('order_id')

# Extraer métricas emparejadas
fcfs_ctd = fcfs_df_sorted['click_to_door'].values
rh_ctd = rh_df_sorted['click_to_door'].values

# Ejecutar test de Wilcoxon
statistic, p_value = wilcoxon(fcfs_ctd, rh_ctd, alternative='two-sided')

print(f"Wilcoxon test: statistic={statistic}, p-value={p_value:.6f}")
if p_value < 0.05:
    print("Diferencia estadísticamente significativa (alpha=0.05)")
else:
    print("No se rechaza H0 (no hay diferencia significativa)")
\end{verbatim}

\textbf{Interpretación del p-value:}

\begin{itemize}
	\item $p < 0.001$: Evidencia muy fuerte de diferencia
	\item $p < 0.01$: Evidencia fuerte de diferencia
	\item $p < 0.05$: Evidencia moderada de diferencia (umbral estándar)
	\item $p \geq 0.05$: Evidencia insuficiente para rechazar $H_0$
\end{itemize}

\paragraph{Test t pareado (alternativa paramétrica)}

Si las diferencias entre políticas se distribuyen aproximadamente normal, el test t pareado es más potente que Wilcoxon. Se calcula:

\begin{equation}
t = \frac{\overline{D}}{\text{SE}(D)} = \frac{\overline{D}}{s_D / \sqrt{n}}
\end{equation}

donde $D_i = M_{\text{FCFS},i} - M_{\text{RH},i}$ son las diferencias por orden, $\overline{D}$ es la media de diferencias, y $s_D$ es su desviación estándar.

\begin{verbatim}
from scipy.stats import ttest_rel

# Test t pareado
t_stat, p_value = ttest_rel(fcfs_ctd, rh_ctd)
print(f"Paired t-test: t={t_stat:.3f}, p={p_value:.6f}")
\end{verbatim}

\textbf{Decisión de uso:} Se reportan ambos tests (Wilcoxon y t pareado) en el Capítulo 8 (Resultados). Si hay discrepancia en conclusiones, se prioriza Wilcoxon (más robusto a violaciones de supuestos).

\subsection{Análisis de tamaño de efecto}

Los p-values indican si existe diferencia significativa, pero no cuantifican la magnitud práctica de la diferencia. El tamaño de efecto mide la relevancia práctica.

\paragraph{Cohen's d (tamaño de efecto estandarizado)}

Cohen's d expresa la diferencia de medias en unidades de desviación estándar:

\begin{equation}
d = \frac{\overline{M}_{\text{FCFS}} - \overline{M}_{\text{RH}}}{s_{\text{pooled}}}
\end{equation}

donde la desviación estándar combinada es:

\begin{equation}
s_{\text{pooled}} = \sqrt{\frac{s^2_{\text{FCFS}} + s^2_{\text{RH}}}{2}}
\end{equation}

\textbf{Interpretación según Cohen (1988):}

\begin{itemize}
	\item $|d| < 0.2$: Efecto trivial
	\item $0.2 \leq |d| < 0.5$: Efecto pequeño
	\item $0.5 \leq |d| < 0.8$: Efecto medio
	\item $|d| \geq 0.8$: Efecto grande
\end{itemize}

\textbf{Implementación:}

\begin{verbatim}
def cohens_d(group1, group2):
    """Calcula Cohen's d para dos grupos."""
    mean_diff = np.mean(group1) - np.mean(group2)
    pooled_std = np.sqrt((np.var(group1, ddof=1) + np.var(group2, ddof=1)) / 2)
    return mean_diff / pooled_std

d_ctd = cohens_d(fcfs_ctd, rh_ctd)
print(f"Cohen's d for Click-to-Door: {d_ctd:.3f}")

if abs(d_ctd) >= 0.8:
    print("  → Efecto grande (diferencia prácticamente relevante)")
elif abs(d_ctd) >= 0.5:
    print("  → Efecto medio")
elif abs(d_ctd) >= 0.2:
    print("  → Efecto pequeño")
else:
    print("  → Efecto trivial")
\end{verbatim}

\paragraph{Diferencia porcentual (interpretación práctica)}

Para facilitar interpretación operacional, se calcula la mejora porcentual:

\begin{equation}
\text{Mejora}\% = \frac{\overline{M}_{\text{FCFS}} - \overline{M}_{\text{RH}}}{\overline{M}_{\text{FCFS}}} \times 100
\end{equation}

Por ejemplo, una reducción de Click-to-Door de 45.2 min (FCFS) a 38.7 min (RH) representa:

\begin{equation}
\text{Mejora}\% = \frac{45.2 - 38.7}{45.2} \times 100 = 14.4\%
\end{equation}

Esta métrica es directamente interpretable para stakeholders (e.g., "RH reduce tiempos de entrega en 14\%").

\paragraph{Intervalos de confianza para diferencias}

Se calculan intervalos de confianza al 95\% para la diferencia de medias usando bootstrap:

\begin{verbatim}
from scipy.stats import bootstrap

# Diferencia de medias observada
diff_observed = np.mean(fcfs_ctd) - np.mean(rh_ctd)

# Bootstrap para intervalo de confianza
rng = np.random.default_rng(2025)
res = bootstrap((fcfs_ctd, rh_ctd), 
                lambda x, y: np.mean(x) - np.mean(y),
                n_resamples=10000,
                confidence_level=0.95,
                random_state=rng)

print(f"Diferencia de medias: {diff_observed:.2f} min")
print(f"IC 95%: [{res.confidence_interval.low:.2f}, {res.confidence_interval.high:.2f}]")
\end{verbatim}

Si el intervalo no incluye 0, se confirma diferencia significativa al 95\%.

	\item \texttt{-d}: Modo detached (background), el contenedor sigue corriendo tras cerrar la terminal.
	\item \texttt{-p 5000:5000}: Mapeo de puerto 5000 del contenedor al puerto 5000 del host (endpoint accesible en \texttt{localhost:5000}).
	\item \texttt{-v "\$\{PWD\}/osrm\_data:/data"}: Montaje de volumen que mapea el directorio local \texttt{osrm\_data/} (conteniendo archivos \texttt{.osrm} preprocesados) al directorio \texttt{/data} dentro del contenedor.
	\item \texttt{osrm-routed --algorithm mld}: Comando que inicia el servidor OSRM usando algoritmo Multi-Level Dijkstra (MLD) sobre el archivo de red especificado.
	\item \texttt{/data/bcs-latest.osrm}: Ruta al archivo de red preprocesado (contiene grafo vial, índices de particiones, metadatos).
\end{itemize}

\paragraph{Verificación de disponibilidad de OSRM}

Tras lanzar el contenedor, se verifica que el servidor responde correctamente:

\begin{verbatim}

\end{verbatim}

\subsection{Ejecución automatizada (\texttt{generate\_results.py})}

El script \texttt{scripts/generate\_results.py} implementa un orquestador que ejecuta el pipeline experimental completo de forma automatizada. Este script es el punto de entrada principal para reproducir resultados.

\paragraph{Arquitectura del pipeline}

El pipeline se estructura en 4 etapas secuenciales:

\begin{enumerate}
	\item \textbf{Generación de instancia sintética} (opcional, puede omitirse con \texttt{--analyze-only})
	\item \textbf{Ejecución de simulación FCFS}
	\item \textbf{Ejecución de simulación Rolling Horizon}
	\item \textbf{Cálculo y comparación de KPIs}
\end{enumerate}

\paragraph{Implementación de la función orquestadora}

\begin{verbatim}
def run_full_pipeline(synthetic_csv_path='data/synthetic_lapaz_orders_limited.csv',
                     skip_data_generation=False):
    """
    Orquestador completo del pipeline de experimentación.
    """
    base_path = os.path.dirname(os.path.dirname(__file__))
    
    print("="*60)
    print("PIPELINE DE EXPERIMENTACIÓN MDRP-BCS")
    print("="*60)
    
    # Paso 1: Generar datos sintéticos
    if not skip_data_generation:
        print("\n[1/4] Generando datos sintéticos...")
        synth_script = os.path.join(base_path, 'scripts', 'make_synth_orders.py')
        result = subprocess.run([sys.executable, synth_script],
                               cwd=base_path, capture_output=True, text=True)
        if result.returncode == 0:
            print(f"[OK] Datos sintéticos generados")
        else:
            print(f"[ERROR] Error: {result.stderr}")
            return
    
    # Paso 2: Ejecutar FCFS
    print("\n[2/4] Ejecutando simulación FCFS...")
    fcfs_script = os.path.join(base_path, 'scripts', 'run_fcfs_instance.py')
    result = subprocess.run([sys.executable, fcfs_script, synthetic_csv_path],
                           cwd=base_path, capture_output=True)
    if result.returncode == 0:
        print("[OK] Simulación FCFS completada")
    
    # Paso 3: Ejecutar Rolling Horizon
    print("\n[3/4] Ejecutando simulación Rolling Horizon...")
    rh_script = os.path.join(base_path, 'scripts', 'run_synth_instance.py')
    result = subprocess.run([sys.executable, rh_script, synthetic_csv_path],
                           cwd=base_path)
    if result.returncode == 0:
        print("[OK] Simulación Rolling Horizon completada")
    
    # Paso 4: Calcular KPIs
    print("\n[4/4] Calculando KPIs y generando comparación...")
    analyze_results()
    
    print("\n" + "="*60)
    print("PIPELINE COMPLETADO")
    print("="*60)
\end{verbatim}

\paragraph{Uso desde línea de comandos}

El script soporta dos modos de ejecución:

\textbf{Modo 1: Pipeline completo (generación + simulación + análisis)}

\begin{verbatim}
python scripts/generate_results.py
\end{verbatim}

Ejecuta las 4 etapas completas. Tiempo estimado: 15-20 minutos en hardware estándar (laptop Intel i5, 16 GB RAM).

\textbf{Modo 2: Solo análisis (asume simulaciones ya ejecutadas)}

\begin{verbatim}
python scripts/generate_results.py --analyze-only
\end{verbatim}

Útil para recalcular KPIs tras modificar la función \texttt{calculate\_kpis()} sin re-ejecutar simulaciones. Tiempo estimado: $<$ 10 segundos.

\textbf{Modo 3: Pipeline con instancia personalizada}

\begin{verbatim}
python scripts/generate_results.py --csv data/custom_instance.csv
\end{verbatim}

Permite evaluar políticas sobre instancia diferente (útil para análisis de sensibilidad).

El pipeline genera los siguientes archivos en \texttt{results/}:

\begin{itemize}

\paragraph{Manejo de errores}

El orquestador verifica códigos de retorno (\texttt{returncode}) de cada subproceso. Si una etapa falla:

\begin{enumerate}
	\item Se imprime mensaje de error con \texttt{stderr} del subproceso fallido
	\item El pipeline se detiene (no continúa a etapas subsecuentes)
	\item Se retorna código de salida no-cero
\end{enumerate}

Esto permite integrar el script en pipelines de CI/CD (Continuous Integration/Continuous Deployment) para validación automática de cambios de código.

\subsection{Trazabilidad de experimentos}

La trazabilidad documenta el contexto completo de ejecución de cada experimento, permitiendo identificar qué versión de código, parámetros, y datos generaron cada conjunto de resultados. Esto es esencial para auditoría científica y debugging.

\paragraph{Identificadores de ejecución}

Cada ejecución del pipeline se identifica mediante:

\begin{itemize}
	\item \textbf{Timestamp:} Fecha y hora de inicio (ISO 8601 format)
	\item \textbf{Instancia de datos:} Path y hash SHA-256 del archivo CSV de órdenes
	\item \textbf{Semilla:} Valor de \texttt{seed} usado para generar instancia sintética
	\item \textbf{Versión de código:} Hash de commit Git (si repositorio está bajo control de versiones)
	\item \textbf{Configuración de parámetros:} Valores de \texttt{config.py} al momento de ejecución
\end{itemize}

\paragraph{Hash de instancia para validación}

Antes de ejecutar simulaciones, se calcula hash SHA-256 de la instancia:

\begin{verbatim}
import hashlib

def compute_instance_hash(csv_path):
    """Calcula hash SHA-256 de archivo CSV."""
    sha256 = hashlib.sha256()
    with open(csv_path, 'rb') as f:
        for chunk in iter(lambda: f.read(4096), b""):
            sha256.update(chunk)
    return sha256.hexdigest()

instance_hash = compute_instance_hash('data/synthetic_lapaz_orders_limited.csv')
print(f"Instance hash: {instance_hash}")
# Output: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
\end{verbatim}

Dos ejecuciones con el mismo hash de instancia deben producir resultados idénticos (verificación de determinismo).
